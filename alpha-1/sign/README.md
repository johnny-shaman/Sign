# alpha/sign

**Sign 自身で書いたプログラム**を置く。`alpha/javascript`（JavaScript による処理系実装）が
「Sign を動かすもの」であるのに対し、こちらは「Sign で書かれたもの」である。

セルフホストへ向けた最初の足がかりとして、字句解析器と構文解析器から始めている。

| ファイル | 内容 |
|---|---|
| `lexer.sn` | 字句解析器。数字・識別子・記号の3種にトークン化する |
| `parser.sn` | 再帰下降パーサ。四則演算の優先順位と左結合を扱う |

## 実行

`alpha/javascript` の処理系に読ませる。

```bash
cd alpha/javascript
node -e "
import('./compile.js').then(async ({compile}) => {
  const I = await import('./interpreter.js');
  const src = require('fs').readFileSync('../sign/lexer.sn', 'utf8');
  const { nodes } = compile(src);
  const env = I.newRuntimeEnv(null);
  let last = I.UNIT;
  for (const n of nodes) last = I.evaluate(n, env);
  console.log(JSON.stringify(last));
});"
```

`test/sign_programs.test.js` が両ファイルを実行して結果を検証しているので、
`node test/sign_programs.test.js` でも確認できる。

## 書いてみて分かった Sign 固有の作法

これらは処理系のバグではなく、いずれも仕様から導かれる帰結である。
Sign でまとまった量のコードを書く際に繰り返し効いてくるため記録しておく。

### 1. トークン列はカンマ（直積）で積む

スペース（余積）で文字列を並べると、`String` が余積の吸収元であるため
1本の文字列に連結されてしまう（[`type_system.md`](../../documents/ja-jp/impl/type/type_system.md) §3.2）。

```sign
[`1` `+` `2`]        ` → `1+2`        スペースは連結される
[`1` , `+` , `2`]    ` → 3要素のリスト  カンマなら構造が保たれる
```

`` `123` 123 = `123123` `` が成り立つ以上これは避けられない。文字列を要素として
並べたい場合はカンマを使う。

名前付きスロット（`[key : val]`）は逆に、値が `__` でもキーが残る。ラベルは型の一部だからで、
位置スロットとはここが違う（同 ※3）。

### 2. 1要素リストはスカラーと同型

`[`2`]` は「1要素のリスト」ではなく `` `2` `` そのものになる
（[`list_model.md`](../../documents/ja-jp/impl/type/list_model.md)）。
リストを先頭から消費していくコードでは、残りが1個になった時点で
リストでなくなるため、長さによる場合分けが要る。

```sign
peek : [~ts] ?
	|ts| = 1 : ts
	ts ' 0
```

### 3. 「尽きた」を `__` で表すと次の呼び出しが消える

これが最も Sign らしい落とし穴である。残りトークンが空であることを `__` で表すと、
それを引数に受けた次の呼び出しが**完全性公理によって本体に一歩も入らず崩壊する**
（[`0_design_principles.md`](../../documents/ja-jp/impl/0_design_principles.md) 原理5）。

原理5 は `update xs` のような再帰的なリスト書き込みが末端で安全に停止することを
保証する機構だが、**再帰を続けたい場面では同じ機構が邪魔になる**。終端を値として
扱いたい場合は、番兵の値を返す。

```sign
sentinel : `end`

rest : [~ts] ?
	|ts| = 1 : sentinel
	ts ' 1~
```

### 4. コメント内にバッククォートは書けない

コメントは行頭のバッククォートで始まり、同じ行に閉じるバッククォートが無い場合に
コメントとなる（[`string_and_comment.md`](../../documents/ja-jp/guide/string_and_comment.md) §2）。
そのためコメント本文中でバッククォートを使うと、そこで文字列として閉じてしまい
後続がすべて壊れる。インラインコメントが存在しない設計の帰結である。

### 5. 制御文字はエスケープシーケンスではなく、文字リテラルで直接書く

文字リテラルは**直後の1バイトをそのまま文字として取る**（`operator_table.md` の特殊記号）。
エスケープシーケンスという概念が無いため、空白・タブ・改行もすべて同じ形で書ける。

```sign
space : \      ` 直後が空白
tab : \        ` 直後がタブ
newline : \    ` 直後に何も無い＝改行がその1バイト
```

`\n` と書くと改行ではなく **`n` という文字**になる点に注意（`\` は次の1バイトを取るだけで、
`n` を改行と読み替える機構は無い）。

なお空白とタブは行末に置くと不可視になるため、エディタや整形処理で落ちる危険がある。
言語側の制約ではないが、`.sn` ファイルを編集する際は行末の空白を除去する設定に
注意すること。改行文字（末尾に何も無い `\`）は行末が `\` で終わるため、この問題を受けない。

### 6. 文字列リテラルに生の改行は書けない

文字列は同一行内で閉じる必要がある（`sign.pegjs` の `string` 規則が `[^`\r\n]*`）。
改行を含む文字列が要る場合は、上記の `newline` 定数を連接して組み立てる。
