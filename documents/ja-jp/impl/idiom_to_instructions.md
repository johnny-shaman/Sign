# 字面と命令の対応——Sign で Sign を書く

Sign の後段を Sign で書くための土台である。

**判定はひとつだけ。ある書き方が正しいのは、それが出す命令が、手で書くつもりだった命令と同じときである。**
書きやすさと機械の良さは別々の話ではない。Sign はアセンブリに近い言い方をするので、同じ意味の綴りが
2つあるなら、命令の少ない方が普通は読みやすい方でもある。以下はその一致を実測で確かめた表である。

本書の数字は **HEAD `04bf32f2`（2026-09-16）** の実測であり、推定はひとつも無い。
アンカー（下の表）だけは、その後に入った「実行時の `__` を連結で畳む」直しの後で測り直してある
——畳む検査のぶん preprocess.sn は 3488 → 3711、lexer.sn は 587 → 602、parser.sn は 993 → 1013。
個々の字面の命令数（§2 以降）は畳みの対象を含まないものが大半で、そちらは 04bf32f2 のままである。

表の中では、改行を ⏎、字下げの TAB を → と書く。

## 1. この書き方でのコンパイラの形

### 1.1 原文は1本の綴りで、位置で持つ

器を切って渡すのではなく、**綴りと添字**を渡す。

```sign
walk : s i n ?
	i = ||s|| : n
	walk s (i + 1) (n + 1)
```

`||s||` はループの中でも **0 命令** である。綴りは `{ptr,len}` で x0/x1 に来ているので、
`i = ||s||` はそのまま `cmp x2, x1` になる。**長さを別の仮引数へ手で持ち上げてはいけない**——
42 命令が 46〜48 命令に増える（綴りによる。実測）。既に x1 に在るものを、もう一度運ぶことになるからである。

器を縮めて歩く形（`cnt (s ' 1~) (n + 1)`）は**黙って誤答する**。空の器は `__` そのものなので、
完全性公理の `cmp x1, #0 / b.eq .Lunit1` が本体より先に立ち、終了の枝に届かない。§5 を見よ。

### 1.2 状態は仮引数の並びである

Sign にループは無い。段を持つのは末尾自己再帰であり、機械の上でそれは `b .Lloop0` になる。
運ぶ状態は仮引数の並びそのものである。

既定引数のブロックは「呼ぶ側が初期値を書かなくてよい」を買える。ただし**ただではない**。

| 書き方 | 命令 | 別形 | フレーム | 1文字あたり（実行） |
|---|---:|---:|---|---:|
| 素の仮引数 `cnt : s i n ?`（呼ぶ側が初期値 `0 0` を書く） | 65 | 121 | 32 バイト | **38** |
| 既定引数で状態を持つ（`i : 0` と `n : 0` を書く） | 80 | 135 | 48 バイト | **45** |

既定の解決は呼ばれた側に在り、`.Lloop0:` は**その上**に置かれる。だから毎周、既定が渡されたかを
問い直す（`movz / cmp / b.ne` ×2 と写し2本）。内側のループでは素の仮引数で書き、既定引数は
外側の入口に置くのがよい。

### 1.3 出来た端から書き出す

器を返すと sret になる。sret 自体は正しく、追記の自己再帰は本物のループになる（`bl` は 0、
確保も段の伸びも1要素あたり 0）。しかし**返す器の上界が書ける形は狭い**。

| 形 | 結果 |
|---|---|
| `(s ' 0) (f (s ' 1~))`（1要素ずつ） | 出る（88 命令、実行 34/要素） |
| `(s ' 0~) (f (s ' 1~))`（1切り出しずつ） | **断られる** |
| 1文字ずつ足して Int の計数で回す | **断られる** |

上界は `konst + Σ coef×‖仮引数‖ + coef×μ‖仮引数‖` としか書けない。桁数が値で決まる 10 進の
書き出しは、この言葉の外側に在る。だから**書き出しは器を返さず、その場で書く**。

```sign
put_str : s i ?
	i >= ||s|| : i
	out # (s ' i) : put_str s (i + 1)
```

書き込みを**枝の条件に置く**のがこの形の要である。`#` の値は書き込み先の番地であって `__` には
ならないので、枝は必ず取られ、枝の値が続きになる。

順に並べるだけなら `seq` が使える。**引数は左から順に評価される**（実測：8引数まで綴りの順に出た）。

```sign
seq8 : a b c d e f g h ? h
```

| 並べ方 | 命令 | `bl` |
|---|---:|---:|
| `seq2` を入れ子（4つ並べる） | 43 | 3 |
| `seq4`（4つ並べる） | 34 | **1** |
| `seq6`（6つ並べる） | 46 | **1** |

n 引数の `seq` を1本用意する方が、入れ子より `bl` が減る。

### 1.4 表は引く。枝で分けない

`match_case` は**直線の鎖**である。枝がいくつあっても、まとめも飛び表も出ない。

| 枝の数 | 命令 | 別形 | 1枝あたり |
|---:|---:|---:|---:|
| 2 | 30 | 48 | — |
| 5 | 54 | 87 | 8 |
| 12 | 110 | 178 | 8 |
| 20 | 174 | 282 | 8 |

実行はさらに素直で、**k 番目の枝に当たるのに `6k + 14`** である（12枝の末尾 86、20枝の末尾 134、実測）。

同じ 12 の分岐を手で書いたもの（どれも同じ値 120 を返すことを確かめてある）：

| | 静的 | 実行（末尾に当たる） |
|---|---:|---:|
| Sign の `match_case` 12 枝 | 110 | **86** |
| 手書きの直線の鎖 | 51 | 27 |
| 手書きの値の表 | 10 | **8** |

対して、名前付きスロットの表は**引くのがほぼ無料**である。

| 引き方 | 静的 | 実行 | 表の大きさに依るか |
|---|---:|---:|---|
| 静的な鍵 ``(infix ' `+`) ' tier`` | 18 | **16** | 依らない（`+` `*` `:` `&&` `%` すべて 16） |
| 実行時の鍵 `f : k ? (infix ' k~) ' tier` | 53 | 91〜383 | **依る**（35 行の線形走査） |

実行時の鍵は綴りの長さで先に落とし、一致の確認は末尾から前へ向かって行う。
`%` で 91、`+` で 154、`:` で 210、表に無い綴り（`><`）で 383。**外れが一番高い。**

だから**綴りが静的に書けるところは必ず静的に書く**。分岐で書くべき所は表で引き、
表で引けない所（レジスタ番号など）は、そもそも表にしない——`x` と 10 進の連結で済む。

### 1.5 失敗は `__`、受けるのは `|`

`__` は呼び出しの鎖を通り抜ける。各段の入口が `movz / cmp / b.eq` の3命令で、本体へ入らずに
`__` を返す。`|` は分岐（csel ではない。右辺を評価しないため）で、**8 命令**である。

ただし**引数として来た `__` は `|` で捕まらない**。完全性公理の見張りが本体より先に立つので、
`|` が捕まえられるのは関数の**中で**生じた `__` だけである。

```sign
c : x ? (b x) | 99
```

`c __` は 99 ではなく `__` を返す（実機・インタプリタとも一致）。

**逆に、関数の中で表を外したときの `__` は `|` で捕まる。** これが「鍵が無ければ既定へ」を
1行で書ける根拠である。JS の `??` / `||` がそのまま1本の `|` になる:

```sign
char_size_of : cs ? (charsets ' cs~) | (charsets ' default_charset~)
```

``char_size_of `nosuch` `` は両エンジンとも `1`（＝ ascii の幅）を返す。**引数として届いた `__`
は素通り、自分で作った `__` は `|` が受ける**——同じ `__` でも、どこで生じたかで振る舞いが
分かれる。

### 1.6 呼ばれない関数は出せない

仮引数の型は呼び出しサイトから決まる。**駆動されていない関数は診断になる。**

```
seq2: 仮引数 b の渡し方が決まりません（直和か族）
```

だから Sign で書く後段の各ファイルは、**自分を使い切る駆動行を持つ**か、上から呼ばれる形で
同じ翻訳単位に入っていなければならない。「まだ使っていないが置いておく」は成立しない。

## 2. 字面 → 機械 → 代金

「命令」はプログラム全体の既定の出力、「別形」は `regAlloc:false`。
**フレームは測っている関数自身の `stp x29, x30` の有無**である（`_.main` は呼び出しがあれば必ず取るので、
そちらは数えない）。実行/回 は qemu のトレースから。すべて実測。

### 2.1 束縛と呼び出し

| 字面 | 機械の上で何になるか | 命令 | 別形 | フレーム |
|---|---|---:|---:|---|
| `x : 42` ⏎ `x` | `mov x9,#42 / mov x0,x9 / ret` | 3 | 3 | 無 |
| `x : 6 * 7 + 1` を1回使う | 定数畳み込みは無い。式がそのまま出る | 7 | 31 | 無 |
| 同じ束縛を2回使う | **右辺がもう一度出る**（`mul` が2つ） | 19 | 55 | 無 |
| 同じ束縛を3回使う | 3つ目も出る | 31 | 78 | 無 |
| `x : f 3` を1回使う | `bl f` 1回＋`.Lbind_x` へ `str`。読むたび `adrp / add :lo12: / ldr` の3命令 | 22 | 34 | — |
| 同じ呼び出しの束縛を2回使う | `bl` は1回のまま。`adrp/add/ldr` が2組 | 34 | 48 | — |
| `add : a b ? a + b` ⏎ `add 3 4` | 呼ぶ側は手書きと同一。呼ばれた側は仮引数ごとに見張り3命令 | 18 | 34 | `add` は**無** |
| 既定引数を省く / 渡す | 省いた印は niche。呼ばれた側の本体は**同一** | 28 / 28 | 39 / 41 | 有 |
| `app $add 3 4`（`$` で関数を渡す） | `app` が消え、呼び出しが `bl add` になる | 18 | 34 | `add` は**無** |

**束縛は値ではなく置換である。** 右辺が式なら使うたびに出し直され、代金は使用回数に比例する。
右辺が**呼び出し**のときだけ一度だけ評価され、`.data` のセルに置かれる。

**`blr` はどこにも出ない。** `$` は静的に解決され、直接分岐になる。`app $add 3 4` では
中継の `app` そのものが消えて `bl add` だけが残る。前段3ファイルを通しても `blr` は 0 である。
実行時の関数値が無いことの裏返しでもある（§5.2「関数の番地を器に入れる」）。

### 2.2 比較と分岐

| 字面 | 機械の上で何になるか | 命令 | 別形 | フレーム |
|---|---|---:|---:|---|
| `\0 <= c <= \9`（両端が字面） | `sub x9,x0,#48 / cmp x9,#9`（符号なし幅比較）＋ csel | **22** | 34 | **無** |
| `(\0 <= c) & (c <= \9)` | 比較2本ぶん。単位元の判別（`cmp / ccmp / csel`）も2組 | **40** | 56 | **有** |
| `a <= c <= b`（両端が仮引数） | 幅比較の綴りを失う | 35 | 55 | 有 |
| `n > 3` を値として返す | 前提（左辺）が返る。単位元の判別つき | 20 | 31 | **無** |
| `n > 3` を条件に使う | 同じ7命令を出したあと `cmp / b.eq` で読み直す | 30 | 38 | **有** |
| `(g n) &#124; 0` | `cmp x0,niche / b.ne` の分岐（短絡のため csel ではない） | 48 | 62 | 有 |
| 同じものから `&#124; 0` を外した下敷き | — | 40 | 53 | 有 |
| `__` が3段の呼び出しを通る | 各段 3 命令で素通し。途中は末尾呼び出し | 35 | 56 | 葉は無 |

**連鎖比較と `&` は同じ意味ではない。** 18 命令ちがい、しかも `&` の側だけがフレームを取る。
文字1つごとに払う場所なので、レキサでは必ず連鎖で書く。良い道は**両端が字面のときだけ**通る。

**比較を条件に使うとフレームが生える。** 値の形（20 命令、フレーム無）と条件の形（30 命令、フレーム有）は
同じ7命令を出し、条件の側はそれを `cmp / b.eq` で読み直す。その読み直しのために生じたレジスタの圧が、
枝の結果を呼び出し先保存レジスタへ押し出し、退避のためにフレームが要る。

#### 段の代金——スタックは、この言語では意味論の一部である

Sign にはループが無く再帰しか無いので、**入力の大きさがそのまま段数になる**。命令数の表だけを見ても
「その入力で走るか」は分からない。段の代金は2つの直線で測れた（どちらも傾きは区間によらず一定）。

| 何 | 1つあたり | 例 |
|---|---:|---|
| 非末尾の算術再帰 | **32 B/段** ＋ 48 | 8000 段で 256048 B。256000 B では踏み抜き、256256 B で通る |
| `preprocess.sn`（入力1文字あたり） | **50 B/文字** ＋ 592 | 13471 文字（＝`preprocess.sn` 自身のバイト数）で 674142 B。663552 B では踏み抜き、679936 B で通る |
| 末尾再帰・相互末尾再帰 | **0**（TCO でループになる） | 64KiB のままで 200000 段が通る |

前段4ファイルを**自分と同じ大きさの入力**として通すのに要るスタック（`50n + 592`、LF のバイト数で）：
`preprocess.sn` 13471 → 659KiB、`operator_table.sn` 9703 → 475KiB、`parser.sn` 4852 → 238KiB、
`lexer.sn` 2025 → 100KiB、`emit.sn` 1760 → 87KiB。**自己ホストには最低でも 1MiB 要る。**

50 B/文字 のほとんどは**予約であって書き込みではない**（実測では1文字あたり約 4.7 B しか書かない）。
素の枠はどれも 96 B 以下で、深さは実行時に大きさが決まる `sub sp, sp, xN`（sret の返値スロット）から来る。
**踏み抜きが疎になるのはこのためで、壊れ方が入力の大きさごとにばらばらだったのもこのためである。**

スタックは image の**下**に置いてある（`alpha/javascript/qemu/link.ld`）。

```
0x40000000  _stack_limit ＝ RAM の下端。ここより下は RAM の外
     ↑ sp はここへ向かって下りる
_stack_top ＝ image の基底（既定なら 0x41000000）
     .text / .rodata / .data / .bss
```

踏み抜くと RAM の外へ出て外部アボートになり、`start.s` の例外表が `STKOVFLT` と FAR/ESR/ELR を流して
0.2 秒で抜ける（`-M virt` の 0x40000000 直下は PCIe ECAM の窓で、書き込みは ESR 0x96000050＝外部アボート）。
限界の 128 B には番人を敷いてあり、落ちずに戻ってきた踏み抜きは `STKSMASH` で捕まる。
sp は `_stack_top`（＝image の基底）から**下へしか動かない**ので、**踏み抜きが image へ届くことはない**。
以前はスタックを image の直後に置いて 64KiB しか与えておらず、`preprocess.sn` は
1300 文字で自分の `.rodata` を、1500 文字で自分の `.text` を書き換えながら走っていた——診断は1件も出ず、
1400 文字では入力長を返し、1425 文字では止まらなくなり、2300 文字を超えるとまた全部正しくなった
（行き過ぎて image を飛び越すため）。**「大きい入力が通った」はスタックが足りている証拠にならない。**

大きさは呼ぶ側が決める：`runAsm(asm, { stack, memMB })`。既定は **16MiB**——いま書ける `.sn` のどれに対しても
20 倍以上の余裕がある。置き場所のおかげで大きく取っても代金は番地だけで、実測でも起動時間は変わらない
（既定・64KiB・64MiB のどれでも 0.2 秒台）。image がスタックの上に載るので、RAM に収まらない大きさは
**リンクで落ちる**（`-m` を増やすなら `memMB` も一緒に渡す）。

### 2.4 器と表

## 5. 書いてはいけない形

断られる形と、**黙って誤答する形**を分けて置く。断られる方は安全であり、黙る方が危ない。

### 5.1 黙って誤答する形

| 書いてはいけない | 何が起きるか | 代わりにこう書く |
|---|---|---|
| 器を縮めて歩く<br>`cnt : s n ?` ⏎ →空の綴りと比べる枝 ⏎ →`cnt (s ' 1~) (n + 1)` | **`__` が返る**（実機・インタプリタとも）。空の器は `__` そのものなので完全性公理が本体より先に立ち、終了の枝に届かない。長さを 0 と比べても、`!s` に書き換えても同じ | 添字で歩く（§1.1）。どうしても縮めるなら **1手前で止める**——長さを 1 と比べて `n + 1` を返す（45 命令、正しい） |
| `(s ' 0) == 104`（Char と Int） | 実機は 104、インタプリタは `__`。符号位置が違うときは両方 `__` なので、**真の場合だけ**食い違う | Char どうしを比べる：`(s ' 0) == (t ' 0)`（49 命令、一致） |
| Char と1文字の綴りを比べる | 1要素の器に持ち上がって綴りの比較ループが回る。観測される値も両側で違う | 同上 |
| `f : p i v ? (p + (i * 8)) # v` を layer 1 で | **断られずに出る。** 実機は書き込み、インタプリタは `__`。同じことを1つの式で書けば（`($x + 8) # 7`）門が「`$` が作った番地は算術に使えません」で止める——**門は構文の形しか見ておらず、仮引数を1回挟むと抜ける** | 番地の算術をしない。書き出し先は束縛した定数にする（`out : 0x9000000`、5 命令） |
| 同じ名前を2回定義する | 診断 0。インタプリタは後の定義を採り、機械は同じラベルを2つ出してアセンブラが断る（`symbol 'g' is already defined`）。**3か所で決まって、どこも一致していない** | 名前を重ねない |
| Int の累算に Char の算術を混ぜる<br>`(acc * 10) + ((s ' i) - zero_ch)` | **`acc` が 2^53 を越えると分かれる。** 実機は 64bit で正しく、インタプリタは倍精度で計算する——2^53+1 は**黙って丸まり**（`…740993` が `…740992` になる）、さらに大きいと `__` になる。`(acc * 10) + 7`（Int だけ）なら 18 桁でも一致するので、**混ぜたことが原因**である | 2^53 を越えない所でだけ混ぜる。越えうるなら Char を先に Int へ落として累算する。根は `interpreter.js` にある（下の注） |

**Int に Char を混ぜた算術の注**（2026-09-16、移植の門を攻めているときに見つけた）。
`interpreter.js` は `Int` を **2^53 までは JS の `number`、それより大きければ `bigint`** で持つ
（`fromBig`）。文字の算術の枝はその入口で `typeof l === "number"` しか見ていないので、
左辺が 2^53 を越えて `bigint` になった瞬間に枝へ入らなくなり、`__` へ落ちる。その手前でも
枝の中は `number` の算術なので、2^53 を越えた結果は倍精度に丸まる。**機械の側は 64bit 整数で
一貫している**ので、分かれるのはインタプリタの側である。

最小の再現（`zero : \0` を置いて）:

```sign
dn : s i acc ?
	i >= ||s|| : acc
	dn s (i + 1) ((acc * 10) + ((s ' i) - zero))
dn `9007199254740993` 0 0
```

インタプリタ `9007199254740992` / 実機 `9007199254740993`。`+ ((s ' i) - zero)` を `+ 7` にすると
**19 桁でも一致する**（`7777777777777777777`）——2^53 を大きく越えていても、`Int` だけなら
`bigint` へ上がって正しく回る。**これは移植した `.sn` の誤りではない**（`target_info.sn` の `digit_num` が
この形で、20 桁の幅プリフィックス `18446744073709551616x41` を書くと `lit_width` の答えが
インタプリタ `-1` ／ 実機 `__` に分かれる）。直す場所は `interpreter.js` であり、**この文書では
書き方の注意として置くに留める**——直し方の決定は利用者のものである。

`alpha/sign/emit.sn`。**診断 0、576 命令、別形 801、`bl` 25、`blr` 0、末尾ループ 3、フレーム 11。**
実機で走らせると UART に本物のアセンブリが出る。

```
movz x9, #42
add x0, x1, x2
sub x10, x11, x12
.err x0, x1, x2
```

最後の行は `><` が表に無いことを `|` が受けた結果である。

```sign
`emit.sn — 後段の最初の一枚。綴りを文字として書き出す`

`operator_table.sn`@~

`--- 書き出し先。番地は束縛するだけで、算術はしない ---`

out : 0x9000000

`--- 並べる。左から順に評価され、最後の値が返る ---`

seq2 : a b ? b
seq4 : a b c d ? d
seq8 : a b c d e f g h ? h

`--- 1文字 ---`

put_char : c ?
	out # c

`--- 綴り。添字で歩く（器を縮めると完全性公理で止まらない） ---`

put_str : s i ?
	i >= ||s|| : i
	out # (s ' i) : put_str s (i + 1)

`--- 10 の冪。n を収める桁を選ぶ ---`

scale : n d ?
	(n / d) = 0 : d / 10
	scale n (d * 10)

`--- 上の桁から 1 桁ずつ。`%` は出ないので割り目で書く ---`

put_digits : n d ?
	d = 0 : n
	out # (48 + ((n / d) - (((n / d) / 10) * 10))) : put_digits n (d / 10)

put_dec : n ?
	n = 0 : put_char 48
	put_digits n (scale n 1)

`--- レジスタと即値。表は要らない——綴りと10進の連結である ---`

put_reg : n ?
	seq2 (put_char 120) (put_dec n)

put_imm : n ?
	seq2 (put_char 35) (put_dec n)

`--- 綴りから命令の綴りを引く。無い綴りなら __ が返る ---`

mnemonic : k ?
	(asm_infix_signed ' k~) ' gpr_signed

`--- 一行ずつ ---`

put_alu : op d n m ?
	seq8 (put_str op 0) (put_char 32) (put_reg d) (put_str `, ` 0) (put_reg n) (put_str `, ` 0) (put_reg m) (put_char 10)

put_movz : d n ?
	seq4 (put_str `movz ` 0) (put_reg d) (put_str `, ` 0) (seq2 (put_imm n) (put_char 10))

`--- 綴りが表に無ければ .err を吐く（__ を | で受ける） ---`

put_infix : k d n m ?
	put_alu ((mnemonic k) | `.err`) d n m

`--- 駆動 ---`

main : x ?
	seq4 (put_movz 9 42) (put_infix `+` 0 1 2) (put_infix `-` 10 11 12) (put_infix `><` 0 1 2)

main 0
```

この 1 枚が §1 の6つをすべて使っている。

| 節 | どこで |
|---|---|
| 1.1 位置で持つ | `put_str s i` |
| 1.2 状態は仮引数 | `put_digits n d` / `scale n d`（内側なので既定引数を使わない） |
| 1.3 出来た端から書く | `out # (s ' i) : put_str s (i + 1)` と `seq8` |
| 1.4 表を引く | `mnemonic`（実行時の鍵）。レジスタ名は表にせず綴りの連結 |
| 1.5 失敗は `__`・受けるのは `&#124;` | `put_infix` の ``(mnemonic k) &#124; `.err``` |
| 1.6 呼ばれて初めて出せる | `main` が全部を使い切っている |

### 6.1 2枚目——`target_info.sn`（型システムと Pass 4 の継ぎ目）

`alpha/sign/target_info.sn`。**診断 0、1293 命令、別形 2053。** 表が8つと、そこからの1つの還元、
それに字面のプリフィックスを分ける小さな走査が乗る。**表だけの枚（`operator_table.sn`、1 命令）と
歩く枚（`preprocess.sn`、3711 命令）の中間**にあたり、両方の代金が1枚に立っている。

移した先が同じ答えを出すことは `test/target_info_sn.test.js` が見る。問いは手で選んでいない
——`target_info.js` の関数と表を1つ残らず包んでコーパスと一式を走らせ、**実際に立った問いだけ**を
拾って表にしてある（`test/target_info_reached.js`、コーパス 41 通り＋一式 40 通り）。

**緑は「合っている」ことの証拠にならない**ので、移した `.sn` と `target_info.js` を1か所ずつ壊して
門が落ちることも見た。壊し方は**この工程が実際に踏む形**で選んである——幅・符号・`match_case` の
1本の腕・未対応ターゲットの落とし所・表の鍵の綴り・charset の表・数の1つずれ。
`no_width : 0 - 1` を `no_width : __` にしたときだけ答えではなく
`まだ出せない識別子です（no_width）` で**出せなくなる**——`__` の束縛には名前が付かない。

**壊す前に、壊れたことを確かめる。** 変異が注釈に当たっていたり意味を変えていなかったりすると、
「門の穴」と「効かない変異」が見分けられない。55 本を 413 通りの問いに当てて、**全部が
1つ以上の答えを動かす**ことを先に見た（`効かない` 0 本）。

走る行の 1.60 倍は、**ほぼ1か所に集中している**。

移植で分かったこと（表の代わりに算術で書ける所）: 桁の値は 10 枝の `match_case` ではなく

### 6.3 門の広さは**畳み方**が決めている

いまの門は **229 通りの問い × 2 エンジン（インタプリタ・qemu）＋ 行と腕の 38 本 ＋ 移さない枝の
1本 = 497 検査**である。最初は 338 だった。増えたのは Sign 側を直したからではなく、**問いの
畳み方を直したから**である。移植の門が捕まえられる上限は「誰かが実際に立てた問い」だが、その
一覧を作るときに**同じ答えの問いを1つに畳んで**いた。ここに穴があった（全部、実測で確かめた）。

最初の門に 51 本の変異（`.sn` へ 26 本・`target_info.js` へ 25 本）を当てると、
**36 本しか赤にならなかった**。素通りした 15 本はこうである。

| 素通りした壊し方 | なぜ見えなかったか |
|---|---|
| `aarch64_firmware` の `float` を 4 にする／鍵の綴りを崩す（Sign・JS 両方） | `widthsOf("aarch64_rpi")` と `widthsOf("aarch64_firmware")` を「答えが同じ」で `aarch64_qemu` へ畳んでいた。**鍵は行である**——答えが同じでも Sign 側は別の行を読む |
| `Raw` の符号・クラス（Sign・JS 両方） | `reduceToMachineType("Raw", …)` を誰も問うていなかった |
| `is_access` の 2 / 4 / 16 の腕（Sign・JS 両方） | `literalParts(…).width` を「数が返る」で畳むと、**5本の腕が1本になる** |
| `utf32` の上限を1つずらす（Sign・JS 両方） | `charLimitOf("utf32")` を誰も問うていなかった |
| `size_of` の「未対応なら `__`」の見張りを落とす（Sign） | 下の 6.4 を見よ。**腕の順番**は鍵でも腕でもないので、行を数えても出てこない |

畳んでよいのは**Sign 側が同じ道を通る問い**だけである。字面の中身（`0x1234` と `0x5678`）は
畳んでよく、表の鍵と腕の値は畳んではいけない。直したあと、**同じ 55 本（6.4 の見張りを落とす
4本を足した）を当て直して 55/55 が赤**になる。

**「答えが `__` でない問い」の数は、広さの目安にしかならない。** 直して 70 → 117 通りに増えたが、
そこから先に足した問い（未対応ターゲット × `Unit`）は**全部 `__` と答える問い**なので、この数は
1つも動かない。それでも門は広がっている——見張っているのが「値」ではなく「断り方」だからである。

**JS 側も壊して確かめること。** Sign 側だけを壊すと、「両側が一緒に動く門」でも同じ点数に見える
——実際この枚は `pass3` / `pass4` / `layout` / `interpreter` / `option_ms` が引いているので、
`target_info.js` を壊すと**Sign 側をコンパイルする道具も一緒に変わる**。25 本当てた結果、
落ち方は「答えが分かれた」か「出せなくなった」のどちらかで、**期待値を共有しているせいで
素通りしたものは1本も無かった**。素通りした 7 本は、Sign 側の双子（同じ行・同じ腕を壊したもの）
とまったく同じ問いの穴である。**両側を同じ形で壊して、穴が同じ所に開いていることまで見る**
——片側だけなら「門が Sign を Sign と比べている」可能性が残る。

**機械の側も本当に落ちる。** 赤になった変異のうち、**qemu の列が一度も落ちなかったものは 0 件**
だった（`.sn` を壊すと解釈器と機械が同じ数だけ落ちる）。`target_info.js` の `gpr` を 4 にしたときは
機械の列が「出せない」に変わる——**コンパイラ自身が同じ表を引いている**からである。

念のため、**機械の答えの側を嘘にして**も見た（`qemu_run.js` の `asInt` に `+1`）。結果は
**解釈 0 / 機械 175 が赤**——qemu が返した x0 がそのまま比較へ流れていることの、直接の証拠である。
「命令が出ている」ではなく「その命令が返した数」を見ている、と言えるのはこの1回のおかげである。

**それでもコーパスの外は見えない。** コーパスの外の綴り（`Float`・`Vector`・`Raw`・`utf32`・
`1x`〜`16x` の幅つき字面・`aarch64_rpi` / `aarch64_firmware`・未対応ターゲット）を 28 本 × 8 通りの
`option.ms` で 224 回コンパイルすると、**55 通りの問いが立ち、そのうち 37 通りは門の表に無かった**。
表を広げたいまでも **27 通りは外**である（残りは字面の中身が違うだけで、Sign 側は同じ道を通る）。
移した `.sn` はその外側の問いにも、解釈器でも実機でも JS と同じ答えを返した——最初の表で外に
出た 37 通りで 232 検査、いまの表で外に出た 27 通りで 180 検査、どちらも食い違い 0 である。
だが**答えが正しいことと、門が見ていることは別**である。次の枚を移すときは、移す前に
「その枚へ誰が何を問うか」を測ること。

そこで分かった、**コーパスにも一式にも道が無い**もの:

* **`Vector` はどの `.sn` からも立たない。** `16x…` の字面は `Address` として型が付く（実測）。
  `Vector` になる道は「片方が既に `Vector` の昇格」しか無く、最初の `Vector` を作る所が無い。
  だから `Vector` の行は **`target_info.test.js` の手書きの検査からしか触られない**。
* **`Float` は前段までしか行かない。** `x : 1.5` は診断 0 で通るが、機械は
  `浮動小数はまだ出せません（1.5）` で断る。幅の表は引かれるので門は見えるが、**実機で
  走らせた Float の値は1つも無い**。
* **幅の混ざった `Struct` は、新しい問いを1つも立てない。** `Int` と `Float` を並べた器も、
  `String` と `Int` を並べた器も通したが、立つのは**欄ごとのスカラーの還元**だけである
  （`reduceToMachineType("Int"|"Float"|"String"|"Char", …)`）。並びの大きさを出すのは
  形を解決する側の仕事で、この枚の責務ではない——**`Struct` の鍵は表に無く、`__` の1本道**
  なので、器の側から門を広げることはできない。

### 6.4 腕の順番は、鍵でも腕でもない

門を攻めていて、**行を1本ずつ数えても出てこない穴**が出た（2026-09-16）。`size_of` の姿はこうである。

```sign
size_of : ty tg ?
	!(widths_of tg) : __
	(fixed_size ' ty~) : (fixed_size ' ty~)
	width_by_class (widths_of tg) (class_of ty)
```

1本目の見張りを落としても、門は **497 検査すべて緑のまま**だった。落とすと
``size_of `Unit` `cortex_m` `` が `__` ではなく **0** を返す——`Unit` は幅が型名だけで決まるので、
ターゲットを見ずに答えてしまう。**分からないターゲットで `Unit` だけ幅を答える**という、原理4 が
一番嫌う形である。同じことが還元の側にもあり、`mt_signed` / `mt_class` の
`!(size_of ty tg) : __` はどちらも**未対応ターゲット × 具体型でしか分かれない**。

問いを3つ足して閉じた（`sizeOf("Unit","cortex_m")` /
`reduceToMachineType("Unit","cortex_m")` / `reduceToMachineType("Int","cortex_m")`）。
**畳むときに落ちたのは「答え」ではなく「順番」である**——`Int` × 未対応と `Unit` × 未対応は
JS では同じ `null` だが、Sign では**違う腕を通って**同じ答えに着く。

`.sn` の腕を1本ずつ落として、門の表よりずっと広い問い（508 通り）に当てると、**最初の表では
7 本が門の外**だった——この3つの見張りと、`is_access` の 2 / 4 / 8 / 16 である。いまは
**観測できる腕は全部、門が見ている**。残るのは、落としても**どの問いでも答えが変わらない**
7 本である:

| 落としても答えが変わらない腕 | なぜ |
|---|---|
| `is_digit` / `fam_ok` / `is_access` の末尾の `__` | 当たる腕が無ければ `__` になる（完全性公理）。**書いてあるのは読む人のためで、機械のためではない** |
| `digit_run` / `digit_num` の長さの見張り（`i >= \|\|s\|\|`） | 範囲の外の `s ' i` は `__` を返し、次の腕が `__` を弾く。先回りの見張りである |
| `lit_family` の `(digit_run s 0) = 0 : __` | 同上（`s ' n` が範囲の外） |
| `bits_to_bytes` の `no_width` | `lit_width` の末尾の余積（`… &#124; no_width`）が同じ値を補う |

**これは「消してよい」ではない。** 計っているのは解釈器の値だけで、機械の側（命令数・
`drive` の行）は別である。`drive` の 20 行は解釈器では1つも答えを動かさないが、落とせば
その関数が「呼ばれていない」ことになって**機械が出せなくなる**（§1.6）。

### 6.5 見えているか——門が自分の穴を名指しする

上の穴は全部、**変異を総当たりで回して**見つけた。門は1回で qemu を 465 回まわすので1本あたり
数分かかり、55 本を6並列で回しても小1時間である——**毎回やる形ではない**。だから門の中に
**行と腕を1本ずつ数える検査**を置いた（`target_info_sn.test.js` の「見えているか」）。
これは qemu を1回も呼ばない（JS の答えだけを見る）ので、代金はほぼ 0 である。

やり方は変異そのものである。`target_info.js` の**行を1つだけ意味の変わる値へ置き**、
表の問いの答えが1つでも動くかを見る。動かなければ、その行は門の外に居る。

```
ok   見えている target_widths `aarch64_rpi` ' gpr
FAIL 見えない   signedness `Raw` ——この行は誰も問うていない。Sign 側に何を書いても門は緑である
```

**ずらし方は「意味が変わる値」でなければならない。** 綴りを汚す（`unsigned` → `unsigned!`）のでは
足りない——JS の還元は `SIGNEDNESS[type] === "signed"` としか聞かないので、`unsigned` をどう汚しても
答えは変わらず、**JS 側でも観測できない**。それは門の穴ではなく観測点が無いだけである。だから
符号は裏返し、クラスは別のクラスへ移し、幅は隣の数へ動かし、腕は落とす。

行の名前も値も `target_info.js` から取る。検査の側に一覧を写すと、**表が増えた日に写した方だけが
古くなる**——この工程が何度も踏んでいる形である（`operator_table` の2つの綴り、`string_and_comment`
の7か所）。そのために `ACCESS_WIDTHS` と族の綴りを export し、族を正規表現の文字クラス
（`[xurb]`）から表へ出した。**通る字面は1つも変わらない**（15346 通りの問いで確認）。
`charLimitOf` も三項から表にした——知らない charset が ascii の上限へ落ちるのが
`DEFAULT_CHARSET` に従った結果ではなく**三項の else に居合わせた結果**だったので、
既定を変えた日に幅だけが動く形になっていた。

いまは **38 本の行と腕がすべて「見えている」**。最初の表に当てると **15 本を名指しで赤にする**
——6.3 の表の穴が、変異を1本も回さずにそのまま出る。

**同じ 15 ではない。** 変異で素通りした 15 本のうち **14 本**がこの検査に出る。出ないのは
`size_of` の見張り（6.4）で、行でも腕でもないからである。逆にこの検査は
`is_access` の **8 の腕**も名指しする——そこは変異を当てていなかった所で、**回した実験より
広い**。**行を数える道具と、壊して回す実験は、別のものを見ている。両方いる。**

**行が消えたことも見ない。** 数えるのは `target_info.js` に**いま在る**行なので、行を1つ
落とせば検査も1つ減るだけである（実測で 38 本 → 37 本）。消えたことを赤にするのは
「答え」の側の仕事で、実際 `ACCESS_WIDTHS` から 16 を落とすと答えが分かれて落ちる。
本数を golden に置かないのは、**行が増えるのは正しい変更**だからである。
