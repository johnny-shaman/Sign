# レンジ式とスタックABI仕様

この文書は、Sign言語における**レンジ式（Range Expression）**の構文・意味論と、
**スタックベースのカリー化ABI**について定義する。

---

## 設計原則：静的機能のみ

SignはCと同様に、**コンパイル時に決定できる静的な機能のみ**を言語仕様として保証する。

- 動的ディスパッチ・遅延評価・GCは言語の責務ではない
- 境界が静的に決まる構造はコンパイラが完全に解析できる
- 動的な振る舞いが必要な場合はユーザーが上のレイヤーとして積む

これにより、Sign自体はゼロコスト抽象化の静的レイヤとして機能する。

### 先行プロジェクトとの比較

同様の思想に立つ先行プロジェクトとして、Static TypeScript（AssemblyScript）、rPython、Rust、Zig がある。
Signはこれらと設計軸を共有するが、既存言語のサブセットではなく**最初から制約込みで設計された独立言語**である。

| 観点 | C | Rust | Zig | Static TypeScript | rPython | Sign |
|------|---|------|-----|------------------|---------|------|
| 起源 | 独自設計 | 独自設計 | 独自設計 | TSのサブセット | Pythonのサブセット | **独自設計** |
| 主な用途 | システム・組み込み | システム・WASM | システム・C互換 | WASM・組み込み | JIT生成器 | **低レイヤ、組み込み、WASM、AI生成** |
| 静的型のみ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| GCなし | ✓ | ✓ | ✓ | ✓ | ✗（独自GC） | ✓ |
| ヒープ管理 | 手動（malloc/free） | 所有権（Box/Vec） | 明示アロケータ | 部分的に手動 | RPython GC | **allocaファースト** |
| クロージャコスト | 手動（関数ポインタ） | あり（Fn トレイト） | なし（手動キャプチャ） | あり | あり | **コンパイル時特殊化（コストゼロ）** |
| 型システム | 構造（弱い） | 代数的 + トレイト | comptime構造的 | 構造的 | フロー解析 | **圏論的** |
| ループ表現 | `for`/`while` 文 | `for`/`while`/イテレータ | `for`/`while` 文 | `for`/`while` 文 | `for`/`while` 文 | **レンジ式（返値あり）** |
| 親言語の負債 | なし | なし | なし | あり（TSの動的機能） | あり（Pythonの動的機能） | **なし** |
| BIOS から書けるか | ✓ | △（コアライブラリ依存） | ✓ | ✗ | ✗ | ✓ |
| AI 生成親和性 | △ | △（所有権が複雑） | △ | △ | ✗ | **✓（設計の主目的）** |

**Signの優位点**：親言語の設計負債がなく、静的制約を構文レベルから一貫して設計できる。
特に「クロージャ = コンパイル時特殊化」によりヒープ確保が設計上存在せず、
Rust の所有権システムや Zig の手動アロケータを必要としない。

## 1. レンジ式（Range Expression）

### 1.1 基本構文

```
[start ~ end]
```

**「返値を持つfor式」**として定義される。`for` キーワードは存在しない。
レンジ式自体が**関数**であり、評価されると値を返す。

```sign
` 1から5まで
` → 1, 2, 3, 4, 5
[1 ~ 5]

` インデックス変数に束縛する
i : [1 ~ 5]
```

### 1.2 ステップ付きレンジ

```
[start ~+ step ~ end]
```

ステップを明示したレンジ。ストライドアクセスパターンが構文に現れるため、
コンパイラがSIMD化・ループアンロールの判断に必要な情報を静的に持つことができる。

```sign
` → 0, 2, 4, 6, 8, 10
[0 ~+ 2 ~ 10]
```

### 1.3 開端レンジ（カウンタ）

```
[start ~+ step]
```

上界を持たない開端レンジ。Cの無限ループカウンタ（`int c = start; ...`）に相当する。
**終了条件は呼び出し元の責任**であり、言語は保証しない（Cと同じ立場）。

```sign
` 0から始まる無限カウンタ
[0 ~+ 1] 
```

## 2. レンジ式による要素アクセス（`'`）

`'` 演算子（get）はコレクションから要素を取り出す。
インデックスとしてレンジ式を使うことで、スライス操作を表現できる。

```sign
[0 ~+ 2 ~ 10] ' [1 ~ 3]
```

```
[0 ~+ 2 ~ 10]  →  [0, 2, 4, 6, 8, 10]
                    ↑  ↑  ↑  ↑  ↑  ↑
インデックス:        0  1  2  3  4  5

' [1 ~ 3]  →  インデックス 1, 2, 3 の要素を取る

結果: [2, 4, 6]
```

イテレーションの記述とスライスの記述が**同一の構文**で統一される。

## 3. レンジ式を用いたループ

### 3.1 ラムダへの適用

レンジ式は高階関数として `$[...]` ブロック（ラムダ）を受け取る。

```sign
[0 ~+ 2 ~ 10] $[
	i ?
		` i を使う処理
]
```

- `[0 ~+ 2 ~ 10]` → イテレータを生成する関数に見えるが、forの記述と相違ない。
- `$[ i ? ]` → `i` を引数に取る無名関数に見えるだけで、実態は単なるforの実行ブロック
- 並置（関数適用）= ループ

実体は結果を返す**for文**である。

### 3.2 コンパイル後の形式

コンパイラはこの構造をタイトなアセンブリループに変換する。
`$[...]` のプロローグ/エピローグはインライン展開前提の呼び出し規約に従い、
関数呼び出しのオーバーヘッドはゼロになる。

```asm
; [0 ~+ 2 ~ 10] $[ i ? ... ]
    mov  rax, 0       ; i = 0（開始値）
.loop:
    ; ... $[...] の本体（インライン展開）...
    add  rax, 2       ; ステップ
    cmp  rax, 10
    jle  .loop
```

### 3.3 無限ループとカウンタ

開端レンジ `[0 ~+ 1]` を関数の引数として使うことで、再帰の表現が関数の再帰ではなく単なるループにしたループカウンタを表現できる。

```sign
f :
		c : [0 ~+ 1]
	?
		` c を使った処理
```

このパターンは：
- 構文上は再帰に見えない
- コンパイラが `c : [1 ~]` を認識した時点で「ループカウンタ」と判断
- 実際には `inc rax` + `jmp .loop` のタイトなループになる

**再帰という概念を使わずに、純粋なループを記述できる。**

## 4. 部分適用のABI

### 4.1 設計方針

Sign の関数適用は**適用の完全性**によって2つのパターンに分かれる。
コンパイラは静的アリティから完全適用か部分適用かを確定し、最適なコードを生成する。

```
完全適用（引数が揃う）  → レジスタ渡し（alloca 不要）
部分適用（引数が足りない）→ コンパイル時の特殊化（実行時の構造体は無い）
```

どちらの場合も**ヒープ確保は発生しない**。関数ポインタ＋捕まえた値の連続ブロック（§4.3）が
実行時に要るのは、**関数を返す関数**が関数オブジェクトの番地を返すときだけである。

### 4.2 完全適用：レジスタ渡し

アリティが静的に確定しており、すべての引数が揃っている場合、
直接レジスタに引数を積んで関数を呼び出す。

```sign
` ← 静的に完全適用が確定
add 3 5
```

```asm
// コンパイラが生成するコード（AArch64）
mov x0, #3    // 第1引数
mov x1, #5    // 第2引数
bl  add
```

alloca は一切不要。C の通常の関数呼び出しと同等コスト。

**レジスタの割り当ては AAPCS64 に従う。**

| 用途 | レジスタ |
|---|---|
| 整数・アドレス引数（第1〜8） | `x0`〜`x7` |
| 浮動小数・ベクタ引数（第1〜8） | `d0`〜`d7` / `v0`〜`v7` |
| 返値 | `x0`（浮動小数は `d0`） |
| 一時（呼び出しで壊れてよい） | `x9`〜`x15` |
| 呼び出し先が保存する | `x19`〜`x28` |
| フレームポインタ / リンクレジスタ | `x29` / `x30` |

参照渡しの集約（§4.6）は `{ptr}` なら1本、`{ptr, len}` なら**2本**を占める
——`len` も渡すものだからである。したがって8本という上限は「引数の個数」ではなく
**レジスタの本数**で数える。

> [!NOTE]
> 以前ここは x86-64 System V の記法（`rdi`/`rsi`/`call`）で書かれていた。Sign が
> 当面 AArch64 だけを対象にすることは [`0_design_principles.md`](../0_design_principles.md)
> が定めており、例だけが別のターゲットのままだった。§4.4 の連続ブロックの説明にも
> 同じ記法が残っている。

### 4.3 関数オブジェクト：fn ptr + contiguous struct

呼び出しサイトや束縛で引数が足りない部分適用（`add3 : add 3`、`(add3 1) 2 3`）は、
**コンパイル時に特殊化した関数**になる（[execution_model.md](../core/execution_model.md) §3）
——`add3(b) { return add(3, b); }` を静的に作るだけで、実行時の構造体は無い。

実行時に**関数ポインタ＋捕まえた値の連続ブロック**（関数オブジェクト）が要るのは、関数を返す関数が
関数オブジェクトの番地を返すときだけである（[type_system.md](../type/type_system.md) §3.5）。捕まえる値が
実行時に決まるので、コンパイル時には特殊化しきれない。これは Unix カーネルの慣用パターンと同一の
構造である。

```sign
add : a b ? a + b
adder : n ? $(add n)     ` 関数を返す関数は、関数オブジェクトの番地を返す
@(adder 3) 5             ` @ で引き戻して当てる → 8
```

```c
// 関数オブジェクト（概念）。置き場は呼ぶ側が用意する（下の NOTE）
struct { void* fn; int captured_a; } *obj = /* 呼ぶ側の置き場 */;
obj->fn = &add;
obj->captured_a = n;
return obj;              // 番地を返す

// 使う側：@ で引き戻して当てる
((add_fn_t)obj->fn)(obj->captured_a, 5);
```

**Unix カーネルとの対応：**

```c
// Linuxカーネル VFS - これも部分適用の表現
struct file_operations {
    ssize_t (*read)(struct file *f, char __user *buf, size_t len);
    //               ↑ struct file *f = キャプチャ済み引数（コンテキスト）
};
```

`struct file *f` は「キャプチャされたコンテキスト」であり、
関数ポインタと合わせてクロージャを形成している。Sign の関数オブジェクトは同じ構造。

> [!NOTE]
> **エスケープ問題は Sign 実行モデルで解決済み**
> Sign では全関数が `main` の内部関数として静的に展開されるため、
> 部分適用が生成元のスタックフレームを超えて生きることが設計上ない。
> 詳細は [core/execution_model.md](../core/execution_model.md) を参照。
>
> **関数を返す関数だけはフレームを超える。** その場合は関数オブジェクトの番地で返し
> （[type_system.md](../type/type_system.md) §3.5「関数を返す関数は、関数オブジェクトの番地で返す」）、
> このブロックの置き場は**呼ぶ側が用意する**——器を返すのと同じ規約である。生成元のフレームには
> 置かないので、戻っても死なない。`$` を付けずに関数を返す本体は、コンパイル時に名指しして止める。

### 4.4 引数順序の保証

連続ブロック内のフィールド順は**コンビネータの規約に従い静的に保証**される。

```
closure { fn: $f, a: val_a, b: val_b }
呼び出し時: fn(a, b, ...) → a→rdi, b→rsi, ...（System V ABI）
```

Sコンビネータ等の変換においても、フィールド順が決定論的であるため
引数順序の整合性が保たれる。

### 4.5 静的アリティの前提

このABIが成立するのは：

- 関数のアリティ（引数の数）が**コンパイル時に確定している**こと
- クロージャ構造体のサイズが**静的に計算可能**であること

のいずれも静的設計原則から保証される。


### 4.6 集約値の引数渡し：参照で渡すのは「メモリに置かれているもの」だけ

§4.2 が定めるレジスタ渡しはスカラーの話である。集約値（`String` / `List` / `Struct` /
`Iterator`）をどう渡すかは、その値が**メモリを占めているかどうか**で決まる。

| 実体 | 渡し方 | 渡るもの | AArch64 |
|---|---|---|---|
| スカラー | 値渡し | 値そのもの | レジスタ1本（§4.2） |
| **規則**（レンジ・`Iterator`） | 値渡し | `{start, step, end}` | レジスタ2〜3本 |
| **入力**（`Reader`） | 値渡し | **番地そのもの**（即値） | レジスタ1本 |
| **要素の並び**（`String` / `List` / `Struct`） | **参照渡し** | `{ptr}` または `{ptr, len}` | レジスタ1〜2本 |

規則は**メモリ上に無い**（[`type_system.md` §2](../type/type_system.md) のアクセス表）。
置かれているのは `{start, step, end}` という固定サイズの構造体だけであり、指す先が無い
ものに参照は作れない。§5 のまとめが `c : [0 ~+ 1]` を「ゼロ（レジスタのみ）」と書いて
いるのはこのことである。

入力も**メモリ上に無い**。規則が `{start, step, end}` の3つを持つのに対し、入力の状態は
**番地だけ**である——頭は番地から読み、尾は同じ番地（進むのは機器の側）。だから番地1語で
足り、器を作らない。`#` が成功時に番地を返す（Input の双対）のと対になる形であり、
[`type_system.md` §3.5](../type/type_system.md) の「`@` の相方は2つしかない」を参照。

要素の並びは逆に、常にメモリを占める。そして **`List(T)` は要素数を型に持たない**
——要素数は定義した場所にしか無いので、呼び出しごとに違う長さが渡る関数側では型から
復元できない。値渡しにすると「同じ型なのに呼び出しごとに渡し方が違う」ことになるため、
参照で渡す。**渡し方が型だけで決まる**という性質はここで保たれる。

参照が何を運ぶかは既に決まっている（`type_system.md` §2「参照が運ぶのは、型が語らない
ものだけである」）。

* `Struct`（形が型にある）→ `{ptr}`
* `List(T)` ・ `String`（要素数が型に無い）→ `{ptr, len}`

§7.5 のスライスが `result_ptr` と `result_len` の2つで済むと書いているのは、この規約を
スライスの側から述べたものである。コピーは発生しない。

> [!NOTE]
> **これは意味論の話ではなく機械の話である。** [原理3](../0_design_principles.md) が
> 「参照渡しは危険な明示的opt-in」と呼んでいるのは**同時アクセスの可否**——複数の位置を
> 同時に生きた状態で保持できるかどうか——であって、値がレジスタで運ばれるかアドレスで
> 運ばれるかではない。`f : [x ~xs] ?` が `Implicit` を、`f : x ~xs ?` が `Iterator` を
> 受けるという区別は、この規約の上でもそのまま成立する。
>
> **静的に大きさが決まる集約を値で渡す（AAPCS 風の）規約も採りうる。** その場合
> 「何バイトまでレジスタに載せるか」の閾値を決める必要があり、`List(T)` は型に要素数が
> 無いので結局参照へ落ちる。まず全面的に参照で揃えておき、必要になった型から値渡しへ
> 上げる——`Iterator` が既にそうなっているように——のが拡張の順序として自然である。


> [!NOTE]
> **`__` の置き方も幅で決まる。** レジスタ1本の値なら上位ビットの niche
> （[`value_representation.md`](../core/value_representation.md) §3.5）だが、`{ptr, len}` で
> 運ぶ値では **`len = 0`** である——空文字列・空リストが `__` そのものだからである
> （`__ = []`、[`unit.md`](../core/unit.md)）。零対象は一つしかないので、器の側にも元から
> `__` の置き場所がある。新しい表現を足したのではない。


### 4.7 器を返す：場所は呼ぶ側が用意する（x8 と x15）

呼ばれた側は器を自分のフレームに置いて返せない——エピローグがその場所を捨てるからで
ある。だから**場所は呼ぶ側が用意し、呼ばれた側がそこへ書く**。AArch64 の間接結果レジスタ
x8 を使うのは AAPCS64 §6.9 と同じだが、Sign はもう1本を対にする。

| レジスタ | 運ぶもの | 誰が決めるか |
|---|---|---|
| **x8** | 返値スロットの先頭アドレス | 呼ぶ側 |
| **x15** | そこに**入る要素の個数**（残り） | 呼ぶ側 |

**場所は最も外側で一度だけ取る。** 自分がもらったスロットをそのまま下へ渡せるなら渡す
——途中で取り直すと、返ってきた器が畳んだフレームを指す。

#### なぜ個数まで渡すのか

大きさは静的には決まらない。決まるのは**上界**であり、`konst + Σ coefᵢ×‖pᵢ‖ + Σ coefⱼ×μ‖pⱼ‖`
という式で、実引数の器の長さから実行時に計算する。呼ぶ側はこの式で `sub sp` する。

以前は、呼ばれた側が**同じ式を自分の仮引数から計算し直す**設計だった。ABI を増やさずに
済み、両側が同じ法則に従っていることが正しさになる——そう考えていた。

これが崩れるのが**追記**である。`(s ' 0) (g s (i - 1))` は器の**続き**を書くので、段が
下がるたびに宛先だけが進む。ところが仮引数 `s` は同じままなので、計算し直した式は毎段
「まるごとの容量」を答えてしまう。照合は素通りし、**上界3に対して41要素書いて踏み抜いた**。

> **どこで割れているかは呼ぶ側の情報である。** ジッパーの焦点を呼ぶ側が選ぶのと同じ形で、
> 器を割ったのは呼ぶ側なのだから、割れ目を知っているのも呼ぶ側しかいない。ここだけは
> 渡すしかない。そして渡ってくるなら、呼ばれた側が計算し直す理由も無い——**決めるのは
> 1箇所**である。

#### 外れたときに何が起きるか

上界は**証明ではなく見積もり**である。証明を要求すると、添字で回る再帰（`f ts i (j - 2)`）
が丸ごと出せないままになる。だから見積もりで通し、**外れても壊れないこと**を代わりの
条件にする。

書く直前に位置を x15 と比べ、越えるなら器は作れない——**作れなかったものは無い**ので
`__` を返す（[完全性公理](../core/unit.md)）。数学では無限はありふれているので、**解が
無いことにも答えを持っていなければならない**。

#### 末尾呼び出しでは渡し直す

x8 も x15 も caller-saved なので、間に `bl` が1つでもあればレジスタの中身は残骸である。
フレームを畳んで飛ぶ前に、退避したスロットから両方を戻す。自己末尾再帰も同じで、飛び先
（`.Lloop`）は仮引数を写す前なので、入口と同じ姿でなければならない。


## 5. まとめ

| 機能 | Cの相当物 | Signの表現 | コスト |
|------|-----------|-----------|--------|
| for ループ | `for(int i=0; i<=5; i++)` | `i : [1 ~ 5]` | ゼロ（インライン展開） |
| ストライドアクセス | `for(int i=0; i<=10; i+=2)` | `[0 ~+ 2 ~ 10]` | ゼロ（SIMD対象） |
| 無限ループカウンタ | `int c=0; while(1){c++;}` | `c : [0 ~+ 1]` | ゼロ（レジスタのみ） |
| スライス | `arr[1], arr[2], arr[3]` | `arr ' [1 ~ 3]` | インデックス走査のみ |
| 完全適用の関数呼び出し | `func(a, b, c)` | `f a b c`（静的に確定） | レジスタ渡し（alloca不要） |
| 部分適用 | `add3(b){ return add(3, b); }` を手で書く | `add3 : add 3`（コンパイル時の特殊化） | ゼロ |
| 関数を返す関数 | `malloc(sizeof(closure))` | `$(…)` で関数オブジェクトの番地を返す（置き場は呼ぶ側） | スタックのみ |


Signの設計は「高レベルな構文に見えるが、コンパイル後はCと同等のコスト」を目指す。
構文と実装コストを切り離し、ABIの規約と静的解析によってゼロコストを実現する。

## 6. alloca の2用途：クロージャ構造体 vs 連続ブロック

`alloca` によるスタック確保は、Sign内で**2つの異なる目的**に使われる。
混同しないよう、用途を明確に区別する。

### 6.1 関数オブジェクト（関数を返す関数専用）

関数を返す関数が、関数オブジェクトの番地を返す場合に使用。§4.3 で説明した通り。
呼び出しサイトや束縛の部分適用（`add3 : add 3`）はコンパイル時の特殊化なので、ここには来ない。

```
用途: adder : n ? $(add n) が返す関数オブジェクト
構造: { fn: $add, captured_a: n }（連続ブロック）
確保: 呼ぶ側が用意した置き場（器を返すのと同じ規約）
特性: ランダムアクセス O(1)、コンテキスト渡しが容易
```

**Unixカーネルの慣用パターンと同じ構造**：
Linuxの `file_operations` 等の「関数ポインタ＋コンテキスト構造体」のこと。

### 6.2 連続ブロック（Array / Vector 専用）

`List` / `Vector` 型の実体として使用。要素がメモリ上で連続している必要がある。

```
用途: [1 2 3 4 5] のような配列データ
構造: 要素が連続したメモリブロック
確保: alloca(sizeof(elem) × n)
特性: ランダムアクセス O(1)、SIMDロード可能、キャッシュ局所性が高い
```

```c
// Sign コンパイラが生成するコード（概念）

// 関数を返す関数 → 関数オブジェクト（連続ブロック、置き場は呼ぶ側）
struct { void* fn; int captured_a; } *obj = /* 呼ぶ側の置き場 */;
obj->fn = &add;
obj->captured_a = n;

// List [1 2 3 4 5] → 連続ブロック
int* arr = alloca(sizeof(int) * 5);        // 連続メモリ
arr[0] = 1; arr[1] = 2; /* ... */
```

### 6.3 使い分けの判断基準

| データの種類 | alloca の用途 | 理由 |
|-------------|--------------|------|
| 完全適用の関数呼び出し | **不要**（レジスタ渡し） | 静的に確定、コストゼロ |
| 部分適用（呼び出しサイト・束縛） | **不要**（コンパイル時の特殊化） | 静的に確定、コストゼロ |
| 関数を返す関数 | **関数オブジェクト** | fn ptr + 捕まえた値の連続ブロック（置き場は呼ぶ側） |
| `List` / `[1 2 3]` | **連続ブロック** | O(1)アクセス、SIMD対象 |
| `Vector` (SIMD型) | **連続ブロック** | SIMDロード命令が連続メモリを要求 |
| レンジ式の一時バッファ | 連続ブロック | stride アクセスのベクトル化に必要 |
| DMA・ハードウェアバッファ | 連続ブロック | ハードウェアが連続アドレスを要求 |

### 6.4 レンジ式とベクトル化の前提

レンジ式 `[0 ~+ 2 ~ 10]` に `layer: 3` 以上で SIMD 最適化を適用するには、
実体が連続ブロックであることが前提：

```sign
` layer: 3 以上
` [0 ~+ 2 ~ 10] の実体が連続ブロックなら、コンパイラは SIMD gather/scatter を生成できる
` → SIMD gather 命令に変換可能
[0 ~+ 2 ~ 10] ' [1 ~ 3]
```


## 7. 構造体と多次元配列の alloca 表現

### 7.1 構造体（Struct）

`Struct`（`[key : val]` 記法）の実体は、フィールドが**固定オフセットで並ぶ連続ブロック**である。
コンパイラはフィールドの型・サイズ・アライメントを静的に決定し、単一の `alloca` で確保する。

> [!IMPORTANT]
> **フィールドの物理オフセットは、宣言順ではなくフィールド名でソートした正規順で割り当てる。**
>
> `==`（構造比較）はHom集合の一致——フィールド名の集合が一致すれば真であり、宣言順序を
> 一切問わない（[`type_system.md`](../type/type_system.md#62-コンストラクタ関数と--の意味論)
> §6.2）。物理レイアウトが宣言順そのままに依存してしまうと、`[x:1, y:2]` と `[y:2, x:1]`
> のように「型としては`==`で真＝同じ」であるはずの2つの構造体が、オフセット配置は異なる
> （`x`が0番目か4番目か）という食い違いを起こしうる。フィールド名でソートして正規化する
> ことで、Hom集合が一致する構造体は常に同一の物理レイアウトを持つことが保証される——
> 数学的な同値性（同型性）と物理的なメモリ配置が食い違わない。

> [!CAUTION]
> **この正規化は名前を持つスロットにのみ適用される。連番スロットには適用されない。**
>
> 上の規則はソートの鍵としてフィールド名を要求する。連番スロット（`1 , 2 , 3`）には
> 名前が無いため鍵が存在せず、**宣言順が唯一の順序であり、そのまま物理配置になる**。
>
> したがって**「N番目のスロットは offset N×幅にある」という確約が得られるのは連番
> スロットだけである。** ハードウェアが配置を決める場面（MMIO のレジスタマップ）、
> 外部と取り決めた配置（FFI 境界、シリアライズ済みデータ）は、必ず連番スロットで書く。
>
> 名前付きスロットに対する `' <連番>` は**宣言順のN番目**を指すのであって、物理位置では
> ない（[`type_system.md` §2](../type/type_system.md)）。両者は宣言順がたまたま正規順と
> 一致するときにだけ揃う。名前付きスロットで `uart ' 2` と書いても「offset 8」の意味には
> ならない——3番目に**宣言した**フィールドが返る。
>
> 名前付きスロットに位置の確約が無いことは欠落ではない。そちらはスロットを**名前で同定
> する**ものであり、位置を約束する必要がそもそも無いからこそ、コンパイラが正規化してよい。

### 7.2 アラインメント：自然境界

各スロットは**自分の幅の境界**に置く。構造体全体の境界は最大スロットの境界であり、
全体の大きさはその境界へ切り上げる。

```
` charset : ascii（Char = 1 byte）のとき
m : [
	a : `x`      ` String  1 byte  → offset 0
	b : 1        ` Int     8 byte  → offset 8（1 の直後ではなく境界まで送る）
]
` 全体: size 16 / align 8
```

根拠はハードウェアにある。

- **Device メモリ（MMIO、`Device-nGnRnE`）は境界を跨いだアクセスでフォールトする。**
  連番スロットは MMIO を書くための形なので（§7.1 の CAUTION）、詰めると動かない
- `ldp`/`stp`（ペア転送）は境界を要求する
- Normal メモリでも境界跨ぎは遅い

全体の大きさを境界へ切り上げるのは、`List(Struct)` の各要素が同じ境界に載るためである
——ストライドが揃わないと `base + i × size` が壊れる。

> [!IMPORTANT]
> **詰め込み効率のための並べ替えはしない。**
>
> 名前付きスロットの並びは名前ソートの正規順が決める（§7.1）。パディングを減らすために
> 順序を変えると、**`==` で等しい構造体が同じ物理配置を持つ**という §7.1 の保証が壊れる。
> 並びを決めるのは名前であって、コンパイラの裁量ではない。
>
> 連番スロットも同様に宣言順が物理配置であり、こちらは外部との取り決めそのものなので
> 動かす余地が無い。**Sign にレイアウト最適化は存在しない**——配置は常に宣言から決まる。


```sign
` 2スロットの構造体のコンパイル後のイメージ（概念）
` 構造体は1エントリでもブロックで書く——1行に並べる綴りは止まる（match_case.md §概要）
point : [
	x : 3
	y : 4
]
```

```c
// コンパイラが生成するコード（概念）
struct { int x; int y; } *point = alloca(sizeof(*point));
point->x = 3;
point->y = 4;
// スコープを抜けると自動回収（free不要）
```

**フィールドのlayer制約**：フィールドの型にも layer 制約が適用される。
`Float` フィールドを持つ Struct は `layer: 2` 以上でのみ使用可能。

### 7.3 多次元配列

多次元配列は**行優先（row-major）の連続ブロック**として alloca で確保する。

```
2次元 [rows][cols]:
  確保: alloca(sizeof(elem) * rows * cols)
  アクセス: element[i][j] = *(base + i * cols + j)
```

サイズは**コンパイル時に静的に決定**されている必要がある（静的設計原則より）。

### 7.4 `'` の連鎖による多次元スライス

多次元配列へのアクセスは、`'`（get）演算子を**左結合でチェーン**することで表現する。
特別な多次元構文は不要。

```sign
` 3×5行列 matrix の行1〜2、列0〜3 を取り出す
matrix ' [1 ~ 2] ' [0 ~ 3]
```

**評価の順序：**

```
① matrix ' [1 ~ 2]
     → 行1〜2 を取り出す（部分行列へのビュー）
     → ポインタ計算のみ（ゼロコピー）

② (結果) ' [0 ~ 3]
     → 列0〜3 を取り出す
     → さらにポインタ計算のみ
```

**n次元への拡張：**

```sign
` 3次元テンソルのスライス
tensor ' [1 ~ 2] ' [0 ~ 3] ' [2 ~ 4]

` 特定の要素アクセス（スカラー）
` → matrix[2][3] と同等
matrix ' 2 ' 3
```

### 7.5 スライスのゼロコピー性

`'` によるスライスはポインタ計算のみで実現される。コピーは発生しない。

```
matrix ' [1 ~ 2] の実装:
  result_ptr  = base + 1 * num_cols * sizeof(elem)
  result_len  = 2 * num_cols
  ↑ これだけ（メモリコピーなし）
```

`layer: 3` 以上では、スライス後の連続領域に SIMD 命令を直接適用できる：

```sign
` layer: 3 以上
` 行1〜2のデータをSIMDで処理
matrix ' [1 ~ 2] ' [0 ~ 4] $[
	row ?
		` row は連続メモリ → SIMD命令に変換可能
]
```

### 7.6 データ種別と alloca 戦略まとめ（更新版）

| データの種類 | alloca の形式 | アクセス | SIMD対象 |
|-------------|--------------|----------|----------|
| 関数オブジェクト（関数を返す関数） | 連続ブロック（fn ptr + 捕まえた値） | O(1) | ✗ |
| `List` / 1次元配列 | 連続ブロック | O(1) | ✓ |
| `Vector` (SIMD型) | 連続ブロック | O(1) | ✓ |
| `Struct` / `Struct` | 連続ブロック（固定オフセット） | フィールド名→オフセット | △ |
| 多次元配列 | 連続ブロック（row-major） | `'` チェーン | ✓ |
| DMA・ハードウェアバッファ | 連続ブロック | 直接アドレス | ✓ |
