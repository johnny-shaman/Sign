# Sign 設計原理

> [!IMPORTANT]
> 本書は `0_definition.md` よりも前に読むべき文書である。個々の仕様（演算子テーブル、型システム、
> コンパイラパイプライン等）は、ここで宣言する原理の具体例に過ぎない。各仕様ファイルの規則を読んで
>「なぜそうなっているか」が分からない場合は、まずここに戻ること。

Signの設計判断はすべて、以下の8つの原理のいずれか（または複数）の具体例として説明できる。
逆に言えば、新しい言語機能を追加・変更する際は、それがこの8つのどれに当てはまるかを常に
確認すること。当てはまらない場合、その機能はSignの設計哲学から外れている可能性が高い。

---

## 原理1：RISC as-is — 演算子はハードウェア命令に対して素直であれ

Signの演算子テーブルの記号選定は、想定するRISCプロセッサ（最初の実装ターゲットはAArch64・
RISC-V）に対して**as-is**——中間表現で均さずに、演算子の並びがほぼそのままターゲットの命令列に
落ちること——を狙って決まっている。

言語は `asm_volatile` という、バックエンドコードを直接挿入できる逃げ道を持つ。これは
「全ての挙動は最終的にユーザーが挙動ベースで直接記述可能である」ことを前提とした設計であり、
個々の演算子が単一命令に対応するかどうか（`^` 冪乗や `!` 階乗のように単一命令に落ちず
糖衣構文となる場合がある）自体は設計上の障害にならない。最終手段が常に存在するため、
コア演算子と糖衣構文の切り分けは「命令対応」ではなく原理2・原理3から決まる。

### as-is が写すのは命令列だけではない——型もである

> **「ハードウェアには型が無い」という通念は誤りである。**
> ハードウェアに無いのは**値に付いた実行時タグ**であって、型ではない。

| ハードウェアの事実 | それは何の型か |
|---|---|
| GPR と FPU が**物理的に別のレジスタファイル**である | 整数と浮動小数点。`add` と `fadd` は別命令であり、silicon が区別を強制している |
| `fcvtas` / `scvtf` のような**変換専用命令**が存在する | 型変換には命令＝コストが伴う。すなわち変換元と先は別の型である |
| 32bit のデバイスレジスタを 64bit ストアで書くと壊れる | **アクセス幅が型** |
| Device-nGnRnE と Normal で再順序化・キャッシュ・投機の可否が変わる | **メモリ属性が型**。MMU のページテーブルは事実上の型テーブル |
| Cortex-M のベクタ表はアドレスを、AArch64 のそれは命令を保持する | **場所に型がある** |
| ARM の関数ポインタは bit 0（Thumb ビット）に命令セットを載せている | ポインタ自身が型タグを持つ稀な例 |

**操作は型付きであり、記憶域も型付きであり、変換は明示的な命令である。**
無いのは「このレジスタの中身は整数です」と値自身が名乗る仕組みだけである。

すなわちハードウェアは、**実行時タグを持たない静的型システム**そのものである。
これは原理2 が「型は実行時ゼロコストの帳簿」と述べている構造と完全に一致する。

したがって Sign の型システムは、**型の無いハードウェアに型を載せているのではなく、
ハードウェアが既に持っている型を書き写している**。as-is とは、演算子の並びが命令列へ
落ちることだけを指すのではなく、**Layer 2 の型がハードウェアの区別そのものであること**
までを含む。`Address`（GPR幅）・`Float`（FPU幅）・`Vector`（SIMD幅）が「幅クラスごとに
実行時のビット表現はただ1種類」（[`type_system.md` §2](impl/type/type_system.md)）と定められて
いるのは、この写像の直接の帰結である。

> [!NOTE]
> **この見方は余積（coproduct）に対する典型的な批判への回答にもなる。**
>
> 「余積は静的に型が定まらない」という批判は、**判別子（discriminant）が値の中に無ければ
> ならない**という前提に立っている。しかしハードウェアは「レジスタの中身が何であるかは、
> どの命令が触ったかで決まる」という形で、判別子を値の外に置いている。
>
> Sign も同じ手を採る——判別子は帳簿（`.ist`）に置く。
>
> - `__` へ収束した理由は Pass 3b が静的に記録する（[`type_system.md` §5](impl/type/type_system.md)）
> - enum の各バリアントは自動採番により**値そのものが判別子**になる（同 §6.2、C の enum と同格）
> - `__`（零対象）はそもそも吸収するためタグを必要としない
>
> ただし、**同一幅のペイロードを持つ直和を実行時にディスパッチする**場合には、依然として
> タグが要る。Sign はここで安全性を主張せず、C の `union` と同じ「呼び出し元の自己責任」を
> 選ぶ（同 §8）。これは敗北ではなく、**ハードウェアが持つ型システムの限界を、そのまま言語の
> 限界として引き受ける**という原理2の立場の帰結である。

**関連文書**：[`compiler_pipeline.md` §1](impl/core/compiler_pipeline.md#1-設計動機risc-プロセッサに対するas-isコンパイラ)、
[`type_system.md` §2](impl/type/type_system.md)（Layer 2 の幅クラス）

## 原理2：型は建前、本音はRISCの固定長制約

> heapless原則や静的単相型付けは、本音ではなく建前である。本質は「RISCが固定長のレジスタと
> 固定長メモリしか持たない」という素の制約であり、heapless・型安全はその制約を言語仕様として
> 言い換えたものに過ぎない。

この立場から、型システムは次のように位置づけられる。

- 型は **実行時ゼロコストの帳簿**（コンパイル時にのみ存在する一時的な記録）であり、実行時には
  一切残らないし、残す必要もない
- 安全性の保証は最初から放棄する。`Point`/`Vector2D` のようにフィールド形状が一致する構造体
  同士の取り違えを検出することは型システムの責務ではなく、**呼び出し元の自己責任**とする
  （C の union と同じ扱い）

コンパイラの Pass 1〜3（識別子テーブル収集・余積解決・型伝播）は、この「帳簿」を作って
Pass 4（コード生成）に渡すためだけに存在する。Pass 4 は struct 名・enum 名等の意味論的な
型情報を一切引き継がず、固定幅レジスタ操作とジャンプ命令テンプレートの選択だけを行う。

> [!NOTE]
> **「実行時ゼロコストの帳簿」は Sign の発明ではなく、ハードウェアの構造の写しである。**
>
> 原理1 で述べた通り、ハードウェアもまた**実行時タグを持たない静的型システム**である
> ——GPR と FPU は物理的に別のレジスタファイルであり、アクセス幅もメモリ属性も型として
> 振る舞うが、値自身が「私は整数です」と名乗る仕組みは無い。何であるかは、どの命令が
> 触ったかで決まる。
>
> 本原理が「型は実行時に一切残らない」と言い切れるのは、Sign が禁欲的だからではなく、
> **写している対象が最初からそういう構造をしているから**である。

**関連文書**：[`compiler_pipeline.md` §2, §3](impl/core/compiler_pipeline.md#2-型システムの立ち位置建前としてのheapless本音としてのrisc固定長制約)、
[`type_system.md`](impl/type/type_system.md)

## 原理3：危険はデフォルトでは書けない、明示的なopt-inでしか書けない

Signの各所に、同じ形のパターンが繰り返し現れる——**安全な既定の書き方があり、危険なことをしたい
場合だけ、別の・より明示的な構文に踏み込む必要がある**、というパターンである。

| 領域 | 安全な既定 | 危険な明示的opt-in |
|---|---|---|
| コード生成全体 | 通常のコンパイル | `asm_volatile`（直接アセンブリ挿入） |
| コンストラクタ由来の確認 | 型による静的な帳簿 | `' !__`（明示的な由来確認） |
| rest引数（list） | 裸の `~xs`（stream、pull型で同時アクセス不可能） | `[x ~xs]`（参照渡し、複数アドレスへの同時アクセスが可能） |
| 仮引数リストのIO | `@address` を規定値にする読み出し（1回きり、副作用の型が見える） | 仮引数部での `#`（Output）は**禁止** |
| 関数本体のIO | — | `@`（Input）・`#`（Output）・`$`（アドレス取得）はIO取り放題。ただし数式に出てこない異質な記号を割り当てることで、「ここは計算ではなく実世界に触れている」ことを視覚的に警告し続ける |

この表からも分かる通り、**危険であること自体を否定する原理ではない**。Signは危険な操作
（生ポインタ経由の同時アクセス、生アセンブリ挿入、任意のIO）をすべて許容する。ただし、
それらは常に「安全な既定から一歩踏み出した」という事実がコード上に可視化される形でしか
書けないようにする。

具体例：`[foo bar ~struct]` のようなブラケット形rest記法は、以前「暗黙性が成功方向に開いて
おり危険」として却下したStoreパターンに似た機能を実現するが、仮引数部での `#` 禁止という
別の原理3の適用により、**明示的な参照渡しの形でしか存在できない**ように文法で狭められている。
暗黙のStoreパターンそのものは依然として存在しない。

> [!NOTE]
> **検討して却下（2026-07-30）**：`?` の左辺（仮引数部）を Scala の for-yield のような
> モナディックジェネレータとみなし、`:` が右辺の中身次第で pure let束縛 / monadic bind の
> 両方を兼ねるとして、仮引数部での `#` を許可する案を検討したが、却下した。
> C++ のデフォルト引数（呼び出しサイトごとに再評価され、`get_next_id()` のような副作用付き
> 関数呼び出しをデフォルト値にそのまま書けてしまう）と同型の問題を再導入するだけであり、
> 「定数に見えるのに実は毎回IOが飛ぶ」という見た目と挙動の乖離は、原理3が禁じている
> 「危険が既定の書き方に紛れ込む」パターンそのものだったため。

**関連文書**：`impl/syntax/` 配下のrest引数仕様（要文書化）、[`operator_table.md`](guide/operator_table.md)

## 原理4：静的に決定可能な違反は、自己責任に丸投げせず弾く

原理2は「型は建前、安全性は自己責任」と述べるが、これは無制限の放任ではない。
**コンパイル時に確実に判定できる違反は、実行時の自己責任に委ねずコンパイルエラーにする。**
自己責任の範囲は、あくまで静的に決定不可能な領域（実行時の値次第で変わる話）に限られる。

> [!IMPORTANT]
> **「型が合わない」は違反ではない。停止させるのは構文が壊れているときだけである。**
>
> ある演算が与えられた型に対して意味を持たないことは、圏で言えば「その対象間に射が無い」
> ということである。しかし `__` は零対象であり、零対象を経由する射 `A → __ → B`（零射）は
> **常に存在する**。したがって型が合わない演算の結果は `__` であって、停止理由ではない。
> これは §3.2 が String + 算術を `__` へ収束させているのと同じ規則であり、例外ではない。
>
> 一方、**構文が壊れている場合はそもそもプログラムが存在しない**。評価すべき射が無いのでは
> なく、射を書けていない。ここだけは停止させる（`SyntaxError`）。
>
> 本原理が挙げる静的拒否ルールは、いずれも「型の不一致」ではない。
>
> | 区分 | 例 | 扱い |
> |---|---|---|
> | 構文が壊れている | 縮約しきれない式、連鎖比較の混在、receiver の後置 `~` | **停止**（`SyntaxError`） |
> | ターゲットに存在しない | `layer` 未満での浮動小数点・SIMD リテラル | **停止**（命令を出せない） |
> | 効果が起きるか不定 | 仮引数部での `#`（Output） | **停止**（下記3を参照） |
> | 表現の取り違え | `[...]` 内での stream 型識別子 | **停止**（下記2を参照） |
> | 型が合わない | `` `abc` + 1 ``、範囲の端点が List、番地の `*`（番地の域に射が無い） | **`__` へ収束**＋Pass 3b の診断 |
>
> 「`__` へ収束」を黙って行うと silently-wrong になるため、静的に判定できた分は
> [`type_system.md` §5 Pass 3b](type/type_system.md) が**なぜ潰れたか**を機械可読な
> `reason` として記録する。値は一様に `__` へ潰れるが、帳簿には理由が残る。

現時点で判明している静的拒否ルール：

現時点で判明している静的拒否ルール：

1. `layer` 未満のコードでの浮動小数点・SIMDリテラル使用（ターゲットが対応しないハードウェア
   機能を静的に検出）
2. `[...]`（ブラケットrest記法）内でのstream型識別子の使用（原理3のstream/参照渡しの区別を
   静的に強制）
3. 仮引数部での `#`（Output）の使用（原理3のStore安全化を静的に強制）
   - 仮引数部のデフォルト式は、その引数が省略されたときにだけ評価される。ここに Store を
     書くと、**書き込みが起きるか否かが呼び出し側の引数の個数で決まる**——呼び出し側から
     見えない制御フローになるため、原理3の「危険は明示的なオプトインでのみ」に反する。
     Input（前置 `@`）は状態の初期化にあたるため対象外であり、Store のみを拒否する
     （[`function_guide.md`](../guide/function_guide.md) 「仮引数リストは関数の状態ベクタである」）

これらはいずれも「型という帳簿（原理2）」がPass 1〜3の時点で既に確定している情報から
機械的に判定できるため、実行時チェックのコストを一切かけずに拒否できる。

## 原理5：完全性公理は速度と安全の両方に効く

完全性公理 `f __ = __`（Unitが渡された関数は、本体を実行せず即座にUnitを返す）は、
単独では小さな規則に見えるが、少なくとも2つの異なる目的を同時に達成する。

- **速度**：関数呼び出し自体（プロローグ・エピローグ・`call`/`ret`）を丸ごとスキップできる。
  特にAArch64/RISC-Vのような潤沢なレジスタを持つRISCアーキテクチャでは、呼び出し元での
  事前判定によってフルの呼び出しシーケンスを回避できるため、非末尾再帰やインライン化・TCOが
  効かないケースで有効
- **安全**：`$__ # expr`（`__` の上書きによる言語破壊）のような致命的なパターンが、
  実行経路として決して踏まれないことを保証する。例えば `update : [x ~xs] ? $x # x * 2 update xs`
  のような再帰的なlist書き込み関数は、末端で `update xs`（`xs = __`）が呼ばれた時点で
  完全性公理により即座に収束し、その回の呼び出しは本体（`$x # ...`）に一歩も入らない。
  実際に危険な形が構文上は存在していても、実行経路としては絶対に踏まれない

1つの単純な公理から、パフォーマンス最適化と安全性保証の両方が同時に導かれる、という点で
Signの設計における最も筋の良い原理の一つである。

## 原理6：積も和も、構造的等価性から自然に生える

> **挙動が型であって、型が挙動を完全に邪魔することはない。**
> 型システムは安全なコード生成の助けにはなるが、挙動を縛る主体ではない——この非対称性こそが
> 本原理、ひいてはSignの型システム全体を貫く一文である。

> 同型性を確認する専用の演算子は不要である——同じ関数（メソッド）が複数の値に対して
> 成功裏に呼べること自体が、それらがHom集合を共有する（同型である）ことの直接の証拠になる。
> 実務上必要なのは`==`（同値性）だけであり、同型性はチェック対象ではなく、
> 型チェックを通過し実行が成功したことの副産物として自然に得られる。

この立場から、代数的データ型の2本柱（積・和）はどちらも専用のプリミティブとして
個別に設計する必要が無く、「構造的な型づけ＋`==`のHom集合意味論」という単一の土壌から
自然に導かれる。

- **積（struct/Struct）**：`[x:1, y:2]`という並置がそのまま積。フィールド名の集合が
  Hom集合を決める（[`type_system.md`](impl/type/type_system.md#62-コンストラクタ関数と--の意味論) §6.2）
- **和（enum/直和型）**：「共通の操作集合に応答する値たち」は、その応答の有無だけで
  自然にクラス分けされる——専用構文を新設せずとも、この暗黙の直和構造は既に成立している。
  既存の明示的なenum構文（`#RGB : Red | Green | Blue`）は、この一般現象のうち
  「値そのものに意味を持たせず、タグとしての区別だけが要る」場合への、ゼロコストな
  糖衣として位置づけられる

Signがtrait/interface宣言構文を持たない（[`type_system.md`](impl/type/type_system.md#1-設計原則型は演算子と構文から自明に決まる) §1）ことと、直和型の専用構文が
enumの糖衣以外に存在しないことは、同じ根から来ている：**型はコードが実際に行った操作の
反映（影）である**という§1の原則が、積・和という型システムの両輪にまで一貫して及んでいる、
ということである。

なお本原理が答えるのは「**一段の中に何が並ぶか**」であり、「**何段まで積めるか**」は
答えていない。後者は要素の型が終端かどうかで決まる別の問いであり、原理7が扱う。

**関連文書**：[`type_system.md`](impl/type/type_system.md) §1・§6.2

## 原理7：入れ子にできるかは、要素の型が終端かどうかで決まる

> **`String ≅ List(Char)` は正しい。しかし `List ≠ List(Char)` である。**
> 差は連接の代数にはない——どちらも自由モノイドであり、結合的で、単位元（`__`）を持つ。
> 差は**要素の型が、その器自身になれるかどうか**にある。

`List(A)` の `A` は開いている。`A` に `List` を置けるので `List ∘ List` に意味があり、
畳む射 `μ : List(List(A)) → List(A)` が**選べる**。適用してもよいし、しなくてもよい。
これが「さらに積める」の中身である。

`String` は `List(Char)` であり、`Char` は終端である——文字の中へは降りられない。
したがって `List(String)` は String としては意味を持たず、`μ` は**強制される**。
文字列に文字列を積むと、要素として残るのではなく連接になる。これが「上には積めない」の
中身である。

つまり両者は同じ `μ` を持っており、違うのは **`μ` が選べるか、強制されるか**だけである。
圏の言葉で言えば `List` はモナドであり、`String` はそのモナドの代数（不動点）である。
別々の構造ではなく、**同じ構造の、深さの違う2点**を見ている。

```
[`ab` `c`]        → `abc`          文字列に文字を積む   → μ が走る
[`a` `bc`]        → `abc`          文字に文字列を積む   → μ が走る
[[1 2] [3 4]]     → [1 2 [3 4]]    リストにリストを積む → μ は走らない
[`ab` , `cd`]     → 長さ2、0番は `ab`  `,` は外側のリストを作る（要素は String のまま）
```

`,` で組んだ外側は `List` であって `String` ではない。**文字列を要素に持つリストは
書ける**——書けないのは「文字列を要素に持つ文字列」だけである。ここを混同すると、
字句解析器が語の列を作れなくなる。

### `η` は Sign では命令を消費しない

`List` のもう一方の射 `η : A → List(A)` は、Sign では `[x] ≅ x`（1要素のリテラルは
要素そのもの）によって**恒等射**になる。したがって持ち上げは0命令である——原理1の
「同型はコストを持たない」がここでも効いている。`$__ = __ = @__` がマシン語の上で
不動点であることの、型の側から見た姿である。

働くのは `μ` だけであり、`μ` は実際に要素を動かすので命令を消費する。
**どちらが無料でどちらが有料かが、構造から決まっている。**

ただし無償なのは**型の上での持ち上げ**であって、表現の上ではない。長さ1の器とスカラーは
同じものだが、レジスタ1本と `{ptr, len}` の2本という別の運び方を持つ——どちらで運ぶかは
決めなければならず、そこは原理8 が扱う。

### コード生成への帰結

返す器の大きさをバイトで出す式が、この一点で2種類に割れる。

| 返すもの | `μ` | 平らか | スロットの大きさ |
| --- | --- | --- | --- |
| `String` | 強制 | 常に平ら | 要素数 × charset 幅（確定する） |
| `List` | 任意 | 入れ子がありうる | 要素数までしか言えない——要素の型を引き直す |

`returnSizeBound` が返すのは**要素数**であってバイト数ではない。要素型が終端なら幅は
即座に決まり、そうでなければもう一段引く必要がある。sret の規約（呼び出し側がスロットを
用意し、呼ばれた側が `#` で書く）において、スロットを何バイト取るかを決めるのが
この判定である。

## 原理8：同型は型では無償、表現では有償

> **`[x] ≅ x` は型の上では無償だが、機械の上では無償ではない。**
> 長さ1の器とスカラーは同じものである。しかし片方はレジスタ1本で運ばれ、もう片方は
> `{ptr, len}` の2本で運ばれる。**同型だから型は迷わない。迷うのはどちらの表現で運ぶか
> である。**

原理7 が「何段まで積めるか」を扱うのに対し、こちらが扱うのは**段0と段1の境目**である。
`C` と `C×C` は別の型ではなく同じものの別の段であり（`bottom : 0` は長さ1のスタック）、
型の側から見れば行き来は自由である。有償なのは表現の側だけで、そこは自由ではない
——1本で受ける入口へ2本を渡すことはできない。

### 決めるのは値であって使い方ではない

同じ書き方が両方の段で成立してしまう。

```
f : n ? n ' 0      f 5          n はスカラー。`5 ' 0` は `5`（長さ1の同型）
f : st ? st ' 0    f bottom     st はスタック。役割は器だが `bottom` はスカラー
```

**この2つは構文が同じである。** 使い方（`' 0` で引く）はどちらでも書けるので、そこから
段を決めることはできない。決められるのは**実引数が何であったか**だけである。

- 全ての呼び出しがスカラーなら、それは本当に長さ1である。1本で運ぶのが正しい
- 器が1つでも混じるなら、器で運ぶ。**狭い方は広い場合を運べないが、広い方は狭い場合を
  長さ1として運べる**——非対称なので、広い方へ寄せるのは情報の破棄ではない
- 使い方から段を決めてはならない。器を要求するスロットへ渡せることは、渡した値が器で
  あることを意味しない（同型で通っているだけである）

使い方が言えるのは「器である」までで、**どの器かは言えない**。そこは族（`Container`）で
書き、呼び出しサイトが実引数を見せた時点で狭める（原理4）。

**段を変えるのは書き方であって、長さではない。** 段を行き来させるのは1要素のリテラル
（`[5]` は `5`）・前置 `~`（持ち上げ）・後置 `~` と添字 `' i`（持ち下げ）だけであり、切り出し
（`' i~`・`' [a ~ b]`）は長さが1でも0でも元の器と同じ型である。端点が同じ範囲（`[3 ~ 3]`）も
長さ1の範囲であって `3` ではない（[`list_model.md`](type/list_model.md) §2.5）。上の「行き来は自由」は
型を合流させるときの話であって、値の段が実行時の長さで変わることではない。

演算は型どおりに決まる。`xs : [10 , 20]` の `(xs ' 1~) + 1` は `List` と `Int` なので `__` である。
一方 `==` は1要素の器とその要素を等しいと見る——スカラーは1要素の器として読めるので、比べる
ときは狭い側を持ち上げればよい。持ち上げは書かずに起きてよく、持ち下げは書かなければ起きない。

### 器だと言いたいなら、仮引数リストで言う

役割が器なら、それは**書ける**。

```
f : st ?    st ' 0     引いてはいるが「器だ」とは言っていない → `List -> _`
f : [~st] ? st ' 0     器を1つ受けると書いてある            → `[st~] -> Int`
```

後者は要素の型まで決まる。分解の形が「これは器で、これがその中身だ」と述べているから
である——型はコードの影であり（§1）、影に写したいものは書いておく必要がある。前者が
要素型まで届かないのは推論の穴ではなく、**そう書いていない**というだけである。

### コード生成への帰結

段が決まらないと**入口と本体で幅が食い違う**。これは実際に何度も踏んだ壊れ方である。

| 段が決まっていないと | 起きること |
| --- | --- |
| 呼ぶ側が1本、受ける側が2本 | `len` の位置に前の呼び出しの残骸が来る |
| 型が値より広い | 返す器の上界が実行時に伸びて、用意したスロットが足りない |
| 型が値より狭い | 器を1本で運ぼうとして `ptr` を値として読む |

どれも「命令は出ているが値が違う」形で出る。型検査を通り、命令列も出て、走らせて初めて
分かる——だから確かめる場所は実機である。

## 原理の適用チェックリスト

新しい言語機能・構文を検討する際は、以下を自問すること。

- [ ] これは想定ハードウェアの命令に素直に対応するか（原理1）。対応しないなら、糖衣構文として
      `asm_volatile` への逃げ道を残しているか
- [ ] 導入しようとしている型は、ハードウェアが既に持っている区別（レジスタファイル・アクセス幅・
      メモリ属性・場所の種別）の写しになっているか（原理1）。ハードウェアに対応物が無い型を
      足そうとしているなら、それは本当に必要か
- [ ] 判別子（どちらの型か）を**値の中**に持たせようとしていないか（原理1・原理2）。
      静的に追えるなら帳簿へ、値そのもので区別できるならそれで足りる
- [ ] 型情報として持たせようとしているものは、実行時に必要な情報か、それともコンパイル時だけの
      帳簿で十分か（原理2）。実行時に持ち越そうとしているなら、それは本当にheaplessと両立するか
- [ ] この機能はデフォルトで危険なことができてしまわないか（原理3）。危険な操作は、安全な既定
      構文とは別の、より明示的な構文でしか書けないようになっているか
- [ ] この機能が禁止しているパターンのうち、コンパイル時に静的に検出できるものはコンパイル
      エラーにしているか（原理4）。それとも安全性を実行時の自己責任に丸投げしていないか
- [ ] 再帰・ループの終端処理は、完全性公理に安全に乗っているか、それとも独自の終端条件を
      別途必要としているか（原理5）
- [ ] 型同士の関係（同型性・積・和）を表現しようとしているなら、それは`==`のHom集合意味論
      から自然に導けないか（原理6）。専用の宣言構文や専用の比較演算子を新設する前に、
      構造的な型づけだけで表現できないか確認したか
- [ ] 新しい器を足そうとしているなら、その要素の型は**終端か、器自身になれるか**（原理7）。
      終端なら畳む射は強制され、そうでなければ選べる——どちらなのかを決めないまま
      レイアウトや返し方を決めていないか
- [ ] 同型（`[x] ≅ x`、`String ≅ List(Char)`）を導入するなら、**どちらの表現で運ぶか**を
      決めたか（原理8）。**命令を消費することは同型の反証ではない**——原理8 の見出しが言う
      とおり同型は「型では無償、表現では有償」であり、`iso` であることは**比較が走ったとき
      だけ**である（利用者の裁定 2026-09-21）。ここにはかつて「0命令で通るか／命令を消費する
      変換を同型と呼んでいないか」と書いてあり、**同じファイルの見出しと別の水準を要求して**
      いた。表現の費用は同型の欠陥ではなく最適化の話である
- [ ] スカラーと器のどちらにもなりうる位置なら、**どちらの表現で運ぶか**を決めたか（原理8）。
      決める根拠は実引数であって使い方ではない——同じ書き方が両方の段で成立する
- [ ] 器を受ける仮引数なら、それを仮引数リストに書いたか（原理8）。`f : st ?` は引いていても
      「器だ」とは言っていない。書けば要素の型まで決まる
