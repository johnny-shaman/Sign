# Sign の末尾呼び出し最適化（TCO）仕様

## 概要

Sign にはループ構文（`for`/`while`）が存在しない。
反復処理は**再帰**と**レンジ式**で表現する。

したがって、再帰がスタックオーバーフローを起こさないことは**言語の基本保証**である。
コンパイラは末尾位置にある呼び出しを `CALL` ではなく `JMP` に変換する（**TCE: Tail Call Elimination**）。

---

## 1. 末尾位置の定義

関数 `f` の本体で、「その呼び出しの結果がそのまま関数の返値になる」位置を**末尾位置**と呼ぶ。

Sign では `?` 演算子の右辺（本体）全体が評価対象であり、
`&`/`|` の各節の**最後に評価される式**が末尾位置になる。

### 末尾位置の例

```sign
` f の呼び出しが末尾位置にある
loop : n acc ?
` ← acc が末尾（再帰でない → TCO不要）
	n = 0 & acc |
` ← loop が末尾位置 → TCO対象
	 loop (n - 1) (acc + n)
```

### 末尾位置でない例

```sign
` 呼び出しの結果をさらに演算に使う → 末尾位置でない
bad : n ?
` ← f n の結果に +1 している → f n は末尾位置でない
	(f n) + 1
```

---

## 2. `&`/`|` チェーンと末尾位置

Sign の条件式 `cond & then | else` は以下のように評価される：

```
cond が Unit でない → then を評価して返す
cond が Unit       → else を評価して返す
```

`then` と `else` の**両方が末尾位置**である。したがって、どちらの節にある再帰呼び出しも TCO 対象になる。

```sign
` &/| の各節が末尾位置
classify : n ?
` neg が末尾（リテラル、TCO不要）
	n < 0  & neg  |
` zero が末尾（リテラル、TCO不要）
	 n = 0 & zero |
` pos が末尾（リテラル、TCO不要）
	 pos
```

```sign
` 再帰呼び出しが各節の末尾にある
collatz : n steps ?
` 基底ケース
	n = 1     & steps            |
` 偶数 → TCO
	 n % 2 = 0 & collatz (n / 2)  (steps + 1) |
` 奇数 → TCO
	             collatz (n * 3 + 1) (steps + 1)
```

各 `|` 節の末尾呼び出しは**すべて独立に TCO 対象**となる。

---

## 3. 相互再帰の TCO

2つ以上の関数が互いに呼び合う**相互再帰**も、呼び出しが末尾位置にあれば TCO 対象。

```sign
` 相互再帰（どちらの呼び出しも末尾位置）
is_even : n ? n = 0 & 1  | is_odd  (n - 1)
is_odd  : n ? n = 0 & __ | is_even (n - 1)
```

```
is_even(1000000):
  → JMP is_odd(999999)     ← CALL ではなく JMP
  → JMP is_even(999998)
  → JMP is_odd(999997)
  → ... （スタック蓄積なし）
  → is_even(0) → 1
```

スタックフレームは常に1枚だけ。スタックオーバーフローは発生しない。

### 3.1 ファイル分割された相互再帰の解決

`is_even` と `is_odd` が**異なる `.sn` ファイル**に分割されている場合でも、
TCO は**暗黙に**動作する。

```
is_even.sn と is_odd.sn をインポートした場合：

Pass 1（プリパス）が
  → is_even : Lambda (arity: 1)
  → is_odd  : Lambda (arity: 1)
をインポートされた全ファイルから事前に収集

TCO 解析は完全な識別子テーブルが確定した後で実行
  → is_even と is_odd は相互に末尾位置での呼び出し
  → 両方が JMP に変換される
```

**未インポートの場合：**
インポートされていない関数は「未定義識別子」として `__`（Unit）に収束する
（`Undefined_Identifiers_and_Unit_ja-jp.md` §1 参照）。
コンパイラは「未定義識別子を末尾位置で呼び出している」場合に警告を出す。
解決策は単純で、該当ファイルをインポートするだけ。特別な前方宣言構文は不要。

---

## 4. コンパイラの変換規則

### 単純末尾再帰

```sign
f : args ? cond & base | f new_args
```

コンパイル後（概念）：

```c
// CALL を JMP に変換
f:
    if (!cond) goto f_with_new_args;  // JMP（スタックフレーム再利用）
    return base;
```

### 複数分岐の末尾再帰

```sign
f : n ?
	cond1 & f a1 |
	 cond2 & f a2 |
	         f a3
```

各分岐がそれぞれ独立に JMP に変換される。

---

## 5. TCO とレンジ式の関係

反復処理の**推奨表現はレンジ式**であり、TCO に依存しない：

```sign
` レンジ式（TCO 不要）
sum : [1 ~ n] $[acc x ? acc + x] 0

` 再帰（TCO が必要）
sum_rec : n acc ? n = 0 & acc | sum_rec (n - 1) (acc + n)
```

レンジ式はコンパイラが直接ループ命令（`LOOP`/`JNZ` 等）に変換するため、
スタックを使わない。再帰より効率的な場合がある。

**ガイドライン**：
- 配列・シーケンスの処理 → レンジ式を優先
- 状態機械・木構造の走査・相互再帰 → 再帰 + TCO

---

## 6. TCO の静的保証

Sign のコンパイラは、末尾位置の再帰呼び出しに対して**必ずTCOを適用する**。
これは最適化ではなく**言語仕様としての保証**である。

- ユーザーが `@tailrec` 等のアノテーションを書く必要はない
- 末尾位置にない再帰はコンパイラが警告を出す（深いスタックが予測される場合）
- 静的アリティと実行モデル（全関数が `main` の内部関数）により、
  TCO の対象を静的に決定できる

---

## 7. 実行モデルとの整合

「全関数が `main` の内部関数」であるため、
関数 `f` から `f`（または他の内部関数）への末尾呼び出しは、
コンパイラが**同一スタックフレームへの JMP** として扱える。

これは C の setjmp/longjmp や Scheme の continuation とは異なり、
スタックを明示的に操作する機構を必要としない。
コンパイラの命令選択（`CALL` → `JMP`）だけで実現できる。

---

## 8. 完全性公理との順序（コード生成の要）

**TCO の飛び先は、完全性公理（`f __ = __`）の検査より前に置かなければならない。**

構造を食い潰す再帰の終端は、ガードではなく完全性公理である
（[`function_guide.md`](../../guide/function_guide.md)「それは完全性公理が終端させて
いるのであって、ガードが効いているのではない」）。したがって検査は**毎回**通る必要が
あり、フレームを使い回す飛び先がその後ろにあると初回しか通らない——命令は出ているのに
止まらない、という診断の出ない壊れ方になる。

AArch64 での並びはこうなる：

```asm
f:
    stp x29, x30, [sp, #-N]!   // フレーム確保（ループの外、1回だけ）
    mov x29, sp
.Lloop:                        // ← 自己末尾再帰の飛び先
    str x0, [x29, #16]         // 仮引数をスロットへ（毎回）
    <引数が __ か検査>          // 完全性公理（毎回）
    b.eq .Lunit
    <本体>
    <新しい引数を x0.. へ>
    b .Lloop                   // 自己末尾再帰：フレームはそのまま
.Lunit:
    <__ を返値レジスタへ>
    ldp x29, x30, [sp], #N
    ret
```

相互末尾呼び出しは自分のフレームがもう死んでいるので、畳んでから飛ぶ：

```asm
    <新しい引数を x0.. へ>
    ldp x29, x30, [sp], #N     // 自分のフレームを畳む
    b g                        // x30 は元の呼び出し元のまま
```

> [!NOTE]
> **累算しながら完全性公理で終端させる形は TCO の外に落ちる。**
>
> ```sign
> walk : s acc ? walk (s ' 1~) (acc + 1) | acc    ` 末尾ではない
> ```
>
> §2 が末尾位置と定めるのは `then` と `else` であって `cond` ではない。この形は再帰
> 呼び出しを `|` の左（`cond` 位置）に置いており、結果が `__` かどうかを見てから飛び先を
> 決めるので、評価しきる必要がある——スタックが積まれる。
>
> 完全性公理が終端させるのは**構造を食い潰す再帰**であり、そちらは結果を組み立てるので
> そもそも末尾ではない（`(s ' 0) (take_while p (s ' 1~))`）。TCO が受け持つのは累算・
> 状態機械の再帰であり、そちらは `cond & base | f new_args` と書く。普段は住み分けて
> いるが、**両方を一度に欲しくなったときだけ**この穴に落ちる。

## 9. alloca クロージャと TCO の安全保証（実験的考察）

### 9.1 問題の所在

部分適用クロージャは `alloca` 上に `{ fn_ptr, captured_args }` として存在する（→ [Range_Expression_and_Stack_ABI](../memory/Range_Expression_and_Stack_ABI_ja-jp.md) §4.3）。
TCO で `f` から `g` へ `JMP` するとき、`f` 内の `alloca` 領域が上書きされる可能性がある。

### 9.2 main アリーナ方式（有望な解決策候補）

**核心的な洞察**: TCO 対象コードでは再帰の深さが O(1) に収束するため、
必要な alloca サイズも**静的に確定できる**。

```
通常の再帰（TCO なし）:
  f(n) → f(n-1) → f(n-2) → ...   ← スタック深さ O(n) → alloca 総量が静的に不定

TCO 対象の末尾再帰:
  f(n) → JMP f(n-1)               ← スタック深さ O(1) に収束
  alloca の有効フレームは常に 1 枚    → 総量 = 1 フレーム分のみ→静的に確定できる
```

**main アリーナとの整合**:

```c
// コンパイラが生成する概念コード
int main() {
    // 静的解析: TCO 対象の呼び出しグラフ内で
    // 各関数のクロージャ構造体サイズの最大値を計算
    char __sign_arena[MAX_CLOSURE_SIZE_IN_TCO_CALL_GRAPH];
    
    // JMP しても __sign_arena は main が生きている限り存在
    // → alloca クロージャの安全性が保証される
}
```

### 9.3 実験で確認すべき点

1. **相互再帰**（`is_even` ↔ `is_odd`）において、
   各関数の alloca サイズが静的に決定できるか

2. **TCO JMP がアリーナの同一領域を再利用**（上書き）しても問題ないか  
   （次の JMP 先が必要とする前に前の値を参照しないことの保証）

3. 非 TCO の通常 `CALL` と混在する場合のアリーナ分離戦略

> [!NOTE]
> この考察は実験的な提案であり、検証中である。
> 実装で問題が山積みされた場合はプラン B（TCO 対象を自己再帰のみに限定）への移行も検討する。
