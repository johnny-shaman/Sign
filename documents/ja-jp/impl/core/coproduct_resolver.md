# コプロダクト・リゾルバー（余積解決器）仕様

本仕様書は、構文解析直後の段階において、スペース ` ` で区切られたフラットな並び（`coproduct_block`）を型タグの優先順位に基づいて二分木ASTへと貪欲に縮約（Reduction）するアルゴリズムについて規定します。

---

## 1. 概要とデッドロックの回避

Sign言語において、スペースによる並置は「余積（Coproduct）」を意味し、型に応じて~~逆適用、~~`apply`（関数適用）、`compose`（関数合成）、`concat`（リスト連接/双積）のいずれかに還元されます。~~ただし逆適用は固有のノードを持たず、左右を入れ替えた `apply` へ展開される糖衣構文です（§3.1）。~~（旧仕様：この段落の2か所の打ち消しは、逆適用の廃止による（alpha1 の R47））

型推論（Algorithm W）の完了を待ってからASTを構築しようとすると循環依存が生じるため、本リゾルバーは**構文解析直後に各ノードに「やんわり」と付与された型タグ（構造的・構文的種類情報）**を用いて、決定論的に結合関係を解決します。

## 2. 項の型カテゴリ判定（getCategory）

解析対象の各ノード `node` に対し、型推論前のおおまかなカテゴリ（`Lambda` または `Atom`）を以下のルールに従って判定します。

- **`Lambda`（関数・射）と判定される条件**:
  - ノード自身に `isLambda` フラグが立っている。
  - `?`（関数定義）や `compose`（合成ノード）、部分適用状態の `operation`（オペランドが一部欠けている中置・前置・後置演算子など）。
  - `print`, `<print>`, `_` 等の定義済みの組み込み関数名。
  - 前置演算子 `@` が適用されている項。
- **`Atom`（値・対象）と判定される条件**:
  - 数値リテラル、文字列リテラル。
  - 環境マップ `env` に登録された識別子のうち、カテゴリが `Atom` であるもの。
  - 算術演算やリスト連接 `concat` 等の通常の演算ノード。
  - その他上記に該当しないもの。

## 3. 優先順位（Precedence）の定義

隣接するペア `(LHS, RHS)` の型カテゴリ組み合わせに対して、以下の縮約を定義します。

| 名前 | 左辺型 (`leftCat`) | 右辺型 (`rightCat`) | 還元先ノード | 意味 |
| :--- | :--- | :--- | :--- | :--- |
| **10.5** | `Lambda` | `Lambda` | `compose` | 射の合成（関数合成） |
| **10.4** | `Lambda` | `Atom` | `apply` | 射の適用（関数適用） |
| **10.3** | `Atom` | `Lambda` | ~~`apply`（左右を入れ替えて展開）~~ | ~~逆適用（右辺の関数に左辺の値を適用）。§3.1 参照~~（旧仕様：逆適用は廃止、alpha1 の R47） |
| **10.2** | `List`（同じ階） | `List`（同じ階） | `concat` | 同じ階どうしを**平らに**繋ぐ（`xs ys`（`xs : 1 2`・`ys : 3 4`）は `[1 2 3 4]`）。§5.2 |
| **10.1** | `Atom \| List \| Struct` | `Atom \| List \| Struct` | `unshift` | 階が違うか `Struct` を含む対。浅い方を1段ずつ上げていちばん深い項の階に揃えてから繋ぐので、浅い方は深い方の**1要素として**足される（`0 [1 2 3]` は `[0 1 2 3]`、`m [5 6]`（`m : 1 2 , 3 4`）は行が1つ増える）。構造体は欄を繋がず、並びの1要素。§5.2 |
| **10.0** | `Atom` | `Atom` | `construct` | 直和/双積（リストの連接） |

> [!IMPORTANT]
> **`10.x` は縮約の名前であって、解決の順序ではない。** 番号は歴史的なもので、他の文書
> （`operator_table.md` 等、計8ファイル）が名前として参照しているので残してある。
> **順序は下の §3.0 が定める。**

### 3.0 解決の順序

**余積での関数適用は、構築より下の優先順位である。** `f a b` と書いたとき、`a b` が先に
器になってから `f` へ渡るのが自然な読みであり、`(f a) b` のように1つずつ食うのは「関数適用が
構築より内側にある」と言っているのと同じである。

**ただし、1つ取ってもまだ足りない関数だけは先に食う。** `g : a b ? …` に `g 1 2` と書いた
とき、`1 2` を器にしてから渡すと引数が1つしか無いことになる。アリティが「あと要る」と
言っている間は適用が内側であり、飽和した時点で構築へ譲る——順序を静的な段だけで決めず、
関数自身のアリティに聞く。

**そして合成が最も内側である。** `double inc 5` は「double してから inc」であり、射が
並んだらまず合成が決まって、その合成へ値が渡る。合成が未飽和の適用より後ろにあると
`inc 5` が先に潰れて `double (inc 5)` になり、**順序が逆さまになる**。

内側から順に：

| 順 | 対 | 条件 | 縮約 |
| :--- | :--- | :--- | :--- |
| 1 | `Lambda` `Lambda` | — | `compose` |
| 2 | `Lambda` `Atom` | **未飽和**（この1つを取ってもまだ要る） | `apply` |
| 3 | `Atom` `Atom` | — | `concat` / `unshift` / `construct`（形が決める。10.2〜10.0） |
| 4 | `Lambda` `Atom` | 飽和済み | `apply` |
| 5 | `Atom` `Lambda` | ~~ポイントフリーは除外（§3.1）~~ | ~~`apply`（左右入れ替え）~~（旧仕様：逆適用は廃止、alpha1 の R47） |

実測（`alpha/javascript`、木をそのまま）：

```text
d : x ? x * 10        1引数

d 1 2   →  construct(apply(d, 1), 2)    2 が 1 を取り、余った 2 は 3 で器へ
1 d 2   →  construct(1, apply(d, 2))    Atom Atom の対が無いので 4 が動く

f : x y ? x           2引数

f 1 2   →  apply(apply(f, 1), 2)        未飽和なので 2 が2回
f 1 2 3 →  construct(apply(apply(f, 1), 2), 3)   飽和した後は 3 へ譲る

double : x ? x * 2    inc : x ? x + 1

double inc 5 →  apply(compose(double, inc), 5) = 11   1 が先に合成を決める
inc double 5 →  apply(compose(inc, double), 5) = 12   並べた順がそのまま流れる
```

> [!NOTE]
> **この順序は以前と逆である。** 一時期は正しさを最適化より優先して 10.5→10.0 の番号順に
> 解決していたが、現在は構築が適用より内側である。番号順に読むと `d 1 2` が `(d 1) 2` に
> なり、実装（`pass2.js` の `COPRODUCT_PHASES`）と食い違う。**番号と順序は別物である。**



> [!IMPORTANT]
> **スペースは常に余積であり、同じ階に積む。** 階を上げるのはカンマ（直積）・2行以上の括りの改行・
> 前置 `~` で、後置 `~` は1段下ろす（[`list_model.md`](../type/list_model.md) §1 の表・§2.2）。
>
> 括りは内を解いて外す（`[x] ≅ x`）。括らない行の項は全部、いちばん深い項の階に揃えてから
> （浅い項を1段ずつ上げて）左から積む——同じ階どうしは平らに繋がり（10.2）、上げた浅い項は深い方の
> 1要素になる（10.1）。揃える階は行全体で決まり、足す向きは書いた順のままなので、左右の種別で
> 規則は変わらない。後置 `~` は項の階を下ろすだけで、繋ぐ規則は同じである。`[1 2] [3 4]` は
> `[1 2 3 4]` であり、2次元は `1 2 , 3 4` と書く（§5.2）。

> [!NOTE]
> 数値は [`operator_table.md`](../syntax/operator_table.md) の欄と対応する**名前**である。
> **大小は解決の順序を表さない**——順序は §3.0 が定める（`10.0` の構築が `10.4` の適用より
> 内側である）。
>
> **`10.x` は tier でもない。** 空白（余積）そのものは `operator_table.js` では tier 11 で
> あり、`10.x` はその内部のカテゴリ対に付けた名前である（演算子表の ※6 を参照）。

### 3.1 10.3 は独立したノードを作らない（逆適用は糖衣構文）

> [!WARNING]
> **旧仕様**（利用者 2026-11-11）。この節（§3.1 と、下の2つの小節「receiver は1オブジェクトとして数えられるものに限る」「ポイントフリーは 10.3 の対象外」）のうち、10.3（`Atom` `Lambda` の対）を逆適用として読む規則と、それを前提にした所は、今の仕様ではない。それは次の所である：節と2つの小節の見出し、`x f` を左右を入れ替えた `apply(f, x)` へ展開する規則（この印のすぐ下の太字の文と、その下のコードブロック、receiver の小節のコードブロックの `x f` の行）、「つまり `x f` は」の段落のうち、`x f` を適用の記法とする所と、10.3 を左右を入れ替えた適用の規則として規範に残す所と、最後の文（逆適用のノードの型と評価規則を糖衣にした、という所）、「固有のノードを持たせると、」の段落を逆適用を糖衣にした理由として読む所と、`(5 add) 3` を 8 と見込む所、receiver（10.3 の左辺）に後置 `~` を書けないという規則（小節の最初の文と、コードブロックの `x~ f` の行と、その下の段落）、ポイントフリーを 10.3 の対象から外すという規則（receiver 記法という別経路を重ねない話と、`5 [+]` の読みの話）。逆適用は廃止した（利用者 2026-10-23、alpha1 の R47）。今は、値の後ろの関数はその値を取らず、積まれて後ろの項を右から受ける。`x~ f` が今どう読まれるかは、ここでは決めない。「つまり `x f` は」の段落の、適用の意味論は `apply` 一つだけという所と、空白の縮約はカテゴリ対で決まるという理由と、「固有のノードを持たせると、」の段落の、実装で起きた取りこぼしの記録そのものは、この印の外。同じ段落の、`5 add` が完全性公理で `!_` へ潰れる所と、`!_ 3` を余積の左単位元で 3 とする所も、この印の外で、ここでは決めない。receiver の小節のコードブロックの `f x` の行（前置適用で、並びは口が前から要素を取る）と、ポイントフリーが前置適用（`[+ 1] 5`）で呼ばれることも、この印の外。

**10.3 は `apply_reverse` という固有のノードを作りません。左右を入れ替えた通常の `apply` へ展開します。**

```text
x f    →    apply(f, x)        `f x` と完全に同じノードになる
```

つまり `x f` は**記法だけの存在**であり、適用の意味論は `apply` 一つだけです。10.3 という**解決規則そのものは規範に残ります**——空白がどの縮約へ落ちるかはカテゴリ対でしか決まらないためです。糖衣にしたのは、ノードの型と、それに固有の評価規則です。

固有のノードを持たせると、`apply` に対する規定が逆適用へ届かないという取りこぼしが構造的に生じます。実装（`alpha/javascript`）では実際に二度起きました。末尾呼び出し最適化が `apply` しか検出せず receiver 形の末尾再帰だけがスタックを消費し、静的な部分適用の判定も届かないため `5 add` が完全性公理で `!_` へ潰れ、`(5 add) 3` が 8 ではなく 3（`!_ 3` の余積左単位元）を返していました。

#### receiver は1オブジェクトとして数えられるものに限る

10.3 の左辺（receiver）に**後置 `~` を書くことはできません（構文エラー）**。

```text
f x      可。通常の前置適用。`x` が並び（List・String・器を持つ名前）なら、裸の口と最後でない括りの口は先に繋いで前から要素を取る
x~ f     構文エラー。`~` は展開の指示であって、数えられる1つの値ではない
x f      可。`x` を1つの receiver として渡す
```

`x~ f` と書いた側が「receiver を1個渡す」つもりなのか「複数引数へ展開する」つもりなのかは静的に確定できません。[原理4](../0_design_principles.md)により、値を返さずここで弾きます。

#### ポイントフリーは 10.3 の対象外

ポイントフリー記述の Lambda（`[+]`、`[+ 1]`、`[!_]`、`[* 2,]` 等、演算子の種類を問わない）は 10.3 の対象にしません。ポイントフリーは前置適用（`[+ 1] 5`）という呼び出し方だけを持ち、receiver 記法という別経路を重ねません。これは「一つのことを表現する方法は一つ」の方針であり、かつ `5 [+]` のように 5 をどちら側の被演算子とみなすか不定になる読みを防ぎます。

## 4. 総当たり優先順位解決アルゴリズム（Reduction）

フラットな項の並び `items`（例: `a b c d` に対する型タグ `Ta Ub Vc Wd`）に対して、以下の手順で二分木を構築します。

> [!WARNING]
> **旧仕様**（利用者 2026-11-11）。この下の手順のうち、1. の段の走査の最後の段（「→ 逆適用（Atom-Lambda、§3.1 により `apply` へ展開）」の所で、「§3.0 の解決順（1〜5）」の 5 もこの段のこと）と、3. の最初の箇条の最後の文（「10.3 の場合は §3.1 の通り、左右を入れ替えた `apply` になります。」）は、今の仕様ではない。逆適用は廃止した（利用者 2026-10-23、alpha1 の R47）。今は、値の後ろの関数はその値を取らず、積まれて後ろの項を右から受ける。ほかの4つの段（合成・未飽和の適用・構築・飽和済みの適用）と、手順の残りは、この印の外。

1. **段の走査**:
   §3.0 の解決順（1〜5）を上から順に処理します。**`10.x` の番号順ではありません。**
   すなわち compose（Lambda-Lambda）→ 未飽和の適用（Lambda-Atom かつアリティがまだ要る）
   → 構築（Atom-Atom）→ 適用（Lambda-Atom、飽和済み）→ 逆適用（Atom-Lambda、§3.1 により
   `apply` へ展開）の順。**合成が最も内側で、構築は適用より内側である。**
2. **リストの左結合スキャン**:
   現在適用中の優先度 `prec` に対し、`items` の左から順に隣接するペア `(items[i], items[i+1])` を走査します。
3. **マッチングと縮約 (Reduction)**:
   - 各ペアの型カテゴリ `(catL, catR)` が `prec` の条件と一致した場合、その2つの項を取り出して新しい `operation` ノード（`concat`, `compose`, `apply`）に結合します。10.3 の場合は §3.1 の通り、左右を入れ替えた `apply` になります。
   - 例: `f 1 2 3`（`f` はアリティ2）では `(f, 1)` と `(f 1, 2)` が段2に当たり、飽和した
     あとの `3` は段3で器へ回って `(f 1 2) 3` になります。**同じ並びでも、関数のアリティで
     どこまで食うかが変わる**のはこの1点です。
   - `double inc 5` は段1（合成）が先に `double inc` を決め、その合成へ 5 が渡ります。
     ここが段2より後ろにあると `inc 5` が先に潰れて順序が逆さまになります。
   - 縮約が実行された場合、リストのインデックスを更新して、再びリストの最初から再スキャンを行います（左結合性の保証のため）。
4. **収束**:
   すべての優先度レベルの処理が終了したとき、リストは単一のルートノードに収束します。

この総当たり優先度ディパッチにより、曖昧なスペース結合関係が型タグに基づいて一意かつ健全に解決されます。

## 5. リスト・構造体（Struct）の並置と階の揃え

### 5.1 階は書いた形が決める
空白で並べた `List` どうしも、`Struct` を含む並びも、1つの規則で積まれる。繋ぎ方を決めるのは各項の**階**であり、階は書いた形が決める——数と文字は0階、`,`・2行以上の括りの改行・前置 `~` が階を上げ、後置 `~` が1段下ろし、空白は同じ階に積む（括りは内を解いて外す、`[x] ≅ x`）。仮引数のように定義サイトから中身の見えない名前の階は、渡された値で決まる（[`list_model.md`](../type/list_model.md) §2.2）。記号の意味は、左右の種別や印の組み合わせで変わらない。

### 5.2 結合の条件と評価のセマンティクス

括りの内を先に積んで1つの値にし、括らない行の項は全部、いちばん深い項の階に揃えてから（浅い項を1段ずつ上げて）左から積む。揃える階は行全体のいちばん深い項で決まり、隣り合う2項だけでは決まらない（`5 6 m` も `m 5 6` と同じ4行になる）。

1. **同じ階どうし（`list list`）**
   - 平らに繋ぐ（`concat`、10.2）。`xs ys`（`xs : 1 2`・`ys : 3 4`）も `[1 2] [3 4]` も `[1 2 3 4]` である。2次元にしたいならカンマ（`1 2 , 3 4`）か、行ごとに改行した括りで書く。
   - 書いた括りを並べた `[1 2] [3 4]` と、それを入れ子にした `[[1 2] [3 4]]` は平らな `[1 2 3 4]` で、読む段が書いた所に warning を1つ出す（言い分は「2次元なら `1 2 , 3 4`、平らなら `1 2 3 4`」）。出すのは並びの項が全部「2項以上の値を書いた括り」の時だけで、`0 [1 2 3]`・`[1 [2 3]]`・名前で繋ぐ `xs ys` には出ない。この warning の名前は未決である。
2. **階の違う物（`element list`・`list element`・`matrix row`）**
   - 浅い項をいちばん深い項の階まで1段ずつ上げてから繋ぐ（`unshift`、10.1）。上げた項は深い方の並びの**1要素**になる。`0 [1 2 3]` は `[0 1 2 3]`、`[1 2 3] 4` は `[1 2 3 4]`、`m [5 6]`（`m : 1 2 , 3 4`）は `[1 2 , 3 4 , 5 6]` である。
   - 括らない項はそれぞれ揃う。`m 5 6` と `5 6 m` は `5`・`6` がそれぞれ長さ1の行になって4行、括りの内を先に積んだ `(5 6) m` は3行である。
   - 要素が文字列でも同じで、`` `ab` ts ``（`` ts : `cd` , `ef` ``）は cons で `` [`ab` , `cd` , `ef`] `` になる。
3. **構造体（`struct struct`・`struct 5`）**
   - 構造体は空白で並べても欄を繋がず、並びの**1要素**になる（10.1）。`st 5` は2要素、`[[g : inc] [g : double]]` は構造体2つの List である。
   - 欄を混ぜるのは組み直し（[`list_model.md`](../type/list_model.md) §5.3.1）で書く。
   - 構造体に後置 `~` を付けて並べた `st~ 5` の読みは未決である。
4. **後置 `~` と前置 `~`**
   - 後置 `~` は項の階を1段下ろす（μ）だけで、繋ぐ規則は同じである。`m~` は `[1 2 3 4]`、`m~ 5 6` と `m~ [5 6]` は `[1 2 3 4 5 6]` である。1階の並びに付けた `xs~` も、0階の数に付けた `5~` も、下ろした先が自分なので `xs`・`5` と同じ値で、知らせは出ない（`m [5 6]~` は `m [5 6]` と同じ3行）。
   - 1段上げるのは前置 `~`（η）で、括りと違って解けない1段の持ち上げである。`~[1 2]` は `1 2` を1行に持つ行列（`' 0` で `[1 2]`）である。`~x~` は前置が先に結んで `x` になる。

```text
m : 1 2 , 3 4    xs : 1 2    ys : 3 4    ts : `cd` , `ef`    st は構造体

xs ys        →  [1 2 3 4]                同じ階を平らに繋ぐ（10.2）
0 [1 2 3]    →  [0 1 2 3]                0 を1階に揃えて足す（10.1）
[1 2 3] 4    →  [1 2 3 4]                同じ規則（左辺が器かどうかは関係ない）
m [5 6]      →  [1 2 , 3 4 , 5 6]        [5 6] を行の階に揃えて足す（10.1）
m 5 6        →  [1 2 , 3 4 , 5 , 6]      5・6 はそれぞれ長さ1の行に揃う（10.1）
5 6 m        →  [5 , 6 , 1 2 , 3 4]      揃える階は行全体で決まる（10.1）
(5 6) m      →  [5 6 , 1 2 , 3 4]        括りの内を先に積む（10.1）
`ab` ts      →  [`ab` , `cd` , `ef`]     cons（10.1）
st 5         →  st と 5 の2要素           欄を繋がず、並びの1要素（10.1）
m~           →  [1 2 3 4]                後置 ~ は1段下ろす
m~ [5 6]     →  [1 2 3 4 5 6]            下ろした m と同じ階で平らに繋ぐ（10.2）
```

### 5.3 リゾルバーでの実装処理

> [!NOTE]
> **alpha の記録（規則ではない）**：下のコードは、alpha の前の実装（pre-alpha の `coproduct_resolver.js`、
> [`pre_alpha.md`](../appendix/pre_alpha.md)）が `concat` の還元に置いた検査である。両辺が `List` / `Struct`
> （`bracket` ブロックや `coproduct_block` 等を含む）と判定された対を、双方に後置 `~` がある時だけ繋ぎ、
> それ以外はこの段で結ばずに飛ばす。規則は §5.2 である。

```javascript
// coproduct_resolver.js の実装ロジック
if (isListL && isListR) {
  const leftHasTilde = (left && left.type === 'operation' && left.operator === '~' && left.position === 'postfix');
  const rightHasTilde = (right && right.type === 'operation' && right.operator === '~' && right.position === 'postfix');
  if (leftHasTilde && rightHasTilde) {
    // 双方にチルダがある場合のみ、連接（concat）として結合を許可する
    newNode = { type: 'operation', operator: ' ', left, right, name: 'concat' };
    items.splice(i, 2, newNode);
  } else {
    // チルダがない、または片方にしかない場合はマージせず、この時点での結合をスキップする
    continue;
  }
}
```

### 5.4 裸のストリーム仮引数は書けない（名指しで断る）

括りの外に `~名前` を置く仮引数——`f : x ~xs ?`・`f : ~this ?`・仮引数のブロックの `~xs` の行
（既定値が付いていても）——は**書けない**（利用者の裁定 2026-10-04）。コンパイラは仮引数の並びを
組む所で名指しで断る（`OperationError`、理由 `bare-stream-param`）。1行の形もブロックの形も、
ラムダの中・枝の中・`$` で物にした形・export・取り込みも、同じ1か所を通る。

器（String・List・Struct）は**括りで受ける**。丸ごと受けるなら `[~xs]`、頭と残りに割るなら
`[x ~xs]`、構造体なら `[~this]`・`[foo bar ~this]`。括りは渡された1個の実引数を受けるので、
`~` を付けずに渡すのが正しい呼び方である。並べた実引数も括り1つの器になる（`f 1 2 3` は
`f (1 2 3)`）。C も値渡しと参照渡しだけで足りている——裸の `~xs` は値でも場所でもない
第3の受け方だった。

```sign
` ❌ 名指しで断る（裸のストリーム仮引数）
f : x ~xs ? x
```

```sign
get_age : [x ~xs] ? x

` ✅ 括りで受ける。~ は要らない
get_age [1 2 3]
```

判定は仮引数の並びの形だけで決まる：括りの外（並びのトップレベル）に `~名前` があれば断る。
括りの中の `~名前` は rest である（`[x ~xs]`・混在形の `a [h ~t]`・ブロックの `[~this]` の行）。

残るもの：括りの中の rest、範囲・規則（`1 ~+ 2`）、入力（`~@uart`）、貪欲なポイントフリー
（`[+] 1 2 3`）。後置 `~` は、2階以上の物を1段下ろす所（`m : 1 2 , 3 4` の `m~` は `1 2 3 4`、
`[+] m~` は `10`）と、鍵の位置（`list ' 1~`・`list ' @i~`）と、撒く取り込みの `@~` に残る。
並びを関数へ渡すのに `~` は要らない（`f lst` と書けば、裸の口は前から要素を取る。畳み込みは `[+] [1 2 3]`）。

> [!NOTE]
> 以前この節は「裸の Rest パラメータへ `~` なしで List（と文字列、2026-09-28）を渡すと TypeError」を
> 定めていた。`f : x ~xs ?` へ `f [1 2 3]` と渡すと配列全体が `x` に束縛されて `~xs` が空になる、
> という静かな挙動を止める門だった。受ける形そのものを廃止したので、この門は対象を失った。
