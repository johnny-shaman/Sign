# Sign 値表現仕様:文字 boxing と Unit の物理表現

## 1. 概要

Sign 言語の文字型(Char)は **標準 UTF-8(RFC 3629 準拠)** をエンコーディングとして採用する。
MUTF-8 のような独自拡張・overlong 表現は一切用いない。UTF-8 が overlong 表現を禁止しているのは、
規格上の些末な制約ではなく、任意の 1 バイトからその役割(単独文字/継続バイト/先頭バイト)を
自己同期的に判定できるという性質と、overlong 表現を悪用したバイト列偽装(NUL バイトインジェクション等)を
構造的に防ぐという、二重の安全性を担っているためである。Sign はこの安全性を毀損しない。

> [!IMPORTANT]
> **Sign における文字の「boxing」とは、標準 UTF-8 の先頭バイトが本来持つビットパターン
> (`0xxxxxxx` / `110xxxxx` / `1110xxxx` / `11110xxx`)そのものを指す。**
> 型情報(何バイト列か)は、UTF-8 自身の自己記述性から無償で得られる。
> MUTF-8 のような独自エンコーディングは必要ない。

> [!IMPORTANT]
> **本文書が定める UTF-8 は「境界の形式」である。メモリ上の `String` の表現ではない。**
>
> UTF-8 を採る理由は上の通り、先頭バイトのビットパターンが「何バイト列か」を自己記述する
> ため boxing が無償になることである。その利点が効くのは §4 が扱う**外部から届いた Byte 列を
> Char 列へ変換する境界**であって、メモリ上に置いた後の表現ではない。
>
> メモリ上の Char は**固定幅**である。[`type_system.md`](../type/type_system.md) が `List` を
> 「固定幅要素の連続領域」と定め、`String ≅ List(0u)` の根拠を「要素幅が同じなら同一の
> ビット表現」としている以上、可変長のままでは `s ' i` を `base + i × sizeof(T)` の 1 命令で
> 出せず、`String` が `List` でなくなってしまう。
>
> 幅は [`option.ms` の `charset`](../build/option_ms_schema.md) が決める
> （`ascii` = 1 byte / `utf32` = 4 byte、既定は `ascii`）。どちらも固定幅なので同型は保たれる。
> U+0000 を niche として `__` に充てる規則（§3）は、どちらの幅でもそのまま成り立つ。

## 2. UTF-8 エンコーディング規則(標準準拠)

| コードポイント範囲 | バイト列 | 先頭バイト |
| --- | --- | --- |
| U+0001 〜 U+007F | `0xxxxxxx` | 1バイト(ASCII 互換) |
| U+0080 〜 U+07FF | `110xxxxx 10xxxxxx` | 2バイト |
| U+0800 〜 U+FFFF(サロゲート域を除く) | `1110xxxx 10xxxxxx 10xxxxxx` | 3バイト |
| U+10000〜U+10FFFF | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` | 4バイト |

> [!NOTE]
> **U+0000 は Char 型のコードポイント範囲に含まれない。** 理由は次章。
> **U+D800〜U+DFFF(サロゲート域)も同様に Char 型の範囲外**とする。単独の Scalar Value として
> 不正であることは Unicode 標準自身が規定しており、Sign 独自の制約ではない。

## 3. `__`(Unit)と U+0000 の関係:niche による統合

### 3.1 基本方針

Char 型の内部表現(コードポイントを保持する整数)は、Unicode の仕様上 **U+0000 を正当な文字として
使う理由が実務上ほぼ存在しない**(制御文字としての原義は失われて久しく、テキストの中身として
意味を持つ場面がない)。そこで Sign は、この 1 点を **Char 型の値域から構造的に除外する(niche)**。

```
Char 型の値域 := { U+0001, ..., U+D7FF } ∪ { U+E000, ..., U+10FFFF }

除外される 1 点 U+0000 のビットパターンは、
Char 型の文脈においては `__`(Unit)として扱われる。
```

これは Rust の `char` 型がサロゲート領域を除外し、`Option<char>` が `char` と同一サイズで
済むようにしている niche 最適化と、同型の技法である。

### 3.2 なぜこれで overlong 問題が消えるか

MUTF-8 は「U+0000 を無理に 1 コードポイントとして表現し続けるために、regular UTF-8 が禁止する
overlong 列を特例的に許可する」という設計だった。これは規格の穴を突く回避策であり、
標準準拠の UTF-8 デコーダを通過した瞬間に破綻する(不正列として拒否される、あるいは
過去に実際に悪用されたのと同じ攻撃面を再現する)。

Sign の設計はこれと根本的に異なる。**U+0000 という値そのものを Char 型の世界から消す**ため、
「U+0000 をどう安全にエンコードするか」という問い自体が発生しない。エンコードすべき対象が
存在しないのだから、特殊なバイト列も要らない。

### 3.3 `$__` の指すもの

```
Sign rodata(コンパイラ管理):
┌──────────────────────┐ ← $__ が指すアドレス
│ [Char niche スロット] │ (Char 型内部表現において構造的に出現しない値)
└──────────────────────┘
```

- 物理番地 0x00 とは無関係(ターゲットのメモリマップ上の意味は問わない)
- ARM のリセットベクタ・stdin(fd=0)・RISC-V の実装依存リセットベクタ等、いかなる
  ハードウェア規約とも衝突しない(niche はあくまで Char 型の内部表現空間の話であり、
  アドレス空間の話ではないため)
- 書き込み不可(read-only)。`$__ # X` はこの領域への書き込みであり、致命的エラーとする

### 3.4 配置規約:`.rodata + 0x00 = $0u00`

niche slot は `.rodata` セクションの**先頭(オフセット0)**に予約するという単一の規則を、コンパイラが常に守る。

```
$0u00 = .rodata セクションの開始アドレス + 0x00
```

他の定数(文字列リテラル等)はこの後に連続して配置される。この規約により:

- `$0u00` は `.rodata` セクションの開始アドレスそのものと一致し、他の定数の数やビルドごとの内容変化に一切依存せず一意に求まる
- niche の値そのもの(U+0000)と配置オフセット(0x00)が一致するのは意図的な語呂合わせであり、覚えやすさに寄与する
- `.rodata` は実行中に一切移動しない静的領域であり、GC の管理対象でもないため、[`memory_management.md`](../memory/memory_management.md) の `###`(Pin アロケーション)とは無関係である。`###` は GC によって再配置されうる**ヒープ上の**オブジェクトを固定するための機構であり、もともと動かない `.rodata` 定数には適用の必要がない
- layer 0(ベアメタル)でも layer 1+(OS上)でも、リンカの `.rodata` 配置はすでに確立された仕組みであり、新たな"Pin"機構を介さずに両方で一貫した答えを出せる

### 3.5 GPR 幅の型の niche:`0x8000000000000000`

`Char` に niche が要ったのと同じ理由が、`Int` と `Address` にもある。**レジスタ1本に
「値」と「値の不在」の両方を入れるには、値域から1点を外すしかない。**

これはコード生成で避けて通れない。Sign では **`__` だけが偽であり、`0` は真である**
——`0 = 0` は真で、そのとき返せるオペランドは `0` しかない（[`comparison.md`](../type/comparison.md) §2.1）。
`__` を `0` で表すと、この真が偽と区別できなくなる。

```
GPR 幅の niche := 0x8000000000000000
```

根拠はどちらもハードウェアの側にある。

* **`Int`** — 2の補数で唯一「正の対応物を持たない」値（`INT_MIN`）である。除外すると
  値域が `-(2^63 - 1)` 〜 `2^63 - 1` と対称になる。もともと `-INT_MIN` が定義できない
  点であり、そこを外すのは値域を歪めるというより**歪みを取り除く**方に近い。
* **`Address`** — AArch64 の仮想アドレスは上位16ビットが全0か全1でなければ正準では
  ない。`0x8000...` は非正準領域にあり、**そもそも有効なアドレスになりえない**。

`Float` はこの値を使えない——`0x8000000000000000` は**負のゼロ**という正当な値だから
である。浮動小数の niche は NaN のペイロードから採ることになるが、まだ決めていない。

> [!IMPORTANT]
> **niche は型の内部表現空間の話であって、アドレス空間の話ではない**（§3.3 が `$__` に
> ついて既にそう書いている）。`0x8000000000000000` を niche にすることと、その番地に
> 何かが在るかどうかは無関係である。
>
> [`unit.md`](unit.md) §5.1 は「Unit値を NULL ポインタとして表現」「xZR レジスタの特性を
> 活用」と書いていたが、これは同じ文書の §5.2 とも食い違っていた——§5.2 の表は
> `0x00`（アドレス値ゼロ）を「**有効な値を持つ**」と明記している。0 が有効な値である
> 以上、0 を不在の印にはできない。

### 3.6 boot-up 初期化:`$__` と `@__` の不動点

`$`(アドレス取得)と `@`(デリファレンス)は一般に互いに逆写像ではない(`@$x = x` だが `$x ≠ x`)。
しかし `__` の niche slot の中身として、**スロット自身のアドレス値を自己参照的に書き込んでおく**と、
以下の不動点が成立する:

```
$__ = .rodata + 0x00                    (アドレスとしての __)
@__ = *($__) = .rodata + 0x00            (中身としての __ 、自己参照により $__ と一致)
∴ $__ = @__ = __
```

これは `$`/`@` 随伴の単位射と余単位射が、`__` 1つの対象に限って同一値に潰れるという美しい不動点だが、**実現には1回きりの自己参照初期化が必要**である。これは `.rodata`(§3.4)が
本来 read-only であることと一見矛盾するが、**read-only 保護が有効になる前の、一回きりの特権的な書き込み**として
区別すれば矛盾しない。

- **layer 0(ベアメタル)**：リンカが `.rodata` セクションのレイアウトを確定させた時点で、niche slot の値はリンカ自身が
  自分のアドレスを解決できる。boot-up コードの実行を待たず、**リンク時のリロケーションとして解決済みの値**が
  Flash/ROM イメージに書き込まれる。ELF の `R_*_RELATIVE` 型リロケーションと同じ発想であり、
  ハードウェアの特権モードも boot-up ランタイムも一切介さない
- **layer 1+(OS上)**：ローダがプロセスイメージを作成し、`.rodata` ページを read-only 保護（mprotect 等）
  する**直前**に、ローダ自身がロードアドレスを解決して niche slot に書き込む（ASLR 下でも
  ロードアドレスはロード時点で確定するので問題ない）。通常の動的リンカの self-relocation フェーズと
  完全に同じ手続きであり、Sign 固有の新しいブートストラップは一切不要

どちらの layer でも、**既存のリロケーション/ロード専用フェーズの一部としてこの自己参照書き込みが行われる**点が
重要である。`.rodata` が read-only 保護されるのはこの初期化の**後**であり、§3.3の「`$__ # X` は致命的
エラー」はあくまで**実行時のユーザコードからの書き込み**に適用され、boot-up リロケーションはその規制の
外側（リンカ/ローダというツールチェーンの特権）で行われるという位置づけになる。

### 3.7 将来の拡張余地：Unicode非文字（noncharacter）を使った追加niche

Unicode標準は U+0000 とは別に、「将来も絶対に文字として割り当てられない」と保証されている
**非文字（noncharacter）**を 66 個予約している（`U+FDD0`～`U+FDEF` の 32 個、及び各面（plane）末尾の
`U+xFFFE`/`U+xFFFF` の 34 個）。U+0000 と同じ理屈で niche 化できるが、用途の性質が異なる：

- **`U+FDD0`〜`U+FDEF`（32個）**：ペア構造を持たない、フラットな32個の独立したセンチネルとして使える
- **各面末尾の `U+xFFFE`/`U+xFFFF`（17面 × 2 = 34個）**：このペアは偶然ではなく、BOM（`U+FEFF`）が
  バイトオーダー逆転で読まれた際の誤検出パターンとして意図的に非文字化された経緯を持つ。つまり
  「面（plane）というチャンネルごとに2値のペアが組になっている」という構造がすでに Unicode 自体に存在している。
  追加のビットや型タグを一切使わずに「17種類のチャンネル × 各、2値」を Char 型経由で表現できる余地がある

これは U+0000 の niche と同様、ソフトウェア側の発明ではなく **Unicode 標準自体が保証する未使用領域**を活用するという発想であり、
具体的な利用方法（例：複数の特殊値を必要とする型の表現）は未確定のまま今後の検討事項とする。

**さらに大きな拡張余地：サロゲートペアの組み合わせ**

サロゲート域 `U+D800`〜`U+DFFF`（2048個）も §2 の通り Char 型の範囲外として既に除外済みだが、
これを high surrogate（`U+D800`〜`U+DBFF`、1024個）と low surrogate（`U+DC00`〜`U+DFFF`、1024個）の
**ペアの組み合わせ**として捉えると、`1024 × 1024 = 1,048,576` 通りという大きなタグ空間になる
（UTF-16がサロゲートペアで補助面を表現する仕組みと同じ理屈のため、補助面のコードポイント数と一致する）。
Signは4バイトUTF-8で補助面を直接表現するためサロゲート機構自体は不要だが、不要だからこそこの
組み合わせ空間を丸ごと転用できる。U+0000（1個）や非文字（66個）と比べても桁違いの規模であり、
この利用方法も同様に今後の検討事項とする。

**UTF-8を選択できない環境向け：ASCII C0制御コード領域**

上記はいずれも Unicode/UTF-8 の存在を前提とするが、非常に制約の強いベアメタルターゲットや
 Byte 型のみで完結する層では UTF-8 デコード自体が不要/不可能な場合もある。その場合は、
さらに一段下の層である **ASCII C0制御コード領域（0x00〜0x1F、33個）**が同様の役割を果たせる。
実際`lexer.js`はすでに`\x02`（STX）/`\x03`（ETX）をIndent/Dedentマーカーとして使用中であり、
これは本節で述べているnicheの発想と同一である（UTF-8さえ前提としない、より基礎的な例）。

- `0x00`（NUL）— Unicode niche（U+0000）とは別に、Byte型文脈でも同様の位置づけになりうる
- `0x02`/`0x03`（STX/ETX）— 既にIndent/Dedentマーカーとして使用中
- `0x09`/`0x0A`/`0x0D`（TAB/LF/CR）— 空白・改行として意味を持つため除外
- **`0x1C`〜`0x1F`（FS/GS/RS/US: File/Group/Record/Unit Separator）** — ASCII規格が制定時点から
  「階層的なデータ区切り」のために予約していた4つ。Signが今`\x02`/`\x03`でやっている
  インデント区切りと完全に同じ発想がASCII制定時点で既に標準化されていたことになる
- 他に `0x01`, `0x04`〜`0x08`, `0x0B`〜`0x0C`, `0x0E`〜`0x1B` も未使用のまま残っている

Unicode/UTF-8が使えない環境でも、このC0領域はbyte列レベルで常に存在するため、同様の拡張手段として
利用可能である。

## 4. Byte 型との明確な分離

バイナリセーフ性(任意の 0x00〜0xFF を正当なデータとして扱う必要)が要求される場面は、
Char 型ではなく **Byte 型** が担う。

| | Char 型 | Byte 型 |
| --- | --- | --- |
| 値域 | Unicode Scalar Value(U+0000, サロゲート域を除く) | 0x00 〜 0xFF 全域 |
| niche | あり(U+0000 が `__` と同一視される) | なし |
| 終端表現 | 不要(`__` は niche、センチネル不要) | 長さの外部化(`[len ~bytes]`)を強制 |
| 典型用途 | 文字列・テキスト | 画像・シリアライズ済みデータ・FFI 境界 |

Byte 型には niche が存在しないため(全 256 値が正当なデータになりうる)、終端やUnitを
バイト値に同居させる回避策は取らない。これは前々節の C 言語 NUL 終端・EOF センチネルが
抱えていた病理(データと境界情報を同一チャネルに多重化する誤り)を、構造的に再発させない
ための明示的な設計判断である。

外部から届く任意のバイト列(他システムが生成した、U+0000 を含みうる UTF-8 データ等)は、
まず Byte 型として受け取り、Char 型列への変換時に U+0000 の有無を検査する。この変換境界は
`@`(前置・input)が Unit で吸収元に倒れる規則と対応する。

## 5. 幅を書く:`NxHHHH` / `NuHHHH` 記法

> [!NOTE]
> **設計として確定、実装は未着手。** 現状 `0x…` は幅を語らないため、`@` も `#` も常に
> 8 byte で出る。

### 5.1 何が問題か

`0x09000000` は「その番地に何が居るか」を一言も語っていない。したがって `@0x09000000` は
`Raw` 型になり、`widthOfType` が機械型に落とせず既定の 8 byte へ倒れる——`ldr x9, [x9]` が
出る。だが MMIO のレジスタは 8/16/32 bit であることが普通であり、**64 bit で触るのは
単に誤りである**(隣のレジスタを巻き込む、あるいはバスが受け付けない)。

幅を語る手段が無いので、書き手には「きちんと bit 幅ぶんの 0 埋めを怠るな」という規律しか
残らない。**規律は検査できない。**

### 5.2 記法

プリフィックスの数を幅として読む。**内部では常に byte** であり、族ごとに書き方が違うのは
表面だけである(§5.3)。

| 記法 | 数の単位 | 幅 | `@`(読む) | `#`(書く) |
| --- | --- | --- | --- | --- |
| `0x…` | — | **`option.ms` に従う**(§5.4) | 語幅の `ldr` | 語幅の `str` |
| `1x…` | byte | 1 byte | `ldrb` | `strb` |
| `2x…` | byte | 2 byte | `ldrh` | `strh` |
| `4x…` | byte | 4 byte | `ldr w` | `str w` |
| `8x…` | byte | 8 byte | `ldr` | `str` |
| `16x…` | byte | 16 byte | `ldr q`(SIMD、layer 3) | `str q` |
| `0u…` | — | **`option.ms` の `charset` に従う** | — | — |
| `8u…` | bit | 1 byte(UTF-8) | — | — |
| `16u…` | bit | 2 byte(UTF-16) | — | — |
| `32u…` | bit | 4 byte(UTF-32) | — | — |

機械にその幅の命令が無いもの(`3x` `5x` `6x` `7x` `9x` …)は診断で弾く。

#### 正規形は2桁

幅を書く場合は**2桁**である(`01x` `02x` `04x` `08x` `16x` / `08u` `16u` `32u`)。
boot コードは MMIO の読み書きを並べて書くので、桁が揃う方が読める。

書く側に摩擦は無い——**preprocess が padding する**。演算子の周りに空白を入れるのと同じ、
表面の正規化である(`8x` と書けば `08x` になる)。`0x` / `0u`（言っていない）だけが1桁で、
そこは幅ではないので別扱いでよい。

### 5.3 UTF は 8 で割る——揃えるのはフロントエンドの仕事

`x` の数は byte、`u` の数は bit である。これは不統一に見えるが、**それぞれの族の世界共通の
呼び名に合わせているだけ**であり、「UTF-8」と書きたい人に `1u` と書かせるのは不自然である。

フロントエンドが `u` の数を 8 で割って byte へ正規化する。**以降のパスは byte しか見ない。**

> [!IMPORTANT]
> **自然な対応はフロントエンドが吸って、コード表面には現れない。** 表面が慣習に従い、内部が
> 1 つの事実だけを持つ、という分担である。同じ判断が「1 要素の器はスカラーと同型」の持ち上げ
> にも効いている(型の側で吸い、書き手には見せない)。

### 5.4 幅を言わない場合は `option.ms` に従う

`0` は「幅 0」ではなく「**言っていない**」である。言わなければ `option.ms` が決める。

| 族 | 従う設定 |
| --- | --- |
| `0x…` | `target` の語幅(aarch64 なら 8 byte、32 bit ターゲットなら 4 byte) |
| `0u…` | `charset`(`ascii` = 1 byte、`utf32` = 4 byte) |

既定を機械語の側で 8 に決め打たないので、**32 bit ターゲットでは書き換えなしに 4 byte に
なる**。そして既存のコードはすべてそのまま通る。

### 5.5 なぜこの形が収まるか

**`0` は既に族の印だった。** 文法は `0x`(番地)・`0r`(レジスタ)・`0b`(2 進)・`0u`(符号位置)
という族を持っており、先頭の `0` は「これは素の数ではない」を言う印として機能していた。
そこへ幅を載せるのは、印の位置に意味を足すだけで新しい構文を作らない。

**プリフィックスの後ろは変わらない。** 値の取り出しは全経路が `.slice(2)` で書かれているが、
`[0-9]+` へ広げても「族の文字の次から」で読めばよく、解析の形は同じである。

**出す側は既に幅で分岐している。** `loadAt` / `storeAt` は 1/2/4/8 を `ldrb`/`ldrh`/`ldr w`/
`ldr` に出し分けており、`Char` の 1 byte も `charset: utf32` の 4 byte もこの道で出ている。
足りないのは**幅をノードへ載せること**だけである。

### 5.6 これは型の属性ではなく、その読み書きの事実である

C の `sizeof` は型が持つ固定値であり、同じ番地を別の幅で触るには型を偽装するしかない。
Sign では幅が**現場に書かれる**——同じ番地をバイトでもワードでも触れるのは、デバイスが
それを許すからであって、型が嘘をついているからではない。

幅が番地の側に載るので、**読みと書きの両方に効く**。番地が幅を宣言し、値がそれに従う。

### 5.7 器の均質性は診断で守る

番地と文字では、幅の効き方が違う。

| | 幅が効く範囲 |
| --- | --- |
| `Nx`(番地) | **その 1 回の読み書き**。同じ番地を byte でも word でも触れる |
| `Nu`(符号位置) | **その器の全体**。`String ≅ List(Char)` は `base + i × 幅` で引く |

したがって「このリテラルだけ 4 byte」は器を壊す。だが `maxCodePointOf` が既に「その
`charset` で書ける符号位置の上限」を見ているので、そこに幅の一致を足せば
**「宣言した幅がプログラムの `charset` と食い違う」を名指しできる**。

均質性が書き手の規律ではなく、**機械が守る規則**になる——`Nx` が 0 埋めについて言うのと
同じ筋である。

### 5.8 `__` との関係

幅を宣言した読みには、`__` との曖昧さが無い。

- 読めた結果は**その幅の数**である。**`0` は正当な値**であって「無い」ではない
  (Sign では `0` は真、[`unit.md`](unit.md))。
- 「無い」は番地の側から来る——`@__ = __`(§3.6 の不動点)。データの側からは来ない。

niche は 64 bit なので 1 byte の読みには入らないが、**入る必要が無い**。狭い読みは値を
返し、`__` は番地が既に語っている。

### 5.9 解釈系との一致

現状、解釈系は生番地について記憶を持たない——`@0x09000000` は番地の数そのものを返し
(`@p = p`)、機械は本当に読む。**両者は黙って食い違っている。**

幅があると、解釈系は疎な記憶(番地 → 値の表)を持てる。

| 式 | 解釈系 | 機械 |
| --- | --- | --- |
| `4x09000000 # 65` | 表へ 65 を 4 byte にマスクして置く | `str w` |
| `@4x09000000` | 表から読む | `ldr w` |
| `1x09000000 # 0x1234` | 下位 1 byte(`0x34`)だけ置く | `strb`(同じ) |

本物のハードウェアが無くても**両方のエンジンが同じ観測を返す**。そして「宣言した幅ぶんの
0 埋め」は書き手の規律ではなく、**両側が同じ場所で切る規則**になる。

### 5.10 `{ptr, len}` の `ptr` が幅を持つ

`Nx` は「その番地に居るものの幅」を言う記法である。同じ事実を**値の型として**持てば、器は
自分の引き方を自分で語れる。

```
器 := { ptr : Address(w), len }      w = 要素1個の byte 数
```

#### なぜ効くか

添字は `base + i × w` であり、切り出しは `{ptr + i×w, len - i}` である——**要るのは `w` だけ**
で、要素が `Int` か `Char` かは引く側の関心ではない。`w` が効くのは器を引く所だけで、書かれた番地の
算術は伸縮しない——`p + n` も `p - q` もいつもバイトである（C の型付きポインタの差のように要素の
大きさで割らない。type_system.md §3.6「番地の域の射」）。ところが現状 `w` は要素型から出して
いる(`elementCellSize`)ので、要素型が無いと引けない。

実測(preprocess.sn、2026-09-01):

| 関数 | 型 | 切り出せるか |
| --- | --- | --- |
| `pop : [~st] ? st ' 1~` | `st` は `Container`、要素型なし | **出せない**(幅が決まらない) |
| `top : [~st] ? st ' 0` | `st` は `Int \| List \| Struct` | 直和のままでは引けない |

切り出しの機械そのものは既に汎用である(`elem.size` を掛けるだけ)。詰まっているのは**幅の
1点だけ**であり、`ptr` が幅を持てばどちらも通る——直和であっても「1個 8 byte」と言えるなら
`' 0` は `ptr` から 8 byte 読むだけになる。**中身が何かを知らずに引ける。**

#### `List(T)` より弱く、しかし十分である

`Container(w)` は「要素が `T` である」とは言わない。だが引くのに要るのは幅だけなので、
**分かっている以上のことを名乗らないまま、必要なことは言えている**(原理4)。要素型が
分かる場面ではこれまで通り `List(T)` が使われ、分からない場面でも器は死なない。

#### 型で持つ。値では持たない

> [!IMPORTANT]
> **上位ビットにタグを詰める設計は採らない。** AArch64 の仮想アドレスは上位16ビットが
> 全0か全1でなければ正準ではなく(§3.5)、タグを載せると参照のたびにマスクが要る
> (TBI は MMU を要求するので `layer: 0` では使えない)。そして**その非正準領域こそ `__` の
> niche が使っている場所**であり、タグは `__` と同じ資源を奪い合う。
>
> 型で持てば代金はゼロである(原理8：同型は型では無償、表現では有償)。`{ptr, len}` は
> 2 本のままで、幅は使う場所ごとにコード生成時に確定する。

#### 幅はどこで決まるか

器を**作った場所**で決まり、型に載って運ばれる。`Nx` リテラルはそれを直接書く手段である
——`4x09000000` は「4 byte のものを指す番地」であり、リテラルで書けるものが値の型としても
持てる、というだけの話である。

### 5.11 実装の当たり

| 場所 | 変更 |
| --- | --- |
| `sign.pegjs` | `address = $("0x" Hex+)` → `$([0-9]+ "x" Hex+)`、`unicode` も同様 |
| フロントエンド | 数を byte へ正規化(`u` は 8 で割る)。`0` は未指定として残す |
| Pass 3 | 未指定なら `option.ms`(`target` の語幅 / `charset`)から埋める |
| | `Nu` は `charset` との一致を検査(§5.7)。機械に無い幅は診断 |
| Pass 4 | `@`(前置 input)と `#`(中置 output)が `loadAt` / `storeAt` へ幅を渡す |
| `interpreter.js` | 疎な記憶と幅マスク(§5.9) |
| Pass 3 / `layout.js` | `ptr` の型に幅を載せ、引く側はそこから取る(§5.10) |

## 6. Id射(`!__`)の dispatch

### 6.1 Id射はエンコード領域に格納しない

Id射の振る舞いは boxing されたバイト列の中身とは無関係であり、**コンパイラが静的に生成する**
(ゼロコスト)。

```
__ | X のコンパイル方式(概念):
  左辺が Unit → 右辺をそのまま返す(Id射の等価操作)
  左辺が非Unit → 左辺をそのまま返す(短絡評価)
```

### 6.2 `!__` の実体

`!__` は恒等射（真）である。「引数をそのまま返す純粋な射」として呼べる（`!__ x = x`）が、
コンパイラが静的に解くので（§6.1）、関数の番地も連続ブロックも持たない（機械の上では `0` として運ばれる）。
[type_system.md](../type/type_system.md) §3.5 の意味での関数オブジェクト（`$` で運ぶ
{関数の番地, 捕まえた値…}）ではない——だから関数の本体が `!__` を返すのに `$` は要らない。
型は `∀A. A → A`。`__`(零対象)とは異なる非 Unit 値(真)である。

## 7. I/O との衝突まとめ

| 値 | UTF-8 表現 | 生の 0x00 | ARM ベクタ衝突 | stdin(fd=0)衝突 |
| --- | --- | --- | --- | --- |
| `__`(Char 文脈) | (存在しない、niche) | なし | なし | なし |
| `"hello"` | 標準 UTF-8 準拠 | なし(Char 型に U+0000 が存在しないため) | なし | なし |
| 任意バイナリ | Byte 型(長さ外部化) | あり得る(正当なデータとして) | 該当なし(Byte型はアドレス空間と無関係) | 該当なし |

> [!IMPORTANT]
> Sign の文字列は標準 UTF-8 として出力され、**外部の任意の標準準拠 UTF-8 ツール
> (OS・ブラウザ・他言語ランタイム等)でそのまま安全に解釈できる。** MUTF-8 のような
> Sign 内部限定の安全性ではなく、業界標準への準拠そのものによる安全性である。
