# Sign 整数オーバーフロー仕様

## 概要

C における最大の設計上の欠陥のひとつが **signed 整数オーバーフローの未定義動作（UB）** である。
Sign はリテラルの型によってオーバーフロー挙動を**静的に確定させる**ことで、
この問題を構造的に排除する。

---

## 1. Sign の数値リテラル型とオーバーフロー挙動

Sign の数値リテラルはプレフィックスによって型と意味が決まる。

| リテラル | 型の意味 | Layer 2 型 | オーバーフロー挙動 | 理由 |
|---------|---------|---------|-----------------|------|
| `0` | 通常の整数（十進） | `Int` | **ラップアラウンド** | 算術演算の自然な挙動。システムに悪影響なし |
| `0r00` | ビット列（raw バイナリ）| `Int` | **ラップアラウンド** | bit演算はラップが前提（暗号・ハッシュ等） |
| `0x00` | アドレス（ポインタ）| `Address` | **`__`（Unit）に収束** | 不正アドレスへのアクセスを防ぐ |
| `0u00` | Unicode コードポイント | `String`（Char） | **`__`（Unit）に収束** | 無効コードポイントの伝播を防ぐ |

**原則——その誤りが致命的かどうかで分ける**:
- 溢れた値が**機械を殺さず、情報も漏らさない**型 → ラップアラウンド。検査の命令を払わない
- 溢れた値が**任意の記憶を読み書きしうる**型 → `__`（Unit）に収束。検査の命令を必ず払う

`Int` の溢れは**間違った数**でしかない。数は番地として使われないので、読み書きの先は
変わらない。`Address` の溢れは**間違った番地**であり、回り込んだ番地はそのまま任意の記憶を
指す——読めば隣の秘密が漏れ、書けば機械が止まる。**致命的なものは必ず検査し、致命的で
ないものは検査の代金を払わない。** 表の「理由」の欄はこの基準の言い換えである。

> [!IMPORTANT]
> **この表が `Int` と `Address` を別の Layer 2 型に分けている根拠である。**
> 溢れ方が違う以上、両者は同じ型ではありえない——ビット幅が同じ（どちらも GPR 1語）
> ことは統合の理由にならない。記法による域の決定は type_system.md §3.6 を参照。

### 1.1 機械の上で払う命令

基準はそのまま命令の数になる。見るのは**結果の型**である（整数段では左辺が域を決める
——`p + 8` は `Address`、`8 + p` は `Int`。type_system.md §3.6）。

| 結果の型 | `a + b` の命令（AArch64） | 検査 |
|---|---|---|
| `Int` | `add x9, x9, x10` | しない（回ってよい） |
| `Address` | `adds x9, x9, x10` / `csel x9, <niche>, x9, hs` | 桁が上がったら `__` |

`-` は `subs` と `lo`（借りが出たら 0 の下へ溢れた）である。分岐ではなく条件選択で置く形は、
C の `__builtin_add_overflow` を clang -O2 で落としたものと同じである。

**番地に足す数は負でもよい**（`p + -4` は `p - 4` と同じ番地）。そのとき桁上がりだけでは
判定できない——負の数を足して正しく戻る番地は、符号なしで見ると必ず桁が上がるからである。
見たいのは数学の値 `p + n`（`p` は符号なし、`n` は符号あり）が `0` 以上 `2^64` 未満に
収まるかで、それは**両辺をそれぞれの符号で1語伸ばしたときの上の語が 0 か**と同じである：

```
asr  x13, x10, #63          // n の上の語（0 か -1）。符号なしの辺の上の語は xzr
adds x9, x9, x10            // 下の語
adcs x13, xzr, x13          // 上の語 = p の上の語 + n の上の語 + 桁上がり（`-` は sbcs）
csel x9, <niche>, x9, ne    // 上の語が 0 でなければ溢れた
```

両辺とも符号なし（または足す数が、`Int` として64ビットで読んで非負の定数——十進の `18446744073709551615` は -1 である）なら上の語は桁上がりそのものなので、`asr` と
`adcs` が畳まれて表の2命令になる（どちらも niche を置く `movz` は数えていない）。
C の `__builtin_add_overflow(u64, i64)` を clang -O2 で落とすと、同じ判定に8命令を使う。

**除算は溢れないが、番地の域では割る数を見る**（左辺が番地のとき。商も番地——type_system.md §3.6「番地の域の射」）。
正の数で割った商は被除数を超えないので、上の物差し（0 以上 2^64 未満か）では何も払わない。見るのは割る数が
0 以下かどうかで、これは溢れではなく、枠の大きさとして意味があるかの規則である。

| 演算 | 命令（AArch64） | 検査 |
|---|---|---|
| `p / q`（`q` は番地） | `udiv` / `cmp` / `csel …, eq` | 0 で割ったら `__`（番地は負にならない） |
| `p / n`（`n` は `Int`） | `udiv` / `cmp` / `csel …, le` | 0 以下で割ったら `__` |
| `p / 4096`（正の字面） | `udiv` | しない（商は被除数を超えないので溢れない） |

`udiv` は負の数 `-n` を 2^64 − n という大きな符号なしの数と読むので、負の数で割った商は 0 か 1（被除数が
2^64 − n 以上のときだけ 1）になり、0 で割れば 0 を返す。どれも意味の無い小さな番地を黙って出す形なので、
まとめて `__` にする。剰余 `p % a` も同じ規則に従う——0 で割った剰余は被除数なので、見なければ揃えの形
`p - (p % a)` が 0 番地になる（機械はまだ `%` を出さない）。以前は負の数で割ったときだけ絶対値で割ってから
商が 0 かを見ていた（`cneg`・`ccmp` を含む形）。

**番地の域に、掛け算・冪・左シフト・階乗の射は無い**（type_system.md §3.6）。`p * k` は溢れを見る前に `__` で
あり、機械は掛け算の命令を出さずに niche を置く。以前はここで積の上の語を `umulh` で見て、溢れなければ
番地を返していた。C でもポインタは `*` `/` `%` の被演算子になれない（C17 6.5.5）。

**整数を 0 で割ると、商は 0、剰余は被除数である**（`Int`・`Char`）。AArch64 の `sdiv`/`udiv`/`msub` が
そう答えるので命令を足さず、除法の等式 `a = (a/b)*b + a%b` が `b = 0` でも成り立つ——等式で書き換える
最適化が、除数を確かめずに効く。**番地の域では 0 以下で割ると `__` である**（上の表）。0 番地は layer 0
では読める記憶なので、黙って返すと致命的になる。

> [!NOTE]
> これは今の最適化に向いた形として選んでいる。`0⁻¹ = 0` と置く草原（meadow）とは同じ形だが、
> 草原の代数や分数を入れるときに見直す。

**番地の規則の n 番目も番地の算術である。** `[p ~+ k] ' i` はロードではなく `start + i × step` なので、
同じ物差しで `mul` / `smulh` / `adds` / `adcs` / `csel` を払う（積 `i × step` は添字の側で作る数であり、
番地を掛けてはいない——`p ± n` と同じ「ずらす」射である）。**検査は作る所に置く**——読む所（`@`）だけで
見ると、作った値を名前へ置いて別の所で `@` したとき、回った番地は正しい番地と同じビットなので区別できない。

**2^64 以上の番地の字面は `__` である**（`0x10000000000000010`）。そういう番地は存在しない——
`0x8000000000000000` と同じく、`__` の別の綴りである。十進の字面は `Int` なので 64 ビットで回る
（`18446744073709551617` は 1）。どこに置いても（添字・切り出しの端・書き込み先）同じ読み方をする。

### 1.2 `INT64_MIN` は `Int` の値ではない

GPR 1語の `__` は `0x8000000000000000` である（value_representation.md §3.5）。`Int` として
読むとそれは `INT64_MIN` なので、**`Int` の値域は `-(2^63 - 1)` 〜 `2^63 - 1` であり、
`INT64_MIN` は値ではない**。回り込んだ結果がちょうどそこへ落ちたら、それは `__` である：

```sign
` → __（回り込んだ先が niche）
a : 9223372036854775807 + 1
` → __（リテラルで書いても同じビットである）
b : -9223372036854775808
```

機械はこのために命令を足さない——回り込んだビットがそのまま niche なので、`__` を見る場所
（仮引数の門・`!`・`|`・算術の完全性公理）では `__` として扱われる。合わせるのは解釈器の側で、
64 bit へ回す畳み込みと niche の判定は1つの規則である（回してから見る。見てから回すと、回った
先の niche を見逃す）。`Address` の `0x8000000000000000` も同じビットなので `__` である
——非正準領域にあり、そもそも番地になりえない。§1.1 の検査を通った結果でも、そこへ落ちれば
`__` になる。

> [!WARNING]
> **`Int` の算術の結果を、機械は `__` かどうか見ない。** 溢れは致命的でないので払わない（§1）。
> 完全性公理の検査は「`__` になり得る辺」にだけ出るので、`__` になり得ない辺どうし（リテラル、
> 門を通った仮引数）の和がちょうど niche に落ち、そこへさらに算術が続くと、機械はその niche を
> 数として扱う。`f : a b c ? a + b + c` に `9223372036854775807 1 5` を渡すと、解釈器は
> `__ + 5` で `5`、機械は `INT64_MIN + 5` を返す。どちらも `Int` が溢れた後の数である。
> **この省略は `Int` の算術が続くときだけである。** その niche が番地の算術の辺に来たら、機械も
> 見る（§1.3）——見なければ niche を足した別の番地が出る。以前ここは「番地の算術は溢れを見るので
> 見逃させない」と書いていたが、`p - (a + b)` に `0x1000 9223372036854775807 1` を渡すと機械は
> `0x8000000000001000` を返していた（`p - INT64_MIN` は溢れていない）。

### 1.3 溢れた番地は、次の算術で生き返らない

算術の `__` は普通、両側で単位元である（爆発律——`__ + 3` は `3`）。それを番地に当てると、§1.1 で
`__` にした番地が次の演算で生き返る。`(p + n) - m` で `p + n` が溢れても `m` が残り、番地として
使われる。だから**結果の型が `Address` の算術では、`__` は両側で吸収する**（`__ + k` も `p + __` も
`__`）。規則と、左右対称である理由は [`operator_table.md`](../syntax/operator_table.md) の
「算術の `__` は両側とも恒等射である（爆発律）」の欄が持つ。

機械の上では、爆発律の `csel` が選ぶ先を「残った辺」から niche へ替えるだけである：

| 結果の型 | `a + b` で `b` が `__` になり得るとき |
|---|---|
| `Int` | `cmp x10, x12` / `csel x11, x9, x11, eq`（残った `a`） |
| `Address` | `cmp x10, x12` / `csel x11, x12, x11, eq`（`__`） |

選ぶ先が変わるだけで、命令の数は変わらない。増えるのは**番地の辺に来た `Int` の算術**だけである。
§1.2 の WARNING の省略（`__` になり得ない辺どうしの `Int` の和は見ない）を番地の辺には当てず、
その辺にも `cmp` と `csel` の2命令を払う——niche に落ちた数を番地へ足すと、`__` ではなく別の、
正しく見える番地が出るからである。

## 1.5 layer × リテラル型の切り分け

リテラル型は `layer` 制約とも連携する。
使用できるリテラル型は layer によって異なり、対応しない命令セットを使うとコンパイルエラーになる。

| リテラル | layer: 0 | layer: 1 | layer: 2+ | 理由 |
|---------|---------|---------|----------|------|
| `0`（整数）| ✓ | ✓ | ✓ | 整数演算は全 layer で有効 |
| `0r00`（bit列）| ✓ | ✓ | ✓ | ビット演算は全 layer で有効 |
| `0x00`（アドレス）| ✓ | ✓ | ✓ | 字面は全 layer で書ける。生の番地の算術を機械で出せるのは layer 0 だけ（type_system.md §3.6） |
| `0u00`（Unicode）| ✓ | ✓ | ✓ | バイト列として扱う（layer: 0 では文字列出力不可） |
| `0.0`（float）| ❌ | ❌ | ✓ | FPU は `layer: 2` 以上で有効 |
| SIMD ベクタ型 | ❌ | ❌ | ✓（layer: 3+） | SIMD 命令は `layer: 3` 以上 |

```sign
` layer: 0 で float を使うとコンパイルエラー
` ← layer: 2 以上でないとエラー
x : 3.14
`   「FPU が初期化されていないレイヤーで float は使用不可」
```

型リテラルとオーバーフロー挙動が `layer` と組み合わさることで、
「このコードがどのハードウェア状態で動くか」がコンパイル時に静的に保証される。

## 2. C との比較

### C の signed 整数オーバーフロー（UB）

```c
// signed int のオーバーフロー → 未定義動作（UB）
int x = INT_MAX;  // 2147483647
int y = x + 1;    // UB: コンパイラは「起きない」と仮定して最適化を壊せる

// 実際に起きたこと（GCC の最適化による CVE の原因パターン）
for (int i = 0; i <= INT_MAX; i++) {  // コンパイラ: i は INT_MAX を超えない → 無限ループ生成
    // ...
}
```

C の仕様では `signed` 整数のオーバーフローは **UB**。
コンパイラはオーバーフローが「起きない」と仮定して最適化し、
プログラムが予期しない動作をする。これが多くのセキュリティ脆弱性の原因になった。

### C の unsigned 整数オーバーフロー（定義済み）

```c
// unsigned int のオーバーフロー → ラップアラウンド（定義済み動作）
unsigned int u = UINT_MAX;  // 4294967295
unsigned int v = u + 1;     // → 0（確定、定義済み）
```

`unsigned` はラップアラウンドが規格で定義されている。

### Sign の整数オーバーフロー（すべて定義済み）

```sign
` 通常整数（0）- 64 ビットでラップアラウンド（定義済み）
x : 9223372036854775807
` → -9223372036854775807（回る。+1 なら niche に落ちて __、§1.2）
y : x + 2

` ビット列（0r）- Int なので 64 ビットでラップアラウンド（定義済み）
b : 0rFFFFFFFFFFFFFFFF
` → 0（-1 + 1、回る）
c : b + 0r01

` アドレス（0x）- Unit に収束（定義済み）
addr : 0xFFFFFFFFFFFFFFFF
` → __（Unit）← 番地空間の終端を超えた
next : addr + 1
```

**Sign には「未定義動作」が存在しない。** すべてのオーバーフローは型によって挙動が確定している。

## 3. 暗号・ハッシュでのラップアラウンド活用

`0r` リテラルはビット列（raw binary）であり、ラップアラウンドが設計上の前提：

```sign
` SHA-256 の加算（ラップアラウンド）
` 0r は Int なので + は 64 ビットで回る（32 ビットで回すには幅の前置きで幅を書く——value_representation.md、未実装）
add32 : a b ? a + b

` AES の GF(2^8) 乗算的なもの
` 0r00 型の演算は暗号実装に安全に使える
```

暗号アルゴリズムは意図的なラップアラウンドを利用するが、
Sign では `0r` 型を使うことで**意図が型に明示される**。
「なぜラップするのか」がコードを読むだけでわかる。

## 4. アドレスオーバーフローの安全性

`0x` 型（アドレス）がオーバーフローすると `__`（Unit）に収束する：

```sign
` 番地空間の終端を超える計算
arr  : 0xFFFFFFFFFFFFFF00
` → __（2^64 に届いた）
oob : arr + 256

` 器の末端を超える添字
l : 10 20 30
` → __（範囲外。器の外は読まない）
x : l ' 9
```

C での同等コードはバッファオーバーフローの典型的な原因。Sign では2つの物差しが分担する。
**番地の算術が見るのは番地空間の端**（0 以上 2^64 未満）であり、溢れた番地は `__` に収束して、
後続の番地の算術が `__` を吸収するので生き返らない（§1.3）。0x1000 の器の 1 バイト先（0x1101）は番地として
正しいので、番地の算術は止めない。**器の端を見るのは添字 `'` の範囲検査**であり、範囲外は `__` になる。
このとき機械は器の外を読まない——読む番地を `csel` で `.rodata` に置いた `__` の置き場へ差し替えてから読む
（以前は読んでから値を `__` に替えていたので、layer 0 では器のすぐ後ろの MMIO のレジスタを読みえた）。

## 5. C との対比まとめ

| 型の種類 | C の挙動 | Sign の挙動 |
|---------|---------|-----------|
| signed 整数オーバーフロー | **UB**（コンパイラが何をしてもよい） | ラップアラウンド（定義済み） |
| unsigned 整数オーバーフロー | ラップアラウンド（定義済み） | ラップアラウンド（定義済み） |
| ポインタ演算オーバーフロー | UB または実装定義 | `__`（Unit）に収束（定義済み） |
| 文字コードオーバーフロー | 実装定義 | `__`（Unit）に収束（定義済み） |

**Sign では全ケースが定義済み**。C の signed UB 問題は構造的に存在しない。
