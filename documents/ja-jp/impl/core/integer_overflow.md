# Sign 整数オーバーフロー仕様

## 概要

C における最大の設計上の欠陥のひとつが **signed 整数オーバーフローの未定義動作（UB）** である。
Sign はリテラルの型によってオーバーフロー挙動を**静的に確定させる**ことで、
この問題を構造的に排除する。

---

## 1. Sign の数値リテラル型とオーバーフロー挙動

Sign の数値リテラルはプレフィックスによって型と意味が決まる。

| リテラル | 型の意味 | Layer 2 型 | オーバーフロー挙動 | 理由 |
|---------|---------|---------|-----------------|------|
| `0` | 通常の整数（十進） | `Int` | **罠（wfi）で止まる** | ℤ を1語に入れたもの。溢れた答えは ℤ に在るが語に入らない——資源が尽きたのと同じ |
| `0r00`（`0b01` も） | ビット列（raw バイナリ）| `UInt` | **ラップアラウンド** | 環 ℤ/2^64ℤ。回ることが演算そのもの（暗号・ハッシュ等） |
| `0x00` | アドレス（ポインタ）| `Address` | **`!_`（Unit）に収束** | 不正アドレスへのアクセスを防ぐ |
| `0u00` | Unicode コードポイント | `Char` | **`!_`（Unit）に収束** | 無効コードポイントの伝播を防ぐ |

**原則——答えが域に無いのか、在るのに語に入らないのかで分ける**:
- 答えが**域に無い**（0 で割る、2^64 以上や 0 未満の番地、charset の外の文字）→ `!_`（Unit）に収束する。演算は
  「左辺が選ぶ域 → 結果 | `!_`」の射として閉じる
- 答えは **ℤ に在るが語に入らない**（`Int` の溢れ）→ 罠（wfi）で止まる。値の世界の出来事ではなく資源が
  尽きたことなので、`!_`（値としての「無い」）と混ぜない
- 値の集合が**環 ℤ/2^64ℤ**（`UInt`）→ ラップアラウンド。回ることが演算の定義なので、溢れという出来事が無い

`Int` の域は ℤ であり、64 ビットの語はそれを入れる器の大きさにすぎない（値域は `-(2^63 - 1)` 〜 `2^63 - 1`、§1.2）。
`9223372036854775807 + 2` の答えは ℤ に在るので、「無い」（`!_`）ではない。黙って回すと
`-9223372036854775807` という**正しく見える別の数**になり、`!_` にすると次の算術で単位元として消えて、やはり
別の数が残る。だから止める——置き場の溢れ（sret の容量、[`memory_management.md`](../memory/memory_management.md)）を
罠にしたのと同じ考えである。`Address` と `Char` は違う。番地の域は番地空間そのもの、文字の域は charset の
符号位置そのもの（どちらも位置）なので、2^64 以上や 0 未満の番地、域の外の符号位置は**存在しない**——答えが無いので
`!_` である。暗号やハッシュが欲しいのは回る算術そのものだが、それは ℤ ではなく ℤ/2^64ℤ の演算なので、型を
`UInt`（`0r`・`0b`）に分けて書く。表の「理由」の欄はこの区別の言い換えである。

溢れ方は代数が決める。溢れた後の `!_` を次の演算で吸収するか（§1.3）と診断の重さは、別の物差し——その誤りが
致命的か——が決める。`Address` の溢れは**間違った番地**であり、回り込んだ番地はそのまま任意の記憶を指す
（読めば隣の秘密が漏れ、書けば機械が止まる）。だから番地は `!_` を吸収し、射の無い演算を warning で見せる
（type_system.md §3.6）。文字は位置なので吸収して information、`Int` の `!_`（0 で割った商など）は単位元のまま消える。

> [!NOTE]
> 以前（2026-09-13〜10-10）ここは「その誤りが致命的か」で分けていた——`Int` の溢れは間違った数でしか
> なく、機械を殺さず情報も漏らさないので回してよく、検査の代金を払わない、と。利用者の裁定（2026-10-11）で
> 物差しを代数へ替えた：uint は回ってよい（回らないと暗号で困る）が、int は回るはずがない。同じ日に、`Int` の
> 溢れを `!_` にする案も退けた——`!_` は算術の単位元なので（operator_table.md の爆発律の囲み）、
> `9223372036854775807 + 1 + 5` が `5` という正しく見える別の数になる。致命的かどうかの物差しは、吸収と
> 診断の重さにだけ残る。

> [!NOTE]
> **alpha の現状（規則ではない）。** 解釈器（JS）も機械もまだ `Int` を 64 ビットで回し（罠へ飛ばない）、
> `0r`・`0b` を `Int` と型付けしている（`UInt` はまだ無い）。罠と `UInt` は後の片で入れる。この文書の例（§1.2・
> §2・§3）も、alpha では旧い規則で答える（細目は §1.1 の末の注）。

> [!IMPORTANT]
> **この表が `Int`・`UInt`・`Address` を別の Layer 2 型に分けている根拠である。**
> 3つとも GPR 1語だが、溢れ方が違う——`Int` は語に入らなければ罠で止まり、`UInt` は回り、`Address` は
> 域の外で `!_` になって次の演算で吸収される。溢れ方が違う以上、同じ型ではありえない——ビット幅が
> 同じことは統合の理由にならない。記法による域の決定は type_system.md §3.6 を参照。

### 1.1 機械の上で払う命令

基準はそのまま命令の数になる。見るのは**結果の型**である（整数段では左辺が域を決める
——`p + 8` は `Address`、`8 + p` は `Int`。type_system.md §3.6）。

| 結果の型 | `a + b` の命令（AArch64） | 検査 |
|---|---|---|
| `Int` | `adds x9, x9, x10` / `ccmp xzr, x9, #1, vc` / `b.vs <罠>` | 値域の外なら罠 |
| `UInt` | `add x9, x9, x10` | しない（回ることが演算） |
| `Address` | `adds x9, x9, x10` / `csel x9, <niche>, x9, hs` | 桁が上がったら `!_` |

`-` は、番地なら `subs` と `lo`（借りが出たら 0 の下へ溢れた）、`Int` なら `subs` と `vs` である。番地は分岐ではなく
条件選択で niche を置く——C の `__builtin_add_overflow` を clang -O2 で落としたものと同じ形である。`Int` は罠へ飛ぶ
分岐1つで、飛ばない側はそのまま流れる。`ccmp` は、溢れずにちょうど `INT64_MIN` に着いた結果
（`-9223372036854775807 - 1`）を同じ分岐へ寄せる——溢れていなければ `0 - x9` が溢れるか（`x9` が `INT64_MIN` か）を
見て、溢れていれば `V` を立てたままにする。`INT64_MIN` は値域の外なので、着いた結果も罠である（§1.2）。

`Int` の `*` は積の上の語を見る——`mul` / `smulh` / `cmp x12, x11, asr #63` / `ccmp xzr, x11, #1, eq` / `b.vs <罠>` で、
`mul` のほかに4命令である（上の語が下の語の符号の伸びでなければ溢れた）。冪と階乗は掛け算を重ねたもの、`n << k` は
`n × 2^k` なので、どれも語に入らなければ同じ罠へ飛ぶ。符号反転と絶対値は溢れない（値域が対称なので、§1.2）。
範囲が静的に分かって値域に収まる所（字面どうし、添字の歩み、`||xs||` で抑えた数）は検査を落とす。溢れると静的に
分かる所は罠を残し、warning で名指しする（§1.1 末）。

**右辺が `UInt`（または番地）の `Int` の和・差（`n + u`・`n - u`）は、`u` を 0 〜 2^64 − 1 の数学の値として計算し、
結果が値域の外なら同じ罠へ飛ぶ**（type_system.md §3.6「算術の格子」）。和は `n` を下回らないので
上だけ、差は `n` を上回らないので下だけを見ればよい——符号ビットを裏返して（`eor x11, x9, #0x8000000000000000`）0 〜 2^64 − 1 へずらし、
符号なしで `adds`（差は `subs`）、桁が上がったら（差は借りが出たか 0 に着いたら）罠へ飛び（`b.cs`、差は `b.ls`）、
`eor` で裏返し戻す。`add` のほかに3命令で、`Int` どうしより1つ多い。

**溢れは `!_` を生まない。** だから `!_` になり得ない辺どうし（字面、門を通った仮引数）の `Int` どうしの和・差・積は、
結果も `!_` になり得ない辺のままで、次の算術は爆発律の `cmp` と `csel`（§1.3 の表）を払わない。罠への分岐1つが、
下流の検査を増やさずに済ませている。

**`!_` になり得る辺では、罠へ飛ぶのは両辺が `!_` でないときだけである。** niche のビットのまま計算すると、
`-1 + !_` は符号つきで溢れ、`0 + !_` は `INT64_MIN` に着き、`3 * !_` は積が語に入らないので、どれも罠へ飛ぶ——
爆発律ではそれぞれ `-1`・`0`・`3` である。だから罠の道の入口で辺が `!_` か（niche か、`UInt` の辺なら印か）を見直し、
そうなら残った辺を答えにして戻る。両辺とも `!_`（`!_ + !_`）なら残る辺が無いので `!_` のままである。見直しは飛んだ
側にだけ置くので、飛ばない側の命令は増えない（§1.3 の `cmp` と `csel` はそのまま）。`+` `-` `*`・冪・`<<` と、
`Int` のビット演算（§1.2）の全部に同じ見直しが効く。

**残る辺の型が左辺と違っても、域は左辺の型が決める。** `!_` は値であって型ではないので（[`compiler_pipeline.md`](compiler_pipeline.md)
§3）、`!_` になった `Int` に `UInt` や番地が残る形（`(n / d) + u`）も `Int` の域で答える——残った辺は上の段と同じく
数学の値として読み、値域に入ればその数、入らなければ罠である（`!_ + 0r5` は `5`、`!_ + 0rFFFFFFFFFFFFFFFF` は罠）。
§1.3 の `csel` がビットのまま選ぶと、2^63 以上の `u` が負の数か niche に化ける（`!_ + 0rFFFFFFFFFFFFFFFF` が `-1`）
ので、選ぶ側に `u` の最上位のビットを見る1命令（`tbnz x10, #63, <罠>`）を足す。`Int` どうしの辺には要らない。
（operator_table.md の「左辺が `!_` なら相手の型」は、左辺の**型**が `Unit` のとき——字面の `!_` など、同じ囲みの
「`Unit ⊕ T → T`」——の話である。）

**番地に足す数は負でもよい**（`p + -4` は `p - 4` と同じ番地）。そのとき桁上がりだけでは
判定できない——負の数を足して正しく戻る番地は、符号なしで見ると必ず桁が上がるからである。
見たいのは数学の値 `p + n`（`p` は符号なし、`n` は符号あり）が `0` 以上 `2^64` 未満に
収まるかで、それは**両辺をそれぞれの符号で1語伸ばしたときの上の語が 0 か**と同じである：

```
asr  x13, x10, #63          // n の上の語（0 か -1）。符号なしの辺の上の語は xzr
adds x9, x9, x10            // 下の語
adcs x13, xzr, x13          // 上の語 = p の上の語 + n の上の語 + 桁上がり（`-` は sbcs）
csel x9, <niche>, x9, ne    // 上の語が 0 でなければ溢れた
```

両辺とも符号なし（足す数が `UInt`——`p + 0r18`——か、非負の `Int` の定数）なら上の語は桁上がりそのものなので、`asr` と
`adcs` が畳まれて表の2命令になる（どちらも niche を置く `movz` は数えていない）。十進の `18446744073709551615` は
`Int` の域の外なので字面の時点でコンパイルエラーであり（§1.1 末）、`-1` のずらしにはならない。`UInt` の大きな値も
負のずらしにはならない——`p + 0rFFFFFFFFFFFFFFFC` は `p + (2^64 - 4)` で、`p` が 4 以上なら溢れて `!_` である（戻すなら `p - 0r4` か `p + -4`）。
C の `__builtin_add_overflow(u64, i64)` を clang -O2 で落とすと、同じ判定に8命令を使う。

**除算は溢れない（商の大きさは被除数を超えず、`Int` の値域は対称なので `INT64_MIN / -1` の形も無い）が、割る数を見る。**
`Int`・`UInt` は 0 で割ると `!_`（下の段）、番地の域では 0 以下で割ると `!_` である（左辺が番地のとき。商も番地——type_system.md §3.6「番地の域の射」）。
正の数で割った商は被除数を超えないので、上の物差し（0 以上 2^64 未満か）では何も払わない。見るのは割る数が
0 以下かどうかで、これは溢れではなく、枠の大きさとして意味があるかの規則である。

| 演算 | 命令（AArch64） | 検査 |
|---|---|---|
| `p / q`（`q` は番地） | `udiv` / `cmp` / `csel …, eq` | 0 で割ったら `!_`（番地は負にならない） |
| `p / n`（`n` は `Int`） | `udiv` / `cmp` / `csel …, le` | 0 以下で割ったら `!_` |
| `p / u`（`u` は `UInt`） | `udiv` / `cmp` / `csel …, eq` | 0 で割ったら `!_`（`UInt` は負にならない） |
| `p / 4096`（正の字面） | `udiv` | しない（商は被除数を超えないので溢れない） |

`udiv` は負の数 `-n` を 2^64 − n という大きな符号なしの数と読むので、負の数で割った商は 0 か 1（被除数が
2^64 − n 以上のときだけ 1）になり、0 で割れば 0 を返す。どれも意味の無い小さな番地を黙って出す形なので、
まとめて `!_` にする。剰余 `p % a` も同じ規則に従う——命令のままでは 0 で割った剰余が被除数なので、見なければ揃えの形
`p - (p % a)` が 0 番地になる（機械はまだ `%` を出さない）。以前は負の数で割ったときだけ絶対値で割ってから
商が 0 かを見ていた（`cneg`・`ccmp` を含む形）。

**番地の域に、掛け算・冪・左シフト・階乗の射は無い**（type_system.md §3.6）。`p * k` は溢れを見る前に `!_` で
あり、機械は掛け算の命令を出さずに niche を置く。以前はここで積の上の語を `umulh` で見て、溢れなければ
番地を返していた。C でもポインタは `*` `/` `%` の被演算子になれない（C17 6.5.5）。

**整数を 0 で割ると `!_` である**（`Int` と `UInt`。商も剰余も。文字には除算の射が無い——[`type_system.md`](../type/type_system.md) §3.6「文字の域の射」）。
ℤ にも ℤ/2^64ℤ にも 0 の逆元が無いので、`a / 0` は域の中に答えを持たない——溢れ（答えは在るが語に入らない、罠）
とは違い、答えが無いので `!_` である。Rust の `checked_div` が `None` を返すのと同じ形で、`|` で受けられる
（`(a / b) | 0`）。実行時に止めはしない（罠も throw の見張りも入れない）。`UInt` を負の数 `-n` で割っても `!_` である
——ビットで読むと 2^64 − n で割ることになり、商は 0 か 1 を黙って出す（番地の割り算が `!_` にした形と同じ）。

命令は、`Int` なら `sdiv` の前後に `cmp` と `csel …, eq` の2つで、niche を置く。`UInt` は語の中に niche を持たない
ので（§1.2 の NOTE）、`cmp` の答えをそのまま `!_` の印にする——すぐ `|`・`&`・門で受ければ印は条件フラグのまま消え、
名前へ置く・渡すなら `cset` で2語目に移す（`udiv` は 0 で割ると 0 を返すので、値の語には手を入れない。割る数が
`Int` なら `eq` が `le` になり、負の数も同じ印へ寄る）。`Int` を `UInt` で割るときは、`u` を 0 〜 2^64 − 1 の数学の値
として読む——`u` が 2^63 − 1 を超えれば `|n|` より大きいので、商は 0、剰余は被除数である。
商も剰余も絶対値が被除数を超えないので、値域に必ず入り、罠は要らない。命令は `sdiv`（剰余は `msub` も）の後、
`cmp` の答え（`lt`——`u` の上のビットが立っている）で `csel` を1つ足し、商なら 0、剰余なら被除数を選ぶ。`Int`
どうしより1命令多い。割る数が 0 でないと分かる所（0 以外の字面、門で確かめた
仮引数）では、0 の検査を落とす。割る数が字面の 0（`0`・`0r0`・`0b0`）なら、Pass 3b が information で名指しする。

**`Float` は IEEE 754 のままである**（`1.0 / 0.0` は `+∞`、`0.0 / 0.0` と `x % 0.0` は NaN）。拡張実数の中の
正しい答えであり、FPU がそう答える。**番地の域では 0 以下で割ると `!_` である**（上の表）。0 番地は layer 0
では読める記憶なので、黙って返すと致命的になる。

> [!NOTE]
> 以前（2026-09-13 に仮で入り、09-30 に確定。10-10 まで）ここは「商は 0、剰余は被除数」と定めていた——
> `0⁻¹ = 0` と置く草原（meadow）の読みで、AArch64 の `sdiv`/`udiv`/`msub` がそう答え、除法の等式
> `a = (a/b)*b + a%b` が `b = 0` でも成り立つ。NOTE はそれを今の最適化に向いた形と書いていた。利用者の裁定
> （2026-10-11）で、型ごとにその代数の答えへ替えた。除法の等式で書き換える最適化は、割る数が 0 でないと
> 分かる所でだけ効く。

> [!NOTE]
> **未決**：`Float` の NaN（演算を吸収する）と `!_`（単位元）の繋ぎ方。`(0.0 / 0.0) + 1.0` は NaN のままだが、
> `!_ + 1.0` は `1.0` である。`Float` を入れる片で決める。

**番地の規則の n 番目も番地の算術である。** `[p ~+ k] ' i` はロードではなく `start + i × step` なので、
同じ物差しで `mul` / `smulh` / `adds` / `adcs` / `csel` を払う（積 `i × step` は添字の側で作る数であり、
番地を掛けてはいない——`p ± n` と同じ「ずらす」射である）。**検査は作る所に置く**——読む所（`@`）だけで
見ると、作った値を名前へ置いて別の所で `@` したとき、回った番地は正しい番地と同じビットなので区別できない。

**2^64 以上の番地の字面は `!_` である**（`0x10000000000000010`）。そういう番地は存在しない——
`0x8000000000000000` と同じく、`!_` の別の綴りである。**十進の字面は、`Int` の値域（`-(2^63 - 1)` 〜
`2^63 - 1`）の外ならコンパイルエラーである**（`9223372036854775808`・`-9223372036854775808`・
`18446744073709551617`。エラーはその字面を名指しする）。そういう数は ℤ に在るが `Int` の語に入らない——実行時なら
罠の類（§1）で、しかも字面には語に置く表現そのものが無い（どの 64 ビットもその数ではない）ので、組めない。`0r`・`0b` の字面は、値が 2^64 未満なら `UInt` の
値であり（`0rFFFFFFFFFFFFFFFF` は 2^64 − 1。先頭の 0 は数えないので `0r00000000000000001` は 1）、2^64 以上なら同じく
コンパイルエラーである。どこに置いても（添字・切り出しの端・書き込み先）同じ読み方をする。

**定数を畳んで溢れると分かる式は、字面とは違う**（`9223372036854775807 + 1`、§2 の `y : x + 2`）。式には表現が
ある——罠への分岐として組める——うえ、その式を通る枝が走るかは静的に分からない。だから組んで実行時は罠のままにし、
warning でその式を名指しする。危険は書けて、気付ける。

> [!NOTE]
> **alpha の現状（規則ではない）。** 解釈器も機械も、まだ §1.1 の旧い規則で答える——`Int` の `+`・`-`・`*` は
> 溢れを見ずに 64 ビットで回り（機械は `add`）、罠へ飛ばない。域の外の十進の字面も断らずに 64 ビットで回す
> （`18446744073709551617` は 1）。溢れると分かる定数の式の warning も出ない。`0r`・`0b` は `Int` なので
> `p + 0rFFFFFFFFFFFFFFF8` は `p - 8` になり、整数を 0 で割ると商 0・剰余は被除数で、字面の 0 の information も
> 出ない。後の片で入れる。

### 1.2 `INT64_MIN` は `Int` の値ではない

GPR 1語の `!_` は `0x8000000000000000` である（value_representation.md §3.5）。`Int` として
読むとそれは `INT64_MIN` なので、**`Int` の値域は `-(2^63 - 1)` 〜 `2^63 - 1` であり、
`INT64_MIN` は値ではない**。値域は 0 を挟んで対称なので、**符号反転と絶対値は溢れない**（`-x` も `|x|` も
域の中へ戻る。niche は反転しても niche）。値域の外へ出る結果は、溢れても、溢れずにちょうど `INT64_MIN` へ着いても
罠である（§1.1）——どちらも答えは ℤ に在り、`Int` の語に入らない：

```sign
` → 罠（ℤ では 9223372036854775808。値域の外）
a : 9223372036854775807 + 1
` → 罠（溢れてはいないが、着いた先が niche。ℤ では -9223372036854775808）
c : -9223372036854775807 - 1
` → コンパイルエラー（字面が値域の外、§1.1 末）
b : -9223372036854775808
```

だから `Int` の算術（和・差・積・冪・階乗・`<<`）が niche を作ることは無い。右辺が `UInt` や番地でも、数学の値で
計算して値域を見る（§1.1）。`!_` になり得る辺の算術は、罠の道の入口の見直しで爆発律の答えへ
戻る（§1.1。両辺とも `!_` なら `!_` を運ぶだけ）。`Int` の `!_` は、答えが無かった印（0 で割った、比較が偽、
添字が範囲の外）だけである。解釈器は ℤ で計算してから値域を見る——溢れも niche への着地も、結果の絶対値が
`2^63 - 1` を超えるかという1つの判定で、超えたら止まる（罠）。`Address` の `0x8000000000000000` も同じビット
なので `!_` である——非正準領域にあり、そもそも番地になりえない。§1.1 の検査を通った結果でも、そこへ落ちれば
`!_` になる。

ビット演算は別の道で同じ所へ着く。`&&`・`||`・`;;`・`!!` は被演算子を 64 ビットのビット列として読み、結果は左辺の
型を取る（type_system.md §3.6「算術の格子」）。答えはビット列なので溢れという出来事は無いが、左辺が `Int` なら結果の
ビットは `Int` として読まれる。ちょうど niche なら、その値 −2^63 は ℤ に在って `Int` の値域に入らないので、算術と
同じく罠である（`!!9223372036854775807` は罠）。代金は `cmp x9, #1` / `b.vs <罠>` の2命令——
`x9 - 1` が符号つきで溢れるのは `x9` が niche のときだけである。`!_` になり得る辺のビット演算（`n && !_`）は、
§1.1 の罠の道の入口の見直しで爆発律の答えへ戻る。左辺が `Address` なら着いたビットはそのまま `!_` で（番地に
なりえない、上の段）、命令を足さない。左辺が `UInt` なら niche も値なので値のままである。

> [!NOTE]
> 以前ここには、解釈器と機械が niche で割れるという WARNING があった。機械は `Int` の溢れを見なかったので、
> `!_` になり得ない辺どうし（リテラル、門を通った仮引数）の和がちょうど niche に落ちると、その niche を数として
> 次の算術へ渡していた——`f : a b c ? a + b + c` に `9223372036854775807 1 5` を渡すと、解釈器は `!_ + 5` で `5`、
> 機械は `INT64_MIN + 5`。2026-10-11 の裁定で `Int` の溢れは罠になったので、この割れは規則の上では無くなった。
> 両エンジンとも `9223372036854775807 + 1` で止まる——解釈器の `5` も、溢れた和が単位元として消えた、正しく
> 見える別の数だった。alpha の機械はまだ `add` で回すので、割れは alpha に残っている。

> [!NOTE]
> **`UInt` は niche を持たない。** `UInt` は 2^64 個のビットを全部値に使う（環 ℤ/2^64ℤ）ので、
> `0x8000000000000000` を外すと環が1点で破れ、回った先がちょうどそこへ落ちた計算（暗号・ハッシュ）が黙って
> `!_` になる。だから `UInt` の `!_` は語の外で運ぶ——`!_` になりうる値だけを、値の語と印の対で持つ
> （value_representation.md §3.5、type_system.md §2「Layer 2 の統一原理」の例外）。環の演算は `!_` を作らない。

### 1.3 溢れた番地は、次の算術で生き返らない

算術の `!_` は普通、両側で単位元である（爆発律——`!_ + 3` は `3`）。それを番地に当てると、§1.1 で
`!_` にした番地が次の演算で生き返る。`(p + n) - m` で `p + n` が溢れても `m` が残り、番地として
使われる。だから**結果の型が `Address` の算術では、`!_` は両側で吸収する**（`!_ + k` も `p + !_` も
`!_`）。規則と、左右対称である理由は [`operator_table.md`](../syntax/operator_table.md) の
「算術の `!_` は両側とも恒等射である（爆発律）」の欄が持つ。

機械の上では、爆発律の `csel` が選ぶ先を「残った辺」から niche へ替えるだけである：

| 結果の型 | `a + b` で `b` が `!_` になり得るとき |
|---|---|
| `Int` | `cmp x10, x12` / `csel x11, x9, x11, eq`（残った `a`） |
| `Address` | `cmp x10, x12` / `csel x11, x12, x11, eq`（`!_`） |

選ぶ先が変わるだけで、命令の数は変わらない。`Int` の和・差・積は溢れたら罠で止まり、niche に着かない（§1.2）
ので、`!_` になり得ない辺どうしの `Int` の算術は、番地の辺に来ても `!_` になり得ない辺のままである——見るのは、
0 で割った商や偽になり得る比較のように `!_` になり得る辺だけである。その辺の算術も、罠へ飛ぶのは両辺が `!_` で
ないときだけで、飛んだら罠の道の入口で辺を見直して残った辺へ戻る（§1.1）ので、上の表の `csel` が選ぶ答えと
食い違わない。`UInt` の辺も環の演算なら `!_` になり得ず、`!_` になり得る辺では niche と比べる代わりに印を見る。
以前は `Int` が回って niche に落ちえたので、番地の辺に来た `Int` の算術にだけ `cmp` と `csel` の2命令を払う例外を
置いていた（`p - (a + b)` に `0x1000 9223372036854775807 1` を渡すと、機械は `0x8000000000001000` を返していた
——`p - INT64_MIN` は溢れていない）。

> [!NOTE]
> **alpha の現状（規則ではない）。** alpha の機械はまだ `Int` を回すので、番地の辺の2命令は残っている。外すのは
> 罠を入れる片と同時である（規則ではなく順序）。先に外すと、`p - (a + b)` の `0x8000000000001000` がまた出る。

## 1.5 layer × リテラル型の切り分け

リテラル型は `layer` 制約とも連携する。
使用できるリテラル型は layer によって異なり、対応しない命令セットを使うとコンパイルエラーになる。

| リテラル | layer: 0 | layer: 1 | layer: 2+ | 理由 |
|---------|---------|---------|----------|------|
| `0`（整数）| ✓ | ✓ | ✓ | 整数演算は全 layer で有効 |
| `0r00`（bit列、`UInt`）| ✓ | ✓ | ✓ | 回る算術とビット演算は全 layer で有効 |
| `0x00`（アドレス）| ✓ | ✓ | ✓ | 字面は全 layer で書ける。生の番地の算術を機械で出せるのは layer 0 だけ（type_system.md §3.6） |
| `0u00`（Unicode）| ✓ | ✓ | ✓ | バイト列として扱う（layer: 0 では文字列出力不可） |
| `0.0`（float）| ❌ | ❌ | ✓ | FPU は `layer: 2` 以上で有効 |
| SIMD ベクタ型 | ❌ | ❌ | ✓（layer: 3+） | SIMD 命令は `layer: 3` 以上 |

```sign
` layer: 0 で float を使うとコンパイルエラー
` ← layer: 2 以上でないとエラー
x : 3.14
`   「FPU が初期化されていないレイヤーで float は使用不可」
```

型リテラルとオーバーフロー挙動が `layer` と組み合わさることで、
「このコードがどのハードウェア状態で動くか」がコンパイル時に静的に保証される。

## 2. C との比較

### C の signed 整数オーバーフロー（UB）

```c
// signed int のオーバーフロー → 未定義動作（UB）
int x = INT_MAX;  // 2147483647
int y = x + 1;    // UB: コンパイラは「起きない」と仮定して最適化を壊せる

// 実際に起きたこと（GCC の最適化による CVE の原因パターン）
for (int i = 0; i <= INT_MAX; i++) {  // コンパイラ: i は INT_MAX を超えない → 無限ループ生成
    // ...
}
```

C の仕様では `signed` 整数のオーバーフローは **UB**。
コンパイラはオーバーフローが「起きない」と仮定して最適化し、
プログラムが予期しない動作をする。これが多くのセキュリティ脆弱性の原因になった。

### C の unsigned 整数オーバーフロー（定義済み）

```c
// unsigned int のオーバーフロー → ラップアラウンド（定義済み動作）
unsigned int u = UINT_MAX;  // 4294967295
unsigned int v = u + 1;     // → 0（確定、定義済み）
```

`unsigned` はラップアラウンドが規格で定義されている。

### Sign の整数オーバーフロー（すべて定義済み）

```sign
` 通常整数（0）- 値域の外へ出たら罠で止まる（定義済み）
x : 9223372036854775807
` → 罠（ℤ では 9223372036854775809。Int の語に入らない）
y : x + 2

` ビット列（0r）- UInt なので 2^64 で回る（定義済み）
b : 0rFFFFFFFFFFFFFFFF
` → 0（2^64 - 1 + 1、回る）
c : b + 0r01

` アドレス（0x）- Unit に収束（定義済み）
addr : 0xFFFFFFFFFFFFFFFF
` → !_（Unit）← 番地空間の終端を超えた
next : addr + 1
```

**Sign には「未定義動作」が存在しない。** すべてのオーバーフローは型によって挙動が確定している。

## 3. 暗号・ハッシュでのラップアラウンド活用

`0r` リテラルはビット列（raw binary）であり、ラップアラウンドが設計上の前提：

```sign
` SHA-256 の加算（ラップアラウンド）
` 0r は UInt なので + は 2^64 で回る（32 ビットで回すには幅の前置きで幅を書く——value_representation.md、未実装）
add32 : a b ? a + b

` AES の GF(2^8) 乗算的なもの
` 0r00 型の演算は暗号実装に安全に使える
```

暗号アルゴリズムは意図的なラップアラウンドを利用するが、
Sign では `0r` 型を使うことで**意図が型に明示される**。
「なぜラップするのか」がコードを読むだけでわかる。

逆に、十進で書いた数は `Int` なので回らない。始まりの値が 2^63 − 1 を超えるハッシュは、十進では字面の時点で
コンパイルエラーになる（§1.1 末）——回したい数は `0r` で書く：

```sign
` FNV-1a（64 ビット）。十進の 14695981039346656037 は Int の値域の外
fnv_basis : 0rCBF29CE484222325
fnv_prime : 0r100000001B3
```

## 4. アドレスオーバーフローの安全性

`0x` 型（アドレス）がオーバーフローすると `!_`（Unit）に収束する：

```sign
` 番地空間の終端を超える計算
arr  : 0xFFFFFFFFFFFFFF00
` → !_（2^64 に届いた）
oob : arr + 256

` 器の末端を超える添字
l : 10 20 30
` → !_（範囲外。器の外は読まない）
x : l ' 9
```

C での同等コードはバッファオーバーフローの典型的な原因。Sign では2つの物差しが分担する。
**番地の算術が見るのは番地空間の端**（0 以上 2^64 未満）であり、溢れた番地は `!_` に収束して、
後続の番地の算術が `!_` を吸収するので生き返らない（§1.3）。0x1000 の器の 1 バイト先（0x1101）は番地として
正しいので、番地の算術は止めない。**器の端を見るのは添字 `'` の範囲検査**であり、範囲外は `!_` になる。
このとき機械は器の外を読まない——読む番地を `csel` で `.rodata` に置いた `!_` の置き場へ差し替えてから読む
（以前は読んでから値を `!_` に替えていたので、layer 0 では器のすぐ後ろの MMIO のレジスタを読みえた）。

## 5. C との対比まとめ

| 型の種類 | C の挙動 | Sign の挙動 |
|---------|---------|-----------|
| signed 整数オーバーフロー | **UB**（コンパイラが何をしてもよい） | 罠（wfi）で止まる（定義済み、`Int`） |
| unsigned 整数オーバーフロー | ラップアラウンド（定義済み） | ラップアラウンド（定義済み、`UInt`） |
| 整数の 0 除算 | **UB** | `!_`（Unit）に収束（定義済み、`Int`・`UInt`） |
| ポインタ演算オーバーフロー | UB または実装定義 | `!_`（Unit）に収束（定義済み） |
| 文字コードオーバーフロー | 実装定義 | `!_`（Unit）に収束（定義済み） |

**Sign では全ケースが定義済み**。C の signed UB 問題は構造的に存在しない。
