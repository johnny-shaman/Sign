# System Semantics (Sign言語 システム記述仕様)

## 概要
Sign言語は「高水準な関数型記述（アプリケーション層）」と「低水準なプリミティブ操作（システム層）」を同一の構文でサポートします。
本ドキュメントでは、特にシステム層（コンパイラ、アロケータ、ドライバ等）の実装において使用される**明示的なメモリ操作**について定義します。

> [!NOTE]
> **層ごとに何が使えるかは [`layer_relations.md`](../layer_relations.md) に実測表がある。**
> この文書が「アプリケーション層ではポインタの加減算を禁止する」と定めているのは、そこで
> **上限の門番**として実装されている——生の番地の算術は `layer: 0`（MMIO を扱う層）だけ、
> 生の番地への直接書き込みは `layer: 0〜1` までである。
>
> 層は機能を積み上げるだけではない。**上へ行くほど禁じられるものがある**、という一点が
> 両方の文書に共通している。

## アプリケーション層とシステム層の違い

### アプリケーション層 (ユーザーコード)
*   **メモリ管理**: 自動（コンパイラ/GCが隠蔽）。`alloc` などの直接呼び出しは行わない。
*   **値の扱い**: 参照渡し・値渡しはコンテキスト（関数適用）によって自動的に最適化される。
*   **アドレスの直接操作**: `0x00 # 1` `@0x00` のような直接的なメモリアクセスが可能。
*   **禁止事項**: ポインタのインクリメント、デクリメント。

### システム層 (関数ブロック内部)
*   **メモリ管理**: 明示的。`alloc` 相当のロジックを構成可能。
*   **明示的な参照操作**: `$` (Address Of), `@` (Deref), `#` (Store) を使用して、物理的なメモリ配置やポインタの受け渡しを制御する。

## 明示的な参照操作 (Explicit References)

システム記述（特にアロケータや高効率なライブラリ機能の実装）において、値(Value)と参照(Reference/Address)を区別するために以下の演算子を使用します。

### 1. `$` Reference (Address Of)
変数の「値」ではなく「場所（アドレス）」を取得します。
主に関数へ「参照渡し」を行いたい場合や、変数のスロットそのものを操作したい場合に使用します。

```text
` 関数オブジェクトを値コピーせず、参照として渡す
map $[* 2] ...
` heap_ptr変数そのもの（スロット）に書き込む
$heap_ptr # ...
```

### 2. `@` Dereference (Load)
参照（アドレス）から実体（値）を取り出します。
参照渡しされた引数を利用する際に使用します。

```text
map : f ... ?
` 参照 f から関数実体を取り出して適用
	@f ...
```

### 3. `#` Store (Update)
参照先（アドレス）に値を書き込みます。
変数の更新（再代入）や、ヒープメモリへの書き込みに使用します。
左辺は必ずアドレス（L-Value）でなければなりません。

```sign
` heap_ptr変数のアドレス($)を取得し、そこに next を書き込む
$heap_ptr # next
```

## コンパイラの挙動 (Proto A5)

*   **識別子 (Identifier)**: 常に **R-Value (Value)** として評価されます。
    *   `x` -> `ldr x0, [x_addr]`
*   **代入文脈 (# の左辺)**: 特別扱いはしません。左辺はアドレスとして評価される式でなければなりません。
    *   `$x # y` -> `adr x0, x_addr; ... str y, [x0]`
        `x`のアドレスを取得し、その指す先へ`y`を書き込む（`*x = y`）
*   **明示的な操作**: `$` や `@` を全面的に使用し、マジック（暗黙の型変換）を排除します。

## 参照演算におけるリテラル（`0x00`, `0u00`, `__`）の振る舞い

型システムと値表現仕様（`Value_Representation_ja-jp.md`）に基づき、これらのリテラルに対する参照操作は明確に区別されます。

### 1. `$` (Address Of) の挙動

`$` は定数リテラルに対しても適用可能であり、コンパイラが静的に確保した `.rodata` 領域等のアドレス（Read-Only）を返します。

*   **`$0x00`**: コンパイラが確保した **Address型の値 `0x00`** に対応する rodata スロットのアドレスを返す。
*   **`$0u00`**: Char型の **niche スロット**（U+0000 に対応するビットパターン）のアドレスを返す。U+0000 は Char型の値域から除外されており（`Value_Representation_ja-jp.md` §3 参照）、このビットパターンは `__`（Unit）として扱われる。物理的な MUTF-8 バイト列は一切使用しない。
*   **`$__`**: `__`（Unit）を返す。

これらはすべて異なる有効なアドレスであり、物理番地 `0x00` を指すわけではありません。
（※これらに `#` で書き込もうとした場合は致命的エラーとなります）

### 2. `@` (Dereference) の挙動

`@` は右辺をアドレス（L-Value）として解釈し、そのメモリを読み取ります。

*   **`@0x00`**: Int型の `0` を「アドレス」として解釈し、**番地 0x00 から値を読み取る**。
*   **`@0u00`**: Char型の値をアドレスとして解釈しようとするため、**型エラー** または **Unit 伝播により即座に `__`** に崩壊する。
*   **`@__`**: 左辺が Unit であるため、式全体が即座に **`__`（吸収元）** に崩壊する。

## ターゲット層 (Layer) による物理アドレス参照の差異

`@0x00` や `0x00 # expr` のような「Int値を用いた直接メモリアクセス」の挙動は、実行ターゲットの `layer`（`Option_MS_Spec_ja-jp.md` 参照）に依存します。

### Layer 0 (Baremetal / MCU / Kernel)
*   **`@0x00`**: 物理メモリアドレス `0x0000` を直接読み取ります（ARM のリセットベクタ、割り込みベクタテーブル等）。
*   **`0x00 # expr`**: 物理番地 0 への直接書き込みを実行します。

### Layer 1〜4 (OS上のユーザ空間 / VM / JS)
*   **`@0x00`**: 仮想アドレス `0x00` へのアクセスとなり、大半の OS では **Segmentation Fault**（Null Pointer Dereference）を発生させます。
*   システム層記述として例外ハンドラでトラップされるか、プロセスが即座に終了します。
*   安全性を重視するレイヤーでは、このような未保護のメモリアクセスは事前にバリデーションされるか、意図的なクラッシュ（フェイルファスト）として機能します。

## 非同期の意味論：Sign に `wait` が存在しない理由

> [!IMPORTANT]
> **Sign には「待つ」ための専用命令・専用キーワードが存在しない。これは機能の欠落ではなく、
> 待機が動詞ではなく既存の演算子と型に分解されているためである。**

C は `wait()` のような**動詞**を必要とする。操作の発行と完了の待機が別々の行為だからである。
Sign の IO は Pull 型であり、**消費すること自体が待つことと同一**であるため、両者を分ける
理由が最初から無い。

「関数は動詞と同じ」という Sign の出発点を徹底すると、**待機は動詞ではなく型として現れる**。

### 待機を担う4つの機構

| 機構 | 何が「待つ」のか |
|---|---|
| **前置 `~`（持ち上げ）** | 余積を一回**待機状態に入れる**（サスペンド）。後置 `~`（展開）が逆操作でレジュームにあたる（[`list_model.md` §3.2](../type/list_model.md)） |
| **`Iterator(T)` の消費** | Pull 型のストリームは「値は消費側が要求したタイミングでのみ生成される」（[`list_model.md` §2.3](../type/list_model.md)）。**引っ張る行為が待機そのもの** |
| **`__` ＋ 完全性公理 ＋ TCO** | MMIO 読み出しはノンブロッキングで、準備できていなければ `__` を返す。`\|` によるフォールバックの末尾再帰が、TCO によって実機のループ命令へ落ちる |
| **`asm_volatile`** | `WFI` / `WFE` のような省電力待機命令。代数的な意味を持たない純粋なハードウェア命令であるため、原理1 が定める逃げ道に置く |

### ポーリングの標準形

```sign
` STATUS が立つまで待ち、立ったら DATA を読む
read : ?
	@STATUS & @DATA | read __
```

`@STATUS` が `__`（未準備）なら `&` が短絡して全体が `__` になり、`|` が右辺の
`read __` へ落ちて自分自身を呼び直す。この再帰は末尾位置にあるため
[`tco.md`](tco.md) のトランポリンによってスタックを消費せず、実機では
`while (!ready);` と同じ命令列になる。

**3つが揃って初めて `wait` が不要になっている**点に注意されたい——
`__` が「まだ値が無い」を表し、完全性公理が「無いなら本体に入らない」を保証し、
TCO がそれをループに変える。どれか一つでも欠けると明示的な待機命令が必要になる。

### 待機は型に現れる

[`type_system.md` §2](../type/type_system.md#layer-2-atom-内部型atom-subtype) の Layer 2 型のうち、
以下の2つが待機と直接対応する。

| 型 | 待機との関係 |
|---|---|
| `Iterator(T)` | **まだ生成されていない値の列**。消費（Pull）した時点で初めて値が存在する |
| `Implicit(T)` | **場所**。値そのものではなく「そこに T が現れる」という参照であり、外界が書き込むまで内容は確定しない |

割り込みや DMA を伴う IO で、音声バッファとフレームバッファのように**複数の場所を同時に
生きた状態で保持する**必要がある場合、Pull 型のカーソルである `Iterator` では足りず
`Implicit` が要る。これが `Implicit(T)` を Layer 2 の型として持つ理由であり、
[`0_design_principles.md`](../0_design_principles.md) 原理3 が
「裸の `~xs`（stream、pull型で同時アクセス不可能）」と
「`[x ~xs]`（参照渡し、複数アドレスへの同時アクセスが可能）」を並べている理由でもある。

> [!NOTE]
> 本節は「待機の意味論」を1箇所にまとめたものであり、新しい機能を定義していない。
> 個々の規則は `list_model.md`（前置/後置 `~`、Pull 型イテレータ）、
> `type_system.md`（`Iterator(T)` / `Implicit(T)`）、`tco.md`（末尾再帰のループ化）、
> `0_design_principles.md` 原理1（`asm_volatile`）・原理3（stream と参照渡しの区別）に
> 既に分散している。
