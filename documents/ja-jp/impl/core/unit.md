## 0. 実装に直結する重要性質（クイックリファレンス）

### 0.1 未定義識別子のUnit収束（予約語の完全排除）

Sign言語には `null`, `nil`, `false` などの予約語は存在しません。
**「現在スコープにおいて定義されていない識別子はすべて `__`（無）として評価される」**というコア仕様が存在します。

#### 仮想キーワードとしての活用
この仕様により、ユーザーは任意の英単語やUnicode記号をゼロコストの「仮想キーワード」として利用できます。
```sign
@lazy tick
@iterator next
```
未定義の識別子（`tick`, `next`）は安全に `__` として評価されるため、可読性を高めるための自然言語的なマーカーとして機能します。

この収束は診断上 **information**（非ブロッキング、実行を止めない）として扱う。仮想キーワードとしての
意図的な利用（上記の`tick`/`next`）を委縮させないため、warning/cautionへは格上げしない。ただし
末尾位置での未定義識別子呼び出しは、TCOの前提が崩れる実害があるため例外的に **warning** とする
（[`tco.md`](tco.md) §3参照）。

### 0.2 UnitとFalseの同型性と短絡評価

言語組み込みの論理積（`&`）および論理和（`|`）は短絡評価（Short-circuit）を行います。

```sign
 appendの終了条件と再帰ステップ
append : [x ~xs] [y ~ys] ?
	xs & x (append xs (y ys)) | @x y ys
```
- `xs` が空リストではない（真）場合、後続の再帰ステップが評価される
- `xs` が空リスト（`__`／偽）の場合、`|` の右辺（終了条件）が評価される

### 0.3 演算子の安全な無効化

```sign
[+] : ~x ? __
```
可変長引数 `~x` によってオペランドをすべて吸収し、明示的に `__` を返すことで、演算子が用いられた式全体を安全に `__` に崩壊させます。

### 0.4 `$__`、`@__` の挙動：Unit はすべての演算子を吸収する

`$`（アドレス取得）および `@`（デリファレンス）も、他の演算子と同様に **Unit を吸収する**。

```sign
` $ を Unit に適用しても Unit（吸収元）
$__   = __
` @ を Unit に適用しても Unit（吸収元）
@__   = __
` 上2つの合成として自明
@$__ = __
```

**帰結：`$__` という特別な値は存在しない。**

- Unit を「アドレスとして持ち歩く」必要はなく、`__` をそのまま使えばよい
- 遅延ストリームの終端も `__` を返せば十分。`@__` = `__` によって消費側に伝わる
- `$__` は `0u00`（コードポイント 0）に対応する定数として型システム上定義されるが、  
  その値は `__` と同値であり、ランタイムに独立した実体を持たない

```text
` Before（誤った想定）:
stream : @lazy tick ... | $__   ← 終端に「非Unit値」が必要という誤解

` After（正しい設計）:
stream : @lazy tick ... | __    ← __ を返せば @ が __ を受け取るので等価
```

## 1. イントロダクション

> [!IMPORTANT]
> **`__` は Sign を圏として定義するために必要な零対象（Zero Object）である。**
> 以下の全ての振る舞いはこの一事実から導出される。

零対象（Zero Object）とは、**初対象（Initial Object）と終対象（Terminal Object）が一致した対象**です。

$$\__ = \text{Initial Object} \cong \text{Terminal Object}$$

この一致により、`__` はあらゆる演算に対して以下の双対的振る舞いを同時に持ちます。

| 対象としての役割 | 演算 | 振る舞い |
|:---:|:---:|---|
| **終対象**（吸収） | `&`、比較、関数の入口（`f __`）、**結果が `Address` の算術** | `__ op x = __` |
| **初対象**（単位元） | `|`, `;`, ` `, `,`、**算術 `+ - * / % ^`（爆発律）** | `__ op x = x` |

> [!NOTE]
> 算術がどちらの行に乗るかは**型が決める**。`A × A → A` の算術は、片方が始対象なら残った方しか
> 返せないので単位元になる（`__ + 3 = 3`）。結果の型が `Address` のときだけ終対象の顔を出して吸収する——
> 溢れた番地を次の演算で生き返らせないためで、左右対称である（operator_table.md の爆発律の囲み）。
> かつてこの表は `+`・`*` を終対象の行に置いていた（左辺の `__` が吸収）。

これは「論理的に偽として機能する」という付帯的な説明ではなく、圏論的に記述すると自然に現れる性質です。
以下の各セクションは、零対象としての `__` から導出される各性質を詳述します。

## 2. 双代数としての数学的基盤

### 2.1 基本性質（零対象からの導出）

- **零対象**: Signを圏として定義するために必要な、始対象と終対象の一致点（**これが第一原理**）
- **双代数の単位元**: リスト構造（余代数）の単位元は `__` そのもの。**関数合成（代数）の単位元は
  その射としての顔**（`_` ／ `!__`）である——合成の単位元は射でなければならないからである。
  対象である `__` を Lambda の隣に置くと、合成の相手ではなく**引数**として解決され
  （`f __` → `apply[f, __]`）、完全性公理が先に効く。どちらも零対象から導出される（§2.3）
- **値としての性質**: `__ = []`（空リストと等価）
- **関数としての性質**: 余積の単位元として「プログラムの流れを素通りする」
- **重要な区別**: `__ ≠ 0`（数値ゼロとは明確に異なる：零対象 ≠ 数値）

### 2.2 双代数構造の定義

Sign言語のリスト構造は双代数 `(List, unit, join, extract, duplicate)` を形成します：

#### 代数構造（モナド）

- `unit : A → List A` where `unit(x) = [x]`
- `join : List(List A) → List A` where `join([[a₁, a₂], [b₁, b₂]]) = [a₁, a₂, b₁, b₂]`

#### 余代数構造（コモナド）

- `extract : List A → A` where `extract([x]) = x`, `extract([]) = __`
- `duplicate : List A → List(List A)` where `duplicate([a, b]) = [[a], [b]]`, `duplicate([]) = [[]]`

### 2.3 圏論的証明：`__`の双代数単位元性

**定理**: `__`は双代数 `(List, unit, join, extract, duplicate)` の単位元である

**証明**:

#### モナド単位元の証明

```Haskell

__ >>= f = __                // left unit law (空リストなので結果も空リスト__になる)
m >>= (\x → __) = __         // right unit law

具体例：
__ >>= [+ 2] = [+ 2](__) = __
[1,2,3] >>= (\x → __) = __

```

#### コモナド単位元の証明

```haskell

extract(__) = extract([]) = __           // extraction law
duplicate(__) = duplicate([]) = [[]] = [__]   // duplication law

```

#### 双代数互換条件の検証

```haskell

extract ∘ unit = id:
extract(unit(__)) = extract([__]) = __ = id(__) ✓

duplicate ∘ unit = unit ∘ unit:
duplicate(unit(__)) = duplicate([__]) = [[__]]
unit(unit(__)) = unit([__]) = [[__]] ✓
```

## 3. Unit演算の完全仕様

### 3.1 関数文脈での演算

#### 3.1.1 算術演算子との相互作用

```text
`【比較】Hole（_）は Unit（__）とは別物である
` _ は「まだ値の決まっていない引数スロット」であり、コンパイル時にラムダへ静的脱糖される
` __ は実行時に流通する値であり、下記の伝播則に従う
` この分離により、動的な計算の結果 Unit になった値が部分適用を誘発することがない

`【部分適用の書き方】中置演算子のオペランドに _ は置けない（原理4）
` 欠けている側は位置で示す。両側とも位置で書けるため _ を使う理由が無く、
` 同じ概念に2通りの書き方を生むだけだからである
[+ X]             ` 右辺束縛。(_x) => _x + X
[X +]             ` 左辺束縛。(_x) => X + _x
f _ X             ` 名前付き関数の引数位置には _ を置く。(_x) => f _x X

`【算術演算における爆発律】
` Unit は算術の両側で単位元として消える（A × A → A——片方が始対象なら残った方しか返せない）
__ + X → X        X + __ → X
__ - X → X        X - __ → X
__ * X → X        X * __ → X
__ / X → X        X / __ → X
__ % X → X        X % __ → X
__ ^ X → X        X ^ __ → X

`【結果の型が Address のときだけ吸収】溢れた番地を生き返らせない（左右対称）
__ + K → __       P + __ → __

`【部分適用】他の算術演算子も同じく、欠けている側を位置で示す
[- X]  [X -]      [* X]  [X *]      [/ X]  [X /]
[% X]  [X %]      [^ X]  [X ^]
```

#### 3.1.2 比較演算子との相互作用

```text

`大小比較や等値比較における吸収（比較演算子は両辺とも吸収元）
`左辺Unit: 比較対象が存在しない → 演算不成立 → __
__ < X → __       X < __ → __
__ <= X → __      X <= __ → __
__ = X → __       X = __ → __
__ != X → X       X != __ → X   ` 例外: != は両辺とも単位元。非Unit側を返す
__ > X → __       X > __ → __
__ >= X → __      X >= __ → __

`【部分適用】比較関数も同じく、欠けている側を位置で示す（_ は中置には置けない）
[< X]   [X <]     [<= X]  [X <=]
[= X]   [X =]     [!= X]  [X !=]
```

> [!NOTE]
> **比較演算子と Unit の相互作用**
>
> **左辺が `__` の場合:** `__` は値として確定していないため、比較演算子は演算自体が成立しない。よって `__`（吸収元）が返る。
>
> **右辺が `__` の場合:** 同様に比較対象が存在しないため演算が成立しない。よって `__`（吸収元）が返る。
> これは算術演算子（`x + __ = x`）の「右辺Unit=単位元」とは異なる。比較演算子は**値の順序・等値関係の判定**であり、比較対象の欠損は演算の失敗を意味する。
>
> **`!=` が唯一の例外（両辺とも単位元）:** 片方が `__` であれば「等しくない」ことがその時点で確定するため、比較は論理的に真になる。真のときに情報を運ぶのは**非 Unit 側の値**なので、`__ != X` も `X != __` も `X` を返す。左右で挙動が変わらない点に注意——`__ != X` だけを吸収元にすると、同じ演算子が引数の順序で別の答えを返すことになる。
>
> 両辺とも `__` の場合は「等しい」ので偽となり、`__` が返る。`!==`（構造的非等価）も同じ形である。
>
> なお、`3 < 2 != 4` のような異種比較の連接は**構文上 NG**（比較演算子の連接は同種のみ許可）。
> `3 < 2` の結果を `!=` で使いたい場合は `(3 < 2) | 4` のように余積演算子を使う。

#### 3.1.3 関数適用とアリティ（Arity）による挙動の分岐

明示的にUnit（`__`）を引数として渡した場合の挙動は、対象となる関数のアリティ（引数の満たされ具合）によって双代数的な役割を明確に変えます。

```text
` 完全性公理（§3.4）により f __ = __ が成立するため、
__ f → f __ → __   ` f: Lambda（未飽和）

` 1. アリティが残っている（未飽和な）関数の場合

` 例外： 前置 @ によるデリファレンスは、右辺が飽和時に評価を駆動する
` （遅延評価の 1step 進行と一致）

` saturarated functionは、参照で渡されることになることが自明であるため、@前置演算子のみで評価を駆動する。
` このため、引数にUnitやholeを渡す必要がない。

@F_saturated
`→ 1step評価後、飽和関数または結果が返る。

` 当然、全てを連続して評価するなら、後置~による呼び出しとなる。

```

> [!IMPORTANT]
> **完全性公理** (`Type_System_ja-jp.md` §3.4)：`∀f, f __ = __`
>
> 所有の引数に有効値（非 Unit）が揃って初めて関数呼び出しは真（有値）とみなされる。
> `__` を引数として渡すことは「評価しきれない」（偽）を意味するため、全体が `__` に消去する。
> 前置 `@` によるデリファレンス（評価の駆動）はこの公理の外側にある別概念である。

### 3.3 積・余積における零対象としての振る舞い

`__` は**零対象（Zero Object）**として、積（`&`）と余積（`|`）でそれぞれ異なる役割を担います。これは「論理的に偽として機能する」という付帯的な性質ではなく、**零対象の定義から必然的に導出される振る舞い**です。

> [!IMPORTANT]
> 零対象とは**初対象（Initial Object）と終対象（Terminal Object）が一致したもの**です。
> これにより `__` は積においては吸収元、余積においては単位元として、同時に機能します。

#### 3.3.1 論理積 `&` ── 積（Product）における零対象

`&` は圏論的な積（Product）演算です。零対象 `__` は積の**吸収元（零元）**として機能します。

```text
__ & X → __    ` 終対象として積に吸収（0 × x = 0）
X & __ → __    ` 同上
```

#### 3.3.2 論理和 `|` ── 余積（Coproduct）における零対象

`|` は圏論的な余積（Coproduct）演算です。零対象 `__` は余積の**単位元**として機能します。

```text
__ | X → X    ` 初対象として余積の単位元（0 + x = x）
X | __ → X    ` 左辺が非Unitなら短絡評価
```

#### 3.3.3 排他的論理和 `;` ── 余積の差分

`;` は余積における対称差（Symmetric Difference）です。`__` は余積の単位元として同様に機能します。

```text
__ ; X → X    ` 余積の単位元
X ; __ → X    ` 同上
```

#### 3.3.4 否定 `!`

> [!IMPORTANT]
> **前提：ラムダが Unit と同型になる条件**
>
> Sign において「未評価なラムダは Unit と同型」である。
> これは、一般のラムダが副作用を含む可能性を持ち、Id 射の観点から**評価予定が静的に確定できない**ことに由来する。
> 評価予定が未定 = 「何を返すか約束できない」= Unit と同型。
>
> **例外：評価予定が確定したラムダ**
>
> `!__` が返す Id 射は**副作用のない純粋な恒等関数**であり、Id 射の観点から評価予定が静的に確定している。
> よって「未評価だが Unit ではない」特別なラムダとして機能し、真（非 Unit）として扱われる。
>
> 注：`!__ __` は理論的に正しく `__` を返す（Id射に Unit を渡すため）。
> しかし `!__` 自体は評価予定確定ラムダであるため `__` ではない。

```sign
` → Id射（評価予定確定・非Unit・真に相当）
!__
` → __  （expr が非Unit の場合）
!expr
```

> [!NOTE]
> **外延性公理による `!__` とブラケット表記の恒等射の同一性証明**
>
> `!__` は「副作用のない純粋な恒等関数」として定義されている以上、任意の $x$ に対して `!__ x = x` が成り立つ。一方、ブラケット記法の真の恒等射 `[__ ]` / `[ __]` も静的脱糖 `$p0 ? $p0` の定義より任意の $x$ で `[__ ] x = x` が成り立つ。`Kan_Extensions_Unification_ja-jp.md` §3.5.2 が `__ ≠ 0` の証明に用いた関数の外延性公理 $A = B \iff \forall x (A \text{ op } x = B \text{ op } x)$ をここに適用すると：
>
> ```
> !__ x = x（定義より）
> [__ ] x = x（静的脱糖 $p0 ? $p0 の定義より）
> ∴ 外延性公理により !__ = [__ ] = [ __]
> ```
>
> さらに、裸のHole `_`（何とも演算子結合していない単体の `_`）の静的脱糖極限も同じ形 `$p0 ? $p0` に収束する（`Hole_Static_Desugaring_Spec_ja-jp.md` 参照）。したがって `!__`・`[__ ]`・`[ __]`・裸の `_` の静的脱糖極限は、いずれも**同一の恒等射に到達する4つの異なる構文経路**である。
>
> ただし `_` 自体はランタイム値ではなくコンパイル時に完全に消える構文糖衣（静的脱糖）であり、`!__` はランタイムに存在する値である点で両者は同じ圈に属さない。同一性が成立するのはあくまで「`_` を静的脱糖した後の項」と `!__` の間である。

## 4. 双代数の分配法則

Sign言語の演算子関数化は双代数の分配法則として表現されます：

```text

`分配法則: (f ⊗ g)(hole(x)) = hole(f(x)) ⊗ hole(g(x))
(+ ⊗ *)(hole(x)) = hole(+(x)) ⊗ hole(*(x))

具体例:
_ + 3 → [+ 3]    `Holeによる部分適用の生成
_ * 5 → [* 5]    `hole(*(5))を生成

```

この分配法則により、演算子の自然な関数化と部分適用が双代数の構造から導かれます。

### 5.1 Unit値の表現

**GPR 幅の型では `0x8000000000000000` を niche として `__` に充てる**

- **条件付き命令活用**: AArch64の条件付き命令でUnit判定を効率化

> [!CAUTION]
> **`0` を `__` の印にしてはいけない。**
>
> ここには以前「Unit値を NULL ポインタとして表現」「xZR レジスタの特性を活用」と
> 書かれていたが、それは下の §5.2 の表と食い違っていた——§5.2 は `0x00`（アドレス値
> ゼロ）を「**有効な値を持つ**」と明記している。
>
> Sign では **`__` だけが偽であり `0` は真である**。`0 = 0` は真であり、そのとき
> 返せるオペランドは `0` しかない（[`comparison.md`](../type/comparison.md) §2.1）。
> `__` を `0` で表すと、この真が偽と区別できなくなる——`cbz` で分岐した瞬間に
> 評価器と食い違う。

### 5.2 Unit値のバイナリ表現（`\x00`）

> [!IMPORTANT]
> **`\x00`（ヌルバイト）はSignにおけるUnitのバイナリ表現である。**
>
> **⚠️ `0x00`（アドレス値ゼロ）とは全く異なる概念である。混同しないこと。**

Signのパーサー（およびセルフホストコンパイラ）では、入力ストリーム中の生の `\x00` バイトは**文字データ（Char型）としてでも、アドレス値としてでもなく、Unit型の値として直接解釈される**。

> [!CAUTION]
> **`\x00`（ヌルバイト）と `0x00`（アドレスリテラル）の区別**
>
> | 表記 | 種別 | 意味 |
> |---|---|---|
> | `\x00`（入力ストリーム中の生バイト） | **型シグナル** | Unit型そのもの。**値を持たない。** |
> | `0x00`（Signソース中のリテラル） | **Address型の値** | アドレス0番地。**有効な値を持つ。** |
>
> `\x00` はアドレス空間上の「0番地」を指すポインタではない。
> それは「値が存在しない」という型状態そのものを表す入力ストリームの信号である。

| ソース表現 | 解釈 | 用途 |
|---|---|---|
| `__` | Unit値 | 人間が書くソースコード |
| `\x00`（生バイト） | Unit型として直接識別 | 機械生成トークン・セルフホスト時のワイヤフォーマット |
| `0x00` | **Address型の値ゼロ** | 通常のアドレスリテラル（Unitとは無関係） |

この設計により：

1. **セルフホスト時の効率化**: SignコンパイラがUnit値をトークン列として出力する際、`__`（2バイト）ではなく `\x00`（1バイト）として emit することで処理を効率化できる。
2. **型シグナルとしての明確性**: `\x00` バイトは文字リテラル（`\a`、`\n` 等）とは構文上区別され、文字として扱われることがない。Signの文字リテラルはバックスラッシュ+1文字（`\\x`）の形式であるため、生の `\x00` バイトとは衝突しない。
3. **Stringへの包含禁止**: `\x00` はString型に含めることができない。Signにおいて `\x00` は常にUnitを意味し、文字データとしての意味を持たない。

```
入力バイト \x00  →  lex → Unit型トークン（= __）
                         ↓
           パーサーが unit ルールでキャッチ
                         ↓
           ASTノード: { type: "Atom", dataType: "unit", value: "__" }

※ 入力ストリーム中の "0x00" テキスト → address型トークン（値ゼロのアドレス）← 別物！
```

### 5.3 双代数演算の最適化

```assembly
// __ + X の実装例
cmp x0, #0               // Unit判定
b.eq .generate_partial   // Unitなら部分適用生成
// 通常の加算処理

.generate_partial:
adr x1, .add_closure     // [+ X]クロージャのアドレス
mov x0, x1               // 関数ポインタを返す
ret
```

### 5.4 条件付き命令による効率化

```assembly
// Unit判定と処理の統合
cmp x0, #0               // Unit判定

```

### 6.1 双代数性を活用した関数合成

```sign
`map操作の双代数的表現
map_double : [* 2,]
` → [2, 4, 6, 8]
result : map_double [1, 2, 3, 4]

`部分適用の連鎖

`関数合成
add_then_multiply : [+] [* 2]

` → (5 + 3) * 2 = 16
result : add_then_multiply 3 5
```

### 6.2 Unitを用いた条件分岐

```sign
`Unitの論理的性質を活用
safe_divide : x y ?
	y = 0 & __ | [x / y]

` → __ (Unit)
result : safe_divide 10 0
` → [5] (結果のリスト)
result : safe_divide 10 2
```

> [!WARNING]
> **`&`/`|`連鎖による条件分岐の限界と、match_caseがこの形への脱糖を行わない理由**
>
> 上記のパターンは、本質的には「`cond`が真なら`result`、偽なら`__`を返し、`\|`がその`__`を
> 「マッチしなかった信号」として次の分岐へフォールスルーさせる」という仕組みです。
>
> ここには**構造的な曖昧さ**があります。もしある分岐が、「マッチしたうえで、正当な結果として`__`を返したい」
> 場合、`&`/`\|`連鎖はこれを区別できません。「マッチしなかった」という選択信号と、「マッチした分岐の
> 本体が返した値」という意味信号が、どちらも同じ`__`で表現されてしまうためです。
>
> **このため`match_case`は、この`&`/`\|`連鎖へのプリプロセス段階の脱糖を行わない。**
> match_caseはPass 1〜3が直接処理するネイティブな構文要素として実装され、「どの分岐が選択されたか」という
> 選択信号と、「選択された分岐が何を返すか」という値の信号を別チャンネルとして扱う。一度分岐が選ばれた後は、
> その本体が`__`を返すことを含めて完全に自由であり、`&`/`\|`という汎用のUnit伝播機構を借用しないことで、
> この曖昧さ自体が構造的に発生しなくなる。上記の`safe_divide`のような単純な数値分岐（マッチしない
> 場合に`__`を返すだけで、分岐自体が`__`を正当な値として返す必要がない）では`&`/`\|`連鎖を
> 直接使っても問題ないが、一般の`match_case`はこの限界を回避するためにネイティブ実装を採用する。

## 7. 設計原則と理論的意義

### 7.1 双代数単位元としての一貫性

1. **代数的一貫性**: モナド法則を満たす関数合成の単位元（担うのは射としての顔 `_`、§2.1）
2. **余代数的一貫性**: コモナド法則を満たすリスト構造の単位元
3. **双代数互換性**: 代数と余代数の相互作用を保持
4. **自然変換性**: 関数とリストの間の自然な変換を提供

### 7.2 実装効率との統合

- **理論的純粋性**: 圏論的に記述・検証できる設計
- **実装効率**: ARM64での高効率な機械語生成
- **型安全性**: コンパイル時の双代数構造検証
- **最適化可能性**: 双代数の性質を活用した自動最適化

### 7.3 デバッグ環境におけるUnit追跡と可観測性 (Unit Traceability & Dynamic Payload)

プロダクション環境および Layer 0 のベアメタル実行において、Unit (`__`) はオーバーヘッドゼロの零対象（レジスタレベルでの即時判定・収束）として動作する。一方、**デバッグ環境や高解像度駆動レイヤー（Scriptable/Debug Layer）** においては、障害や条件未成立によって発生・伝播した Unit に対し、その崩壊に至った **「因果の軌跡（Causal Trajectory）」** を追跡できる拡張メタデータ（Unit Payload）を動的に付与・収集する仕組みを提供する。

1. **因果軌跡（Causal Trajectory）の保持**:
   - 直近のパターンマッチング成功履歴や、直前のローカル変数スタックフレームのコンテキスト。
   - `match_case` 等の条件判定が失敗した際に返却された明確な `Text` 説明文。
2. **低レイヤー決定論との照合（Hardware Clock / Sequence ID）**:
   - スクリプティブな高レイヤーでの追跡と Layer 0 のベアメタル実行トレースの整合性を保つため、ハードウェアクロックド・タイムスタンプおよびシーケンス ID をペイロードに包含可能。
3. **「ログのゴミ山 (Landfill)」の排除**:
   - 巨大で無駄なスタックトレースやログファイルを生成（Landfill 化）するのではなく、Unit 自身の伝播経路に必要な最小限の因果情報のみを保持し、必要時のみリバースターゲットでリアクティブに抽出可能。

これにより、ゼロコスト抽象化のベアメタル性能と、高い可観測性（Observability）・決定論的デバッグ追跡性を駆動レイヤーに応じてシームレスに両立する。

## 8. 結論

Sign言語のUnit (`__`) は、単なる「便利な記号」ではなく、評価規則の第一原理から生まれた言語の基盤要素です。圏論的に記述すれば双代数の単位元と同型な振る舞いを示し、モナドとコモナドの両方の観点から整合的に説明できます。これにより、関数型プログラミングとリスト処理の統一的な表現と、「見えない強い型付け」および「ゼロコスト抽象化」の根拠を与えています。

圏論的に見れば双代数的な構造を持つこの設計は、実装効率と理論的整合性を両立し、プログラマにとって直感的な言語として機能します。
