# Sign 実行モデル：すべては main の内部関数である

## 核心

> **Sign のすべての関数は、`main.sn` という1つの関数の内部関数として静的に展開される。**

これは Sign の設計における最も根本的な性質であり、以下のあらゆる設計判断の根拠となる。

---

## 1. ファイル名 = エントリポイント = 関数名

Sign において、`.sn` ファイルは関数定義である。ファイル名がそのまま関数名になる。

```
add.sn       →  関数 add の定義
multiply.sn  →  関数 multiply の定義
main.sn      →  プログラムのエントリポイント（= C の main()）
```

`main.sn` はプログラム全体の「最外スコープ」であり、
他のすべての `.sn` ファイルは `main` の内部関数として取り込まれる。

> [!IMPORTANT]
> **ファイルが外へ渡すのは、前置 `#` を付けたものだけである**（利用者 2026-10-04・10-05）。
>
> - ファイルは普通の返値を持たない（最後の定義を返値として引き回す案は、セキュリティのために
>   採らない）。前置 `#` で、ファイルが返すもの（**公開**）と、内側で計算するもの（`#` の無い定義）を
>   分ける。
> - `#` の無い定義は、ファイルの外から見えない。
> - `main.sn` は仮引数を持たない。入力は前置 `@`、出力は中置 `#` で取り回せるので、IO を引数で
>   受けなくてよい。
>
> 「ファイルが1つの関数のように実行される」は**たとえ**である。

---

## 2. インポートは「内部関数の定義」である

```text
`add.sn`@~   ← add.sn を「インポート」する
```

これは「ファイルを読む」のではなく、**`add` という内部関数を現在のスコープに静的に定義する**操作である。

取り込みの綴りは2つある。どちらもコンパイル時に解決される。

| 綴り | 意味 |
|---|---|
| `` `math.sn`@ `` | `math.sn` が返すもの（`#` の公開の集まり）。公開は名前で引ける（`` add @ `math.sn`@ ``、連なり `` c @ b @ a @ `math.sn`@ `` も同じ） |
| `` `math.sn`@~ `` | **公開**を現在のスコープへ撒く（後置 `~` は場所から撒く印）。内側の定義は撒かれない |

撒かれるのは `#` の公開だけで、`math.sn` の内側の補助は撒かれない。公開どうしは、前置 `#` の段では
1つの平らな名前空間に入る（名前空間は `##` 以上の段で扱う）。

> [!NOTE]
> **alpha は未着地**（2026-10-04）：`` `x.sn`@~ `` はファイルの頂の束縛を**全部**撒き、撒かない `` `x.sn`@ `` は
> 字面の文字列を返す。自己ホストのソース（`alpha/sign/*.sn`）は `#` の公開を持たない。器の仮引数を括りの
> 形へ書き換える片の直後に、各ファイルの外から使われる名前へ `#` を付ける（補助の定義はそのまま内側に残る）。

C で言えば：

```c
int main() {
    // add.sn のインポート = add を内部関数として定義
    int add(int a, int b) { return a + b; }  // C の nested function（GNU 拡張）

    // main.sn の本体
    int result = add(3, 5);  // → 8
    return 0;
}
```

---

## 3. 部分適用は compile-time の静的特殊化である

```sign
add3 : add 3
` → 8
add3 5
```

`add3` は「ランタイムにクロージャを生成する」のではなく、
コンパイラが **`add` を `3` で特殊化した関数 `add3`** を `main` 内に静的に生成する。

```c
// コンパイラが生成するコード（概念）
int main() {
    int add(int a, int b) { return a + b; }

    // add3 : add 3  → コンパイル時に特殊化
    int add3(int b) { return add(3, b); }  // ← 静的に展開

    int result = add3(5);  // → 8
}
```

実行時のクロージャ構造体は存在しない。ヒープ確保も alloca も不要。
例外は**関数を返す関数**だけである（§4）。

---

## 4. クロージャのエスケープ問題が存在しない理由

「クロージャがスタックフレームを超えて生きる」問題（dangling pointer）は、
クロージャを**ランタイムに動的生成**する言語のものである。

Sign では：
- すべての「クロージャ」はコンパイル時に特殊化された内部関数
- 内部関数の寿命 = `main` の寿命 = プログラム全体
- スタックフレームを超えるという概念が設計上存在しない

**例外は関数を返す関数だけである。** `adder : n ? $(add n)` のように、捕まえる値が実行時に
決まる関数を返すときは、コンパイル時には特殊化しきれない。そのときは関数オブジェクト
{関数の番地, 捕まえた値…} の**番地**を返し（`$` を付ける、[type_system.md](../type/type_system.md) §3.5
「関数を返す関数は、関数オブジェクトの番地で返す」）、その置き場は**呼ぶ側が用意する**——器を
返すのと同じ規約である（[stack_abi.md](../memory/stack_abi.md) §4.3）。生成元のフレームには置かない
ので、戻っても死なない。`$` を付けずに関数を返す本体は、コンパイル時に名指しして止める。

---

## 5. 帰結：完全なヒープレス

この実行モデルにより、**Sign の実行モデルは（layer 1 以降において）ヒープを一切必要としない**：

| 機能 | 確保方法 | 理由 |
|------|---------|------|
| 完全適用の関数呼び出し | レジスタ渡し | 静的に確定 |
| 部分適用 | コンパイル時特殊化 | 実行時クロージャ不要 |
| 関数を返す関数 | 呼ぶ側の置き場（関数オブジェクト） | 生成元のフレームに置かないので戻っても死なない |
| 配列・構造体（layer 1以降） | `alloca` 連続ブロック | スコープ終了で自動回収 |
| モジュールスコープの変数 | `main` のスタックフレーム | プログラム全体が寿命 |

GC も `free` も所有権注釈も不要。すべてがコンパイル時に決定する。

> [!IMPORTANT]
> **layer 0 では `alloca` 自体が使用不可**である。`alloca` はスタック（RAM）が初期化済みであることを前提とするため、RAM がまだ初期化されていない layer 0 では利用できない（[Build_System_ja-jp.md](../build/Build_System_ja-jp.md) の layer 表を参照）。layer 0 のコードはレジスタ渡しと `#`/`@` による volatile な生アドレス操作のみで RAM/スタックを手動でブートストラップし（[Entry_Point_ja-jp.md](../build/Entry_Point_ja-jp.md) 参照）、その完了後に layer 1 以上として宣言されたモジュールに制御を渡すことで、初めて `alloca` を伴う配列・構造体・クロージャ相当の機能が使用可能になる。

ただし、`memory_management.md` が定義する stdlib 拡張（Shared-Heap, `##`）は任意選択の layer 1 以上の機能であり、この原則の例外として明示的にオプトインされる。RC/ARC 管理された Shared-Heap は、コア言語のヒープレス性を損なわない、独立した上位レイヤーの機能である。

---

## 6. layer との関係

この実行モデルは `layer: 0`（bare metal）から成立するが、`alloca` の利用可能性は layer によって異なる。
OSなし・ランタイムなしでも、`main` 相当の制御構造自体は成立するが、layer 0 の間はレジスタ渡しと `#`/`@` のみに限定される。

```
layer: 0  → レジスタ渡しと #/@ のみ。RAM/スタックは手動初期化が必要（alloca 不可）
layer: 1  → RAM が使えるようになる（alloca の連続ブロックが使用可能になる）
layer: 2+ → FPU, SIMD 等が加わる
```

Sign のスタックが「BIOS から書ける」のは、この実行モデルが OS のランタイムに
依存しないことの直接の帰結である。layer 0 の手動ブートストラップ（RAM/スタック初期化）は、[Entry_Point_ja-jp.md](../build/Entry_Point_ja-jp.md) が定義する `boot.sn`（`entry`/`stack` フィールド）の役割であり、これが完了して初めて layer 1 以上の alloca ベースのヒープレス実行モデルに引き継がれる。
