# 演算子と層の関係

`option_ms_schema.md` §4 は層を「機能が段階的に追加される」ものとして定める。それは正しいが
**半分**である。実際に測ると、層は**両方向**に働いている——上へ行くほど**使えるようになる**
ものと、上へ行くほど**禁じられる**ものがある。

この文書は、その関係を一枚に置く。数字と ○×は `alpha/javascript` の実装を各層で走らせて
**測った結果**であり、仕様からの推測ではない。

---

## 1. 何が層を決めているか

層は番号ではなく、**ハードウェアの状態**である。番号はその状態の名前でしかない。

| 層 | ハードウェアの状態 | そこで初めて成り立つこと |
|:--:|---|---|
| 0 | RAM 未初期化 | **番地がある**（MMIO は既に在る） |
| 1 | RAM 開通 | **場所が取れる**（`sub sp`）＝コールスタックが立つ |
| 2 | FPU 初期化済 | 浮動小数が計算できる |
| 3 | SIMD 初期化済 | ベクタが計算できる |
| 4 | OS | **ローダーが居る**（メモリマップを OS が決める） |

したがって「その演算子が層 N で使えるか」は、**その演算子が何を要求するか**で決まる。
要求は**2種類しかない**。

- **確保**（`sub sp`）——layer 1 以上。器を組む・持ち上げる・`$匿名式`・sret がこれ。
- **計算器**（FPU / SIMD）——layer 2 / 3 以上。

かつてここには3つ目として「ローダー——layer 4」を挙げていた。**これは取り消す**（§3.5）。
layer 4 が足すのはローダーという*要求*ではなく、ローダーが*居ること*である。演算子の側は
何も変わらない。

> [!IMPORTANT]
> **`import`（後置 `@`）そのものは layer 4 の機能ではない。**
>
> `system_architecture.md` §3.1 が層ごとに定めている通り、後置 `@` は layer 0 から
> **静的に解決可能なシンボルの要求**として有効である。Zig の `@import` と同じく
> **コンパイル時**に解決されるので、確保もローダーも要らない。
>
> 根拠は仕様自身にある——「自身より高い layer のコードはインポートできない」の違反は
> **コンパイルエラー**である（`option_ms_schema.md` §4.1）。実行時に解決するなら静的に
> 検査できないので、この規則は import がコンパイル時であることを前提にしている。
>
> **後置 `@` は全層で同じものである。** かつてここには「layer 4 で足されるのは動的解決
> （`dlopen` 相当）だけ」と書いていたが、これは取り消す——§3.5 の通り、そんな解決方法は
> Sign に無い。

## 3. 表から読めること

### 3.1 同じ演算子が層によって意味を反転させる

`+` は layer 0 では **MMIO のレジスタを選ぶ手段**（`uart + 4`）だが、上の層では
**任意の番地を捏造する手段**になる。だから layer 0 だけで許す。

`#` も同じ形をしている。生の番地へ直に書けるのはハードウェアを触る層（0〜1）までで、
その上では書き込み先が自分の持ち物でなければならない（`$名前`・受け取った参照・分解した先）。

これが閉じると、**上の層で番地として存在できるのは自分が持っているものだけ**になる。
捏造した番地は型として作れないので、層の境界を越えて渡されるポインタを受け側が検証する
必要が無い——C の syscall 境界が毎回やっている仕事が、言語の側で不要になる。

### 3.2 「確保が要るか」が layer 0/1 の境界そのもの

layer 0 の門番は `sub sp` を出す式**すべて**に掛かる。判定は1箇所（`allocaAllowed`）に
集めてある——場所を取る式は6通りあり、それぞれの枝で書けば必ずどれかが漏れるからである。

逆に、**確保が要らないものは layer 0 で全部使える**。切り出し（`s ' i~`）は同じ領域を
指し直すだけ、MMIO は既に在る場所を読み書きするだけ、文字列リテラルは `.rodata` に在る。

### 3.3 構造体は「値」と「配置の記述」で層が違う

`Struct` の実体は「単一の `alloca` で確保する」（`stack_abi.md` §7.1）——**値として作る
なら** layer 1 以上である。

だが**フィールドが全部定数**なら話が別で、フィールドを引いた結果はその番地そのものなので、
畳んでしまえば構造体はどこにも置かれない。MMIO のレジスタ束がまさにこの形をしている：

```sign
uart :
	DR  : 0x9000000
	PAD : 0x9000004

(DR @ uart) # 0x4f
```

これは `layer: 0` で通る。実測すると生の番地を直に書くより**短い**（54 対 58 命令。
UART へ2文字＋RAM へ書いて読み戻すブートで計測）——束縛を1段経由しないぶんである。
**抽象を足した方が速い**という珍しい向きになっている。

#### 3.3.1 マージは1つの操作に見えて、要求の違う3つである

`a~ b~` は「**`a` の器に `b` の器の中を入れる**」であって、両方から新しい器を作る操作では
ない。結果は `a` そのものである。ここから、**上書きになるか複写になるかは左が何かで決まる**
——同じ規則で両方が出るので、例外を書かなくてよい。

```sign
` 左が名前 → 既にある器なので上書き。p 自身が変わる
p~ [ foo : 99 ]~

` 左がその場のリテラル → その器は今作られたものなので、入れることがそのまま複写になる
[ foo : 99 ]~ p~

` ブロック形も新しい器。書いた行が仕様、撒く行が残りを埋める（list_model.md §5.3.1）
[
	foo : 99
	p~
]
```

**要求が違うので層が分かれる。**

1. **在る場所へ書くだけ**なら確保が要らない——`#` 出力（`$名前`）が layer 0 で通るのと
   同じ理由で、`a~ b~` は layer 0 で通る。MMIO のレジスタ束を書き換えるのがまさにこの形で、
   §3.3 の `uart` を `uart~ [ DR : 0x9000010 ]~` と書くのがそれにあたる。
2. **新しい器を作る**なら確保が要る（layer 1 以上）。左にリテラルを置く形とブロック形が
   これで、どちらも「元は無傷」を選んだということである。
3. **鍵が増える**と、名前ソート順（`stack_abi.md` §7.1）で並びが変わるので在る場所には
   収まらない。`bar@0 foo@8` に `aa` を足すと `aa@0 bar@8 foo@16` で全部ずれる——
   Visual Basic の `ReDim Preserve` が最後の次元しか伸ばせなかったのと同じ理由である。
   だからこれは確保であり、layer 1 以上になる。

> [!NOTE]
> **`ReDim` は実行時に要らない。** 全プログラムを見る以上、ある名前を左に置くマージは
> 静的に列挙できるので、鍵の和集合はコンパイル時の事実である。定義の場所で和集合ぶんを
> 一度だけ取っておけば、スロットの位置は途中で動かず、写しは一度も起きない
> ——まだ入っていない鍵は `__` である（完全性公理）。これは layer 1 以上でだけできる。
> layer 0 では確保が無いので、**鍵が増えるマージは書けない**が正しい答えになる。

> [!IMPORTANT]
> **共有の代償は受け手の側に出る。** 1 の形は既にある器へ書くので、その器を見ている
> 他の誰かにも見える。影響されたくないなら 2 の形（左にリテラル、またはブロック形）を
> 取る。**書き分けが構文に出ていて、安全な方を書くのが自然な形**になっている
> ——原理3（危険は明示的な opt-in）がここでも同じ形をしている。

### 3.4 `@` の3つの位置は「何を辿るか」で分かれている

| 位置 | 名前 | 辿るもの | 層 |
|---|---|---|:--:|
| 前置 `@p` | input | **番地**（メモリ） | 0 |
| 中置 `x @ p` | get_at | **構造**（名前空間） | 0 |
| 後置 `p@` | import | **モジュール**（ファイルシステム） | 0（全層で同じ） |

同じ動詞（辿って持ってくる）の目的語が違うだけである。辿る先は遠くなるが、**層が上がる
わけではない**——3つとも layer 0 から使える。辿る先が遠いことと、実行時に何かを要求する
こととは、関係が無い。

中置は `'` と左右が逆で、`s ' x`（s **の** x）に対し `x @ s`（s **において** x）である。
鍵を先に言う語順は**名前解決の語順**であり、だから `@` は右結合で `a @ b @ c` の
**一番右が根**になる（`www.example.com` を右から解決するのと同じ向き）。

後置はその右辺が暗黙になった形——FQDN の末尾ドットが根を指すのと同じである。Sign には
予約語が無いので右辺を名指せず、**後置以外に置き場所が無い**。

### 3.5 「動的」という語が3つの別々の軸を潰していた

後置 `@`（import）を実装して測ったところ、**layer 0 / 1 / 4 のすべてで同じ値が出た**。
コンパイル時に解決されて消えるので、確保も計算器も要らない。表の行が全層 ○ なのはそのためで、
`#` 出力や `+` 生番地のような**上限**も無い。

ここで、この文書と `system_architecture.md` §3.1 が使っていた「動的」という語を分解する
必要が出た。**3つの別々の軸が1語に潰れていた。**

| | 番地が決まる時期 | ソースの見た目 | 型 | C では |
|---|---|---|---|---|
| 静的リンク | ビルド時 | `foo` を呼ぶ | 分かる | ツールチェーン |
| ロード時動的リンク（`ld.so`） | ロード時 | **同じ** | 分かる | ツールチェーン＋OS |
| `dlopen` | 実行時・**文字列で** | `dlsym("foo")` | **消える** | **自力** |

**C が言語機能として提供しているのは、この表の 0 行である。** 静的リンクはツールチェーンの
仕事であり、ロード時動的リンクに至ってはソースが1文字も変わらない。3行目だけが自力で書く
ものであり、しかも型が消えるので `void*` にキャストする——だから C 側の記憶では「動的
リンク＝自力＝特別なもの」として目立つ。潰れやすいのはこのためである。

**Sign の `link:` フィールドはこの軸ですらない。** 中身は `rom` / `ram` / `heap` の
`origin` と `length` である（`option_ms_schema.md` §5.5）——つまり**メモリマップを誰が
決めるか**であって、シンボルをいつ結ぶかではない。

| `link:` | 意味 |
|---|---|
| `static` | メモリマップを自分で宣言する（リンカスクリプト相当） |
| `dynamic` | OS に委ねる |

だから layer 0 で `link: dynamic` がエラーになる理由も、仕様自身が「**OSローダーが存在
しないため**」と書いている（§3.1）。`@` の性質ではなく、OS が居ないことである。

そして **`dlopen` 相当は Sign には書けない**。`foo@` の `foo` はコンパイル時の識別子で
あって、文字列からシンボルを引く道が構文に無い——`name : `libm`` と束縛して `name@` と
書いても、解決されるのは束縛 `name` であって中身の `libm` ではない。`.st` が型を持つので
「型が未知のものを読む」必要もそもそも無い。

**結論：layer 4 が足すのはローダーという要求ではなく、ローダーが居ることである。**
`@` は全層で同じものであり、層を決める要求は §1 の通り**確保と計算器の2つだけ**になる。
残る問いは「別オブジェクトに在るコードをどう指すか」だけであり、それは上の表の1行目と
2行目の違い——**ビルド時に置くかロード時に置くか**——でしかない。どちらもソースは
変わらず、型は `.st` から分かる。層とは無関係である。

### 3.6 書き出し側（`#` の段数）は ELF にそのまま揃っている

取り込みの相方（`system_architecture.md` §2.1 の随伴ペアの書き出し側）は、ELF の3段に
そのまま写る。

| Sign | ELF | 意味 |
|---|---|---|
| （無印） | local（`.global` を出さない） | 外に名前が出ない |
| `#` (Rc) | `.global` + `.hidden` | プロジェクト内では結合できるが共有物からは出ない |
| `##` (Arc) | `.global` | 共有オブジェクトの外から見える |
| `###` (Pin) | `.global` + `.sign.pinned` セクション | 配置を `option.ms` が決められる |

3段が既にある場所へ写しただけである。だから §2.2 の「リンカスクリプトが要らない」は
言い換えではなく、**書く場所が `option.ms` に移った**という事実になる。

ここで効くのは**無印が local になること**の方である。それまで Pass 4 は全部の関数に
`.global` を付けていた——`#` を書いても書かなくても同じで、つまり `#` は機械語に何の
意味も持っていなかった。内部関数の名前がシンボル表に載るのは、`.ist` をディスクに
書き出さない理由（内部識別子名・内部フィールド配置を外に出さない）と同じものが `.s` の
側から漏れていたということでもある。

## 4. 表が示す食い違い

表を作ったことで見えたもの。どれも実装の側の話であり、設計の結論ではない。
§4.1 は決着済み、§4.2・§4.3 が未解決である。

### 4.1 `?` に門番が無い（決着済み）

ラムダの呼び出しは**コールスタックを要求する**（`stp x29, x30, [sp, #-N]!`）。ところが
layer 0 で通ってしまっていた。`-M virt` は最初から RAM が生きているので qemu では動くが、
**本物の BIOS/UEFI 初期フェーズならその1命令目で死ぬ**。「動いているように見えて実機で
死ぬ」は一番たちが悪い形なので、門番を足した（`pass4.js` の `checkStackFree`）。

**止めるのは `?` ではなく、フレームである。** `stp x29, x30, [sp, #-N]!` はプリインデックス
で `sp` を下げて書く——`sub sp` という*形*をしていないだけで、やっていることは確保である。
以前の門番は `sub sp` を探していたので、これに当たっていなかった。

判定は**形ではなく要求**で行う（§5 の通り）。見るのは `wrapFrame` を通した**後**の行で
あり、覗き穴と割り付けがフレームを消し切った関数は `?` を書いていても通る。実際
`f : n ? n + 1` の `f` は名指しされず、名指しされるのは呼ぶ側の `_sign_main` だけである。

足したことで `layer: 0` では関数が呼べなくなった——それは正しい姿で、boot は直列のハード
操作だけで書ける（実測済み）。`bl` は戻り番地 `x30` を上書きするので、呼ぶ側は必ず自分の
戻り先を記憶へ退避しなければならない。切り出し・MMIO・番地の算術・点なし・比較連鎖は
確保を要求しないので、layer 0 で通ったままである。

**併せて分かったこと**：「末尾再帰は layer 0 でも通る」というテストがあったが、これは
誤りだった。自己末尾再帰が積まないのは**繰り返しごとに**であって、入口で取る1つの
フレーム（実測 32 バイト）は確保である。誰も見ていなかったので通っていた。

### 4.2 Float / Vector は層より先に実装が落ちる

`layer: 2` で Float を書くと「浮動小数はまだ出せません」（実装の穴）で止まる。層の門番は
L0/L1 でしか効いていない。**実装した瞬間に上の層で通ってしまう**形ではないが、逆に
「層としては許されている」ことが表から読めない。

### 4.3 未実装が5つ

`==`・`|…|`・`<<`・Float は **Pass 4 の穴**である（`まだ出せない式です`）。
`!`（階乗）はそこまで届いていない——**Pass 2 の解決で落ちる**（`解決できない式です: n !`）
ので、Pass 4 の穴として数えるのは誤りだった。

後置 `@` の静的解決は入った（§3.5）。**構造体（値）も入った**——作る・渡す・返す（sret）・
名前で引く・連番で引く・分解・入れ子・器の要素、すべて実機で値を突き合わせてある。
残る Float は計算器という要求を持つが、他は層とは関係しない。

マージ（§3.3.1）は Pass 4 にまだ経路が無い（`まだ出せない式です（construct）`）。
これは層の問題ではなく、要求の違う3つを分けて出す実装がまだ無いということである。

> [!NOTE]
> `|…|`（絶対値）の診断は現在 `まだ出せない式です（block）` と名乗る。ノードの `type`
> （`block`）を出して `kind`（`abs`）を落としているためで、括弧のブロック（`(x)`）は
> 出せるので読み手を惑わせる。名指しの規律が漏れている箇所。

---

## 5. この表の使い方

新しい機能を作るとき、**先に「何を要求するか」を決める**。要求が決まれば層は自動的に
決まり、門番に何を足すかも決まる。

逆に「実装できたから使える」と進めると、`?` のように**要求と層がずれたまま通ってしまう**。
表はそのずれを見えるようにするためにある。
