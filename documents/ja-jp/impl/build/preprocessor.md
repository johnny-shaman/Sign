# Sign言語プリプロセッサの設計: 構文候補

## 0. 改行の2つの役割（最初の走査）

改行には2つの役割がある。**処理の区切り**（その行を評価してよい、という演算子——
[`operator_table.md`](../syntax/operator_table.md) 基本原則）と、**文字としての改行**（`\` の直後の1文字）である。
同じバイトに両方を担わせると、後の段が文脈から推測することになる。だからプリプロセッサは、
最初に一度だけ左から走査して、この2つを別の符号に分ける（利用者の決定、2026-09-15）。

| ディスク上 | 直前が `\` のとき | それ以外 |
|---|---|---|
| CRLF・LF・CR | **LF**（U+000A、文字の改行） | **CR**（U+000D、処理の区切り） |

- **改行は1文字と数える。** CRLF でも「`\` の直後の1文字」は改行1個である
  （[`reference.md`](../../guide/reference.md) の「直後の任意の1文字」はこの意味で読む）。
- **文字列の中は素通しにする。** そこでの `\` はただの文字なので、改行を LF に変えない。
- **行頭は「直前が CR か、ファイルの先頭」である。** 物理的な0列目ではない。`\` + 改行の次の行は、
  0列目から始まっても同じ処理行の続きであり、空白を挟まずに続けば隣接の規則で（項どうしが密着すれば
  構文エラー）、空白で始まればその空白が余積として読まれる。
- **行頭のコメントはこの走査で判別し、読み捨てる。** 後の段は判別し直さない。判別は生のテキストの上で
  [`string_and_comment.md`](../../guide/string_and_comment.md) §2 のとおりに行い、コメントになるのは
  括弧の外にある処理行の頭だけである（TAB の後は行頭ではない、同 §3）。コメント行の末尾の `\` の後の改行は CR のまま。
- **ブロックの中の続き。** `\` + 改行の後にある TAB のうち、今のブロックの深さぶんは字下げとして
  読み捨て、その後の空白が余積になる。括弧の中では TAB をすべて読み捨てる（括弧の中の字下げは
  もともと意味を持たない）。括弧の中かどうかは `\` + 改行の位置で決める——同じ処理行で開いた括弧も
  閉じた括弧も数える。
- **この走査の後ろの段は CR だけを見る。** 行を切るのも、次の行へつなぐのも、ブロックの印
  （`\x02` / `\x03`）を付けるのも、括弧の深さを数えるのも、処理行（CR で切った行）が単位である。
  LF は行の中の文字として運ばれ、字句では `\` と組んで1つの文字リテラル（`Char` の U+000A）になる。
- **空の処理行は読み捨てる。** TAB と空白しか無い行も空であり、ブロックや括弧の中の空行も同じである。
- **値としての CR** は `0u000D` でだけ書ける。値の中の改行は LF で、`#` で書き出す改行も LF である。
- **ファイルの末尾。** 後ろに何も無い `\` は構文エラーである。`\` + 改行で終われば、LF の文字で終わる。
  最終行がコメントか戻り値かは、CR で切った最後の処理行で決める
  （[`string_and_comment.md`](../../guide/string_and_comment.md) §2）。

> [!NOTE]
> 以前は1種類の符号だったので、`\` + 改行の次が0列目だと区切りにもなって値が黙って変わった
> （`` `L1` `` の続きの `` `L2` `` がコメントになった）。次の行へつなぐ処理は LF を空白に替え、
> `a : \` + 改行 + `+ 1` が `!` になった。ブロックの印を文字リテラルが食って構文エラーにもなり、
> 行頭の空白を許すかどうかは生のテキストから推測していた（`prevEndsWithEscape`）。どれも
> 「この改行はどちらの役割か」を後の段が推測していたことの現れである。
>
> コメントの判別も2か所にあった。前処理は生のテキストで、文法は中置演算子の前後に空白を入れた後の
> テキストで、しかも括弧やブロックの中では試さずに判別していたので、答えが食い違うと `\` の後の改行が
> CR のまま文字に食われ、CR が値に入った。判別をこの走査の1か所にして、文法の文字も CR を取らない。

## 1. 引数名の標準化と位置ベース変換

Sign言語のプリプロセッサは、ユーザーが記述した引数名を位置ベースの標準的な識別子（`_0`, `_1`, `_2`...）に自動変換します。これにより、コンパイラ内部での処理が統一され、最適化が容易になります。

```sign
`原始構文
increment : n ? n + 1
add : x y ? x + y

L : x ? x
R : _ ~x ? x

map : f x ~y ? @f x , map y~
map $[* 2] 1 2 3 4 5

`変換後
increment : _0 ? _0 + 1
add : _0 _1 ? _0 + _1

L : _0 ? _0
R : _0 ~_1 ? _1

map : _0 _1 ~_2 ? @_0 _1 , map _2~
map $[* 2] 1 2 3 4 5
```

この変換により、引数名の衝突回避とコンパイラ内部処理の統一化が実現されます。

## 2. 部分適用と引数順序変換

```
`原始構文
twice : f ? f f
flip : f x y ? f y x
f : x y z ? x * y + z
g : f 2 _ 3

`変換後
twice : _0 ? _0 _0
flip : _0 _1 _2 ? _0 _2 _1
f : _0 _1 _2 ? _0 * _1 + _2
g : _0 ? f 2 _0 3
```

## 3. メモリサイズと使用回数に基づくプリプロセス可能な最適化戦略（最小実装では後回し！）

Sign言語のプリプロセッサは、定義されたリテラルのメモリサイズと使用回数に基づいて最適な変換戦略を適用します：

| 分類             | 使用回数 = 1         | 使用回数 > 1          |
|-----------------|---------------------|----------------------|
| 小リテラル (<32B) | 完全インライン展開     | 完全インライン展開      |
| 中・大リテラル (≥32B) | 完全インライン展開   | テーブル参照による共有   |
| 再帰関数 (全サイズ) | テーブル参照          | テーブル参照           |
| エクスポート定義   | テーブル参照          | テーブル参照           |

表の通り、識別子とその場所を示したテーブルは必要です。

インライン展開とは…

```
`原始構文
add : [+]
add 2 3

`変換後
[+] 2 3
```

## 4. 一般ブロック構文のリスト化変換（ブロック末尾の`,`自動挿入）

ブロック構文で純粋なリスト構築を行う場合、各行末に`,`積演算子の自動挿入を行います。

### 4.1 基本変換ルール

条件式（`:`演算子）を含まない純粋なリスト構築ブロックでは、各行末に`,`を自動挿入します。

```sign
`原始構文
buildData :
	readFile `data1.txt`
	processRaw input
	validateData processed
	saveResult final

`変換後
buildData :
	(readFile `data1.txt`),
	(processRaw input),
	(validateData processed),
	(saveResult final)
```

### 4.2 最終行の処理

リストの最後の要素には`,`を挿入しません。

```sign
`原始構文
simpleList :
	1 + 2
	3 * 4
	5 - 1

`変換後
simpleList :
	[1 + 2],
	[3 * 4],
	[5 - 1]
```

### 4.3 括弧の自動挿入

複雑な式は評価順序を保証するため括弧で自動的に囲みます。

```sign
`原始構文
calculations :
	x + y * z
	func a b c
	simpleValue

`変換後
calculations :
	[x + y * z],
	[func a b c],
	simpleValue
```

## 5. 問題のあるパターンと許可されるパターンの明確化

### 5.1 許可されるパターン

#### パターンA: 純粋な条件分岐
```sign
`✅ 正常：条件分岐のみのブロック
classify : x ?
	x < 0 : `negative`
	x = 0 : `zero`
	x > 0 : `positive`
```

#### パターンB: 純粋なリスト構築
```sign
`✅ 正常：一般処理のみのブロック
processSteps :
	step1 data
	step2 result
	step3 final
```

#### パターンC: 単一式の評価
```sign
`✅ 正常：単一の複雑な式
complexCalc : x ?
	calculateSomethingComplex x y z w
```

### 5.2 問題のあるパターン（アンチパターン）

#### 問題のある混在パターン
```sign
`❌ 問題：条件式と一般処理が同一階層で混在
processData : x ?
	preProcess x
	x < 0 : `negative`
	transform x
	x > 100 : `large`
	finalize x
```

### 5.3 判定基準

- **許可**: ブロック内が条件式のみ、または一般処理のみ
- **問題**: ブロック内で条件式（`:`演算子）と一般処理が同一階層で混在
- **変換**: 一般処理のみの場合は自動的に`,`挿入によるリスト化

この仕様により、Sign言語の「見えない強さ」と設計純粋性が保たれます。
