# Sign 文字列リテラルとコメント構文

## 概要

Sign の文字列は必ずバッククォート（`` ` ``）で囲む。
コメントと文字列の区別は**先読みルール（閉じバッククォートの有無）**によって決まる。

---

## 1. 文字列リテラル

### 定義

```
string = ` [^\n\r`]* `
```

開始と終了をバッククォートで挟んだ、改行（`\n`/`\r`）とバッククォート自身を除く任意の文字列。

```sign
` greeting に文字列を束縛
greeting : `Hello, World!`
message  : `Sign is elegant`
```

### 特性

- 文字列はシングルライン（改行を含まない）
- 空文字列は `__`（Unit）と同型
- 文字列中にバッククォートは含められない（コメント開始と区別できないため）

---

## 2. コメント構文

### 定義（先読みルール）

```
comment = SOL ` [^\n\r]* EOL              ← 行頭 ` は原則すべてコメント
string  =     ` [^\n\r`]* `               ← 閉じ ` がある → 文字列リテラル
```

> [!IMPORTANT]
> **先読みルール**：**行頭のバッククォートは、閉じたうえで後続があるときだけ式になる。**
> それ以外はすべてコメントである。
>
> - **閉じない** → コメント（EOL まで）
> - **閉じるが、後続が無い** → コメント（`` `説明` `` のように閉じて書いてよい）
> - **閉じて、後続がある** → 式（その行は文字列から始まる式である）
>
> 行頭以外のバッククォートは常に文字列リテラルであり、この規則は関与しない。

```text
`これはコメント（閉じなし）
`これもコメント`                ← 閉じても、後続が無ければコメント
`main.sn`@~    ← 閉じて後続 `@~` がある → 文字列（インポートパス）から始まる式
x : `Hello`    ← 行頭ではない → 文字列リテラル
```

### 衝突がない理由

**行頭から文字列で始まる式は、インポートしかない。** 後続を要求するのはそのためである。

```text
`path/to/file`@~    ← 閉じ＋後続 → 式（インポート）
`path/to/file`      ← 閉じ＋後続なし → コメント
` これはコメント      ← 閉じなし → コメント
```

> [!NOTE]
> **かつてこの規則は「閉じたか」だけで判定していた。** インポートパスを行頭に書けるように
> した際の変更だが、そのために `` `説明` `` のように**閉じたコメントがすべて文字列リテラル
> となり**、コメント中にバッククォートを書くと構文エラーになっていた。
>
> 同時に、この節は「行頭に文字列が来ることは構文上ない」と述べながら、その直後に
> `` `main.sn`@~ `` という行頭の文字列を例示しており、前提と例が食い違っていた。
>
> 判定の根拠を「閉じたか」から「閉じたうえで後続があるか」へ狭めることで、3つが同時に
> 解ける——インポートは通り、閉じたコメントはコメントのままであり、コメントの中に
> バッククォートを書ける。実測では、リポジトリ内の `.sn` すべてを通して「行頭の閉じ文字列
> ＋後続」に該当するのはインポートだけである。

> [!WARNING]
> **ファイルの最終行だけは、この判定が返り値を左右する。**
>
> ファイルスコープが返すのは最後の式であり、そこに文字列を書けばその文字列が
> ファイルの返り値になる（インポートした側が受け取るもの）。
> したがって最終行の行頭バッククォートは、コメントか返り値かの分かれ目にある。
>
> - **コメントを書きたいなら、最終行では閉じてはならない**（閉じなければ必ずコメント）
> - **文字列を返したいなら、名前に束縛してから返す**（`` r : `result` `` の次の行に `r`）
>
> どちらの規則を採っても、最終行のこの一点だけは書き手が決めるしかない——
> 「閉じた裸の文字列」が返り値なのかコメントなのかは、書かれたものからは決まらないためである。
> 以前の規則（閉じたら文字列）ではコメントのつもりが返り値になり、
> 現在の規則（閉じ＋後続で式）では返り値のつもりがコメントになる。**向きが違うだけで、
> どちらも黙って起きる。** 上の2つの書き方はどちらの規則でも意図どおりに読まれる。

## 3. インデント内のバッククォート（ドキュメント文字列）

インデント（タブ）の後に `` ` `` が来る場合は、行頭ではないのでコメントにならない。
行頭以外のバッククォートは常に文字列リテラルであり、先読みルールは関与しない。

```text
calc_func : x ?
\t`ドキュメント文字列（タブ後・閉じあり → 文字列として評価されるが捨てられる）`
\tx * 2
```

この文字列は評価されますが戻り値として使われないため、事実上コメントとして機能します。

---

## 4. 最終行の返値

Sign の実行モデルでは**すべてのファイルは関数**である（`impl/core/execution_model.md` 参照）。

したがって、**ファイルの最終行（最後の非コメント式）がそのファイルの返値**になる。

```text
` greet.sn
name : `World`
`Hello, {name}!`    ← 最終行：このファイルの返値
```

```text
` calc.sn
add : x y ? x + y
mul : x y ? x * y

add 3 4    ← 最終行：7 がこのファイルの返値
```

---

## 5. 複数行の文字列

Sign の文字列は**シングルライン**が基本。

複数行の文字列を扱いたい場合は、文字列のリストまたは連接演算子（空白）を使う：

```sign
` 複数文字列の組み立て
` リスト構築
lines : `Line 1` `Line 2` `Line 3`

`改行文字自体を文字として扱う
text  : `Line 1` \
 `Line 2`
```

注意点として、この言語にはエスケープシーケンスを用意する必要が無い。
`\`後の任意の1文字が文字として扱われる。

---

## 6. Unicode との関係

文字列は `0u` リテラル（Unicode コードポイント）のシーケンスとして扱える：

```text
` ASCII 文字列
hello : `Hello`

` 個別コードポイントとしてアクセス
h : `hello` ' 0   ` → \h（0u48）
```

---

## 7. 文法仕様（実装者向けメモ）

- 字句解析レベルでコメント（閉じなしバッククォート行）を削除しても構わない
- シンタックスハイライトや Language Server は**「行頭から始まり閉じバッククォートがない `` ` `` 行」**をコメント色で表示することが推奨される
- PEG では先読み（lookahead）で閉じバッククォートの有無を判定する
- 詳細な実装仕様は `impl/syntax/grammar.pegjs` を参照

---

## 設計の意図

- **バッククォートのみで文字列とコメントを兼用** → 予約語や専用引用符を増やさず、記号を最小限に保てる
- **行スコープ** → コンパイラがトークン境界を一行ずつ静的に解析できる
- **コメントは SOL かつ閉じバッククォートなし** → 視覚的に明確、予約語不要
- **最終行返値** → 「ファイル = 関数」の実行モデルと一致
