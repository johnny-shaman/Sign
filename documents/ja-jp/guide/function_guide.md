# 関数定義とその型について

Signでは、関数定義の方法が多岐にわたって存在する。  
よって、これら関数定義の方法について、具体例を交えたドキュメントをここに記す。

## ポイントフリー記述

全ての演算子を関数として扱う場合、任意のカッコで演算子を囲むことで関数として扱う。  
この時、前置演算子は、`[<op>_]` 後置演算子は `[_<op>]`と記述する。  
ポイントフリー記述の二項演算子は、複数の引数を貪欲に演算する。  
単項式の後ろに`,`を付けたポイントフリー記述は、そのすべてに適用される。

```Sign

` Sumと同等
[+] 1 2 3 4 5

` mapと同等
[* 2,] 1 2 3 4 5

` 否定する関数
[!_] 2 < 3

` 階乗する関数
[_!] 5

` ポイントフリーの合成はストリームで繋がる（list_model.md §2.4③）
` 「2倍の写像」と「合計の畳み込み」が1回のパイプラインになる
[* 2,] [+] 1 2 3 4 5

` 括弧で括ると値（List）に固まる。畳み込むには後置~で再展開する
[+] ([* 2,] 1 2 3 4 5)~
```

## ? 演算子を用いた定義方法

`?`演算子は、左辺に引数リスト、右辺に本体を有する演算子と解釈できる。

```Sign

f : x y ? x + y
```

### match_caseの記述

`?` の右辺を改行・インデントブロックを挟むことで、本体内の : 演算子はmatch_caseとなる。

```Sign

f : x y ?
	x > 3 : x - y
	y < 3 : x + y
	x y
```

> [!IMPORTANT]
> **本体のインデント行は、左辺が何であっても match_case である。**
>
> 左辺が識別子ひとつだけの場合も例外ではない。仮引数はもっとも条件に使いたい対象であり、そのまま条件として書ける。
>
> ```sign
> UART_STATUS : 0x40011000
> UART_DATA : 0x40011004
>
> uartIO :
> 	output
> 	ready : @UART_STATUS
>  ?
> 	ready : UART_DATA # output
> 	uartIO output
> ```
>
> ここでの `ready : ...` は「`ready` を再束縛する」ではなく「`ready` が非Unitなら右辺を評価する」である。**ローカル変数を置く場所は仮引数リストの側**であり（後述「仮引数リストは関数の状態ベクタである」）、本体には分岐だけを書く。同じ行の形が仮引数リストと本体とで別の意味を持つのは、この分担による。

### 本体から構造体を返す — 境界はカッコ

本体のインデント行が全て match_case である以上、そこに `識別子 : 値` を並べても構造体にはならない。構造体を返したいときはカッコで囲む。**構造体と match_case の境界はカッコである。**

```Sign

f : x y ?
	x != y : [
		a : y / x
		b : x + y
	]
```

カッコの中では `識別子 : 値` はフィールドの定義に戻る。配列を返すならカッコは要らない。

```Sign

` 余積で並べる
f : x y ? x y

` 直積で並べる
g : x y ? x , y
```

#### フィールド名の省略記法

カッコの中に裸の識別子を置くと、**フィールド名も値もその識別子から取る**。

```Sign

f : x y ? [
	x
	y
]
```

`f 1 2` は `x` が 1、`y` が 2 の構造体になる。明示的な定義と混ぜてもよい。

```Sign

f : x y ? [
	x
	b : x + y
]
```

> [!NOTE]
> 省略記法が有効なのは2行以上のブロックに限る。`[x]` は「1要素リストはスカラーと同型」（[`list_model.md`](../impl/type/list_model.md)）の形として既に広く使われており、これをフィールドひとつの構造体と読み替えると `(f 1)` のようなカッコがすべて壊れるためである。

### デフォルト引数の記述（ローカル変数代わりにも使える）

`?` の左辺インデントブロックは : 演算子がデフォルト引数の記述となる。

```Sign

f :
		x
		y : x + 1
		z : y + 1
		~rest
	? x y z rest~
```

> [!IMPORTANT]
> **デフォルト引数には純粋な値式 + Input までが使用可能。Output 演算子（`#`）は禁止。**
>
> 理由は**評価が条件付きだから**である。デフォルト式は、その引数が省略された（Unit が渡された）ときにだけ評価され、呼び出し側が値を渡せば**評価ごと飛ぶ**。
>
> ここに `#`（ストア）を書くと、書き込みが起きるか起きないかが**呼び出し側の引数の数で決まる**ことになる。呼び出し側からは見えない制御フローであり、原理3（危険は明示的なオプトインでのみ）に反する。Output が必要な処理は関数本体（`?` の右辺）に書くこと。本体は無条件に評価されるため、この問題が起きない。
>
> Input（前置 `@`）が許されるのは、そこが**状態の初期化を書く場所**だからである（下記「仮引数リストは関数の状態ベクタである」）。「渡されなければ環境から読む」はこの機構の本来の仕事にあたる。加えて、MMIO のレジスタは読むたびに値が変わりうる（clear-on-read もある）ため、読み出した値を名前に束縛できないと、使用箇所ごとに再読み出しすることになり**正しさ**を損なう。
>
> ```sign
> some_ptr : 0x40011000
>
> ` 禁止：デフォルト引数内での Output（原理4によりコンパイルエラー）
> bad :
> 	x : some_ptr # 42
>  ? x
>
> ` 許可：Input はデフォルト引数に書ける
> good_in :
> 	x : @some_ptr
>  ? x
>
> ` 正しい：Output は本体に書く
> good_out :
> 	x
>  ? some_ptr # x
> ```

### 仮引数リストは関数の状態ベクタである

Sign にはローカル変数を定義する専用の構文が**無い**。仮引数リストのデフォルト引数がその役割を兼ねる。これは機能の不足ではなく、原理1（RISC as-is）の帰結である。

レジスタマシンには「ローカル変数」と「引数」の区別が存在しない。どちらもレジスタであり、引数が届く場所がそのままローカルの住処になる。専用構文を設けることは、ハードウェアに無い区別を言語が発明することにあたる。さらに、ローカルを呼び出し側から**隠す**には退避や遮蔽の命令が要る——外から触れるままにしておく方が as-is であり、かつ無料である。

したがって、デフォルト引数として書いたローカル変数は**呼び出し側から上書きできる**。これは穴ではなく機能である。

```sign
f :
		x
		y : x + 1
		z : y + 1
	? z

` f 3 は 5。すべて計算する
` f 3 10 は 11。y を渡すと y の計算を飛ばす
` f 3 10 99 は 99。z を渡すと z の計算も飛ばす
f 3
f 3 10
f 3 10 99
```

ここから3つの性質が導かれる。

- **再開可能性**：途中の値がすべて名前を持ち、その名前がそのまま入口になる。関数はブラックボックスではなく、任意の中間状態から再開できる計算になる
- **メモ化・部分評価**：デフォルト式は「渡されなかったら計算する」節である。既に値を知っている呼び出し側が渡せば、その計算は実行されない。専用の機構をひとつも足さずにキャッシュが手に入る
- **蓄積再帰の素直な表現**：`go acc rest` のような再帰は「状態を渡して自分を再開する」ことに他ならない。初回の呼び出しだけが `acc` を省略してデフォルトを取り、以降の呼び出しは状態を渡す

```sign
go :
		acc : 0
		rest : __
	?
		(rest) : go (acc + (rest ' 0)) (rest ' 1~)
		acc

` どちらも 10。前者は最初から、後者は途中の状態を渡して再開している
go __ [1 , 2 , 3 , 4]
go 6 [4]
```

> [!NOTE]
> **デフォルト値に `__` を置くと、その引数について完全性公理が働かなくなる。**
>
> `__` を受け取っても呼び出しは潰れず、本体が走る。つまりその引数の定義域は `__` まで持ち上げられる。Pass 3 はこれを information として名指しする（`reason: "lifted-domain"`）。
>
> **終端に仕事があっても、公理を止めるのは本来の形ではない。** 完全性公理が与える終端は答えが必ず `__` になるが、終端に**仕事**があるとき——残った状態を吐き出す、閉じ括弧を補う——は、**その仕事を高階関数で渡し、崩壊を `|` で受ける**。
>
> ```sign
> ` 子の呼び出しが公理で潰れた瞬間、この階層の st が最終状態である
> w : k s st ?
>   (w k (s ' 1~) (st (s ' 0)~)) | (@k st)
>
> w $close `abc` __
> ```
>
> [`system_semantics.md`](../impl/core/system_semantics.md) のポーリング標準形（`@STATUS & @DATA | read __`）と同じ形である。**終端に何をするかは関数ではなく呼び出し側が決める**のだから、渡すのが筋であり、`$` で渡された関数はコンパイル時に具体化されるのでコストも増えない。
>
> **代償。** 公理を止める書き方でも動くが、以降その関数は正当な「空」と、失敗して `__` に落ちた値とを区別できない。
>
> リストを受けるだけの引数であれば、`[~xs]` や `[x ~xs]` のように**分解の形で宣言する**方がよい。Unit は分解すべき構造を持たないため、失敗値がそこを通れなくなる。実例は [`examples/n-queen/n_queens.sn`](examples/n-queen/n_queens.sn) を参照——盤は空から始めず、1つ目のクイーンの列を種にしている（`__ = []` なので**空の器は関数へ渡せない**）。

> [!IMPORTANT]
> **分解の形・rest 形の仮引数にデフォルト値は書けない。**
>
> ```Sign
>
> f : [x ~xs] : [1 2 3] ? x    ` 構文エラー
> f : [~xs]   : [1 2 3] ? xs   ` 構文エラー
> f : ~xs     : [2 3 4] ? xs   ` 構文エラー
> ```
>
> 参照が指すのは**呼び出し側が置いた記憶**である（[`stack_abi.md` §4.6](../impl/memory/stack_abi.md)「参照で渡すのはメモリに置かれているものだけ」）。そこへデフォルトを付けると「渡されなかったら呼ばれた側が器を作る」ことになり、**所有が反転する**——しかも作る場所は自分のフレーム（alloca）なので、返せば宙に浮く。返値の設計が sret（呼び出し側がスロットを提供する）へ向かっているのと逆である。
>
> 裸の rest（`~xs`）は stream＝**規則**であり（[原理3](../impl/0_design_principles.md) の表）、既定値として置ける「実体化した列」とは別物なので、やはり書けない。
>
> 裸の仮引数のデフォルトが書けるのは、値がレジスタか `.rodata` に**既に在る**からである——作る場所の問題が起きない。器を既定で持たせたいなら、呼び出し側が作って渡す。

### デフォルト引数と、match_caseの記述は共存可能。

```Sign

f :
		x
		y : x + 1
		z : y + 1
		~rest
	?
		x > 3 : x - y rest~
		y < 3 : x + y rest~
		z rest~
```

これらの関数にそれぞれ型を与えた方がよい。

## 関数適用時

デフォルト引数を持つ関数の適用だけが異なる挙動となる。

```Sign

` 通常は部分適用となる動作（静的脱糖によりラムダに変換される）
` 下の定義は $p0 ? add $p0 10 と同等
add : a b ? a + b
f : add _ 10

` 評価結果: 13
f 3

g :
		x
		y : x + 1
		z : y + 1
	? x y z

` g はデフォルト引数を持つため、これらはアリティ計算から除外される。
` よって、デフォルト引数以外の実引数を渡すだけで自動的に評価が実行される。
` 評価結果: 3 4 5
g 3

` 例えば、予期せぬ演算で __（Unit値）が算出された場合、デフォルト引数を持たない関数は __ に短絡評価される。
` （Unit伝播・即時崩壊）
` 3 < 2 が __ になるため、add __ 1 となり、評価結果は __ に崩壊する
add 3 < 2 1

` デフォルト引数を持つ関数の引数に __ が渡された場合、暗黙でデフォルト引数の定義値による評価が行われる（フォールバック）。
` 3 < 2 が __ になるため、g 1 __ となり、y にはデフォルト値 x + 1 (2) が適用される。評価結果: 1 2 3
g 1 3 < 2

` 可変引数（~rest）に __ が渡された場合の挙動：
` 可変引数はデフォルト引数と「同じ」ように振る舞います。
` つまり、__ が渡された場合は完全性公理による崩壊は起きず、暗黙のデフォルト値である __（空リスト）へフォールバックし、
` 関数は通常通り実行されます。
h : x ~rest ? x rest~

` 評価結果: 1 （__ は空リストとして扱われ、rest~ で展開されると消去されるため）
h 1 __
```

## カッコ囲みの仮引数リストによるチルダ省略

仮引数リスト全体をカッコで囲んで定義した関数は、実引数として渡されたリストや構造体を、呼び出し側で後置チルダ `~`（展開）を付与することなく、そのまま直接受け取ることができます。
この構文の場合、参照が2つ以上あっても参照の数だけカッコで囲むことで、参照の展開による境界を明示することが出来ます。
もちろん、デフォルト引数やmatch_caseとの共存も可能です。
```Sign
` 仮引数リストをカッコで囲む
` 再帰呼び出しはカッコで囲む——適用（tier 10）は加算（tier 13）より緩いため、
` カッコが無いと x + sum_list xs は (x + sum_list) xs と読まれてしまう
sum_list : [x ~xs] ? xs & x + (sum_list xs) | x

` 呼び出し側はチルダなしでリストを渡せる。評価結果: 15
sum_list [1 2 3 4 5]

` デフォルト引数・match_caseとの共存例
func_mixed :
		[
			x
			y : x + 1
			~z
		]
	?
		x > 3 : x - y
		y

` 評価結果: -1 (x=5, y=6. x > 3 なので 5 - 6 = -1)
func_mixed [5]

` 評価結果: 3  (x=2, y=3. x > 3 は偽(__)のため、y が評価される)
func_mixed [2]

` 評価結果: 10 (x=2, y=10. x > 3 は偽(__)のため、y が評価される)
func_mixed [2 10]
```

### リストを畳む再帰は、必ずこの形で書く

上の `sum_list` に終端条件が書かれていないことに注目してほしい。これは省略ではなく、
**ブラケット分解でなければ完全性公理が終端を与えられない**ためである。

```sign
` 良い: 終端条件を書かなくても止まる
map : f [h ~t] ? @f h  map f t

map $[+ 2] [1 2 3 4]     ` [3 4 5 6]
map $[+ 2] []            ` __
```

リストが尽きると `t` が `__` になり、それを受け取った次の呼び出しがブラケット仮引数へ
`__` を渡す。ブラケットは「渡された1個の実引数を分割代入する」宣言なので、分解する対象が
無ければ呼び出し全体が完全性公理（`f __ = __`）で潰れる。これが終端である。

裸の rest（`f ~xs`）では止まらない。rest は引数が何個でも吸うため呼び出しが常に飽和し、
本体へ再入し続ける。終端条件を自分で書く羽目になり、[原理5](../impl/0_design_principles.md)に反する。

```sign
` 悪い: 止まらない
map : f ~xs ? @f (xs ' 0)  map f (xs ' 1~)~
```

> [!IMPORTANT]
> **`x = __` は決して真にならない。空の判定を比較で書こうとしないこと。**
>
> 比較演算子は左辺が零射（`__`）へ落ちた時点で結果が `__` に確定するため、右辺を評価せず
> 短絡する（[`operator_table.md`](../impl/syntax/operator_table.md) 「Unit 欄の読み方」）。
> したがって `xs = __` は、`xs` が空のときこそ `__`（偽）になる。
>
> ```sign
> [] = __      ` __（真にならない）
> __ = __      ` __
> ```
>
> `xs = __ : __` のような終端ガードは**必ず死ぬ**。動いているように見えるコードがあれば、
> それは完全性公理が終端させているのであって、ガードが効いているのではない。
> どうしても空かどうかを値として見たい場合は `!xs`（`__` の否定は恒等射＝真）を使うが、
> 再帰の終端としては上の通り書かずに済ませるのが正しい。

### 展開（後置 `~`）で固定アリティは埋められない

裸の rest（`~xs`）は stream であり、**長さが静的に決まらない**。したがって展開して渡す形が
飽和するかどうかをコンパイル時に判定できない——コンパイラは「実引数が1個しか無い」と見て
部分適用として印付ける。

| 受け側の仮引数 | 呼び方 | 結果 |
|---|---|---|
| `~xs`（裸 rest） | `g (f 3)~` | 通る（rest は何個でも吸う） |
| `a ~rest` | `g (f 3)~` | 通る |
| `[a b c]`（ブラケット） | `g (f 3)` | 通る。**`~` は要らない** |
| `a b c`（固定アリティ） | `g (f 3)~` | **通らない**——部分適用になる |

これは「コンパイラが全部決める、実行時に判定を投げない」という方針の帰結である。リストの
長さがコンパイル時に決まらない以上、飽和したかどうかも決まらない。決まらないものを
実行時に判定させないので、部分適用として静的に確定させる。

**ブラケット分割代入が要求する実引数は常に1個**なので、この不定性が生じない。
[原理3](../impl/0_design_principles.md)の表が挙げている「裸の `~xs`（stream、pull型）」と
「`[x ~xs]`（参照渡し）」の対比が、そのままこの違いである。受け側を固定アリティで書きたい
ときは、展開ではなくブラケットで受けること。

```sign
` 蓄積は再帰の引数として明示的に渡す。デフォルト式は自分自身を参照できないため
` （let* の規則）、デフォルトは初期値専用である。
` 積む演算子は余積（空白）——`,` は直積なので入れ子になる。
read_n :
		n
		acc : __
	?
		n = 0 : acc
		read_n (n - 1) ((0.0 + @sensor) acc)

` 受け側はブラケット。展開（`~`）が要らず、実引数はいつでも1個。
consume : [a b c] ? a + b + c

consume (read_n 3)
```

## 構造体メンバーの一致による自動バインディング

仮引数リスト全体が `[ ]` で囲まれている関数に構造体を実引数として渡す際、構造体のメンバー名（キー）と関数の仮引数名が一致している場合、順番に関わらず自動的に名前ベースで分割代入（バインド）が行われます。

> [!NOTE]
> **これが成り立つのは、名前付きスロットの意味論が「名前→値の有限写像」だからである。**
>
> 名前付きスロットで関心事になるのは「何が在るか」であって「どこに在るか」ではない。
> 物理オフセットは名前でソートした正規順に割り当てられるが、その順序は言語から観測できない
> ——`==` は Hom集合の一致で宣言順を問わず（[`type_system.md` §6.2](../impl/type/type_system.md)）、
> 位置アクセスも持たない。だから順番に関わらず名前で束縛できる。
>
> 一方その**表現**は固定オフセットの連続ブロックであり、キー探索もハッシュも動的な追加も
> 存在しない。名前はコンパイル時にオフセットへ解決され、Pass 4 には残らない。
> つまり**辞書の意味論を構造体のコストで得ている**。上の分割代入が辞書の分解のように
> 読めるのに1命令ずつのフィールドアクセスへ落ちるのは、この二面性による。
>
> 順序そのものが関心事のとき（バイト並び、MMIO、シリアライズ済みデータ）は、名前を持たない
> **連番スロット**（`1 , 2 , 3`）を使う。そちらは宣言順がそのまま物理配置になる。
この構文の場合、参照が2つ以上あっても参照の数だけカッコで囲むことで、参照の展開による境界を明示することが出来ます。
もちろん、デフォルト引数やmatch_caseとの共存も可能で、Listの時の仮引数リストでの展開と同様の構文で定義できます。

```Sign
` 構造体を受け取る関数、~obj は必須ではないが、定義時に渡した構造体以下の構造体を保持したい場合に使う。
calc_diff : [foo bar ~obj] ? foo - bar

` メンバー名を一致させた構造体をそのまま（チルダなしで）渡す
calc_diff [
	bar : 20
	foo : 100
]
` 評価結果: 80 (foo = 100, bar = 20 が自動で紐づく)

func_mixed :
		[
			foo
			bar : foo * 2
			~obj
		]
	?
		foo > 3 : foo - bar
		bar

func_mixed [
	foo : 4
]
` 評価結果: -4 (foo = 4, bar = 8. foo > 3 は真のため、foo - bar が評価される)

```
